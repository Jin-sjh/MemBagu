# 移动端选型：vw 与 rem 方案对比

## 【问题】

移动端布局适配应如何在 vw 与 rem 方案之间选型？原因是什么？

## 【回答】

### 最终选型：vw 方案（优先）/rem 方案（兼容老项目）

### 核心原因：

1. **开发效率高**：纯 CSS 实现，无需 JS 动态计算根元素字体，减少代码冗余和潜在 bug

2. **适配性完美**：天然基于视口宽度等比缩放，完美还原设计稿，适配所有移动端屏幕尺寸

3. **维护成本低**：仅需一次单位换算，后续开发无需维护断点，适配逻辑简单

4. **兼容性良好**：现代移动端浏览器（包括微信小程序、WebView）全面支持 vw 单位，无需额外兼容

5. **性能更优**：无 JS 运行时计算，避免页面闪烁，提升渲染性能

## 真实业务 / 面试场景（案例补充）

### 场景 1：老项目用 rem，新项目选 vw
**背景**：三年前项目用 `lib-flexible` + `rem`（JS 动态算根字号），现在新项目直接 `vw`。
**为什么**：vw 纯 CSS、无需 JS 运行时，避免 flexible.js 在字体加载时抖动；但老安卓 WebView（部分国产浏览器 vw 支持差）才需要 rem 兜底。新项目现代浏览器全面支持 vw，优先选。

### 场景 2：1px 边框用 vw 会"消失"
**为什么**：设计稿 750px 宽，1px 物理边框换算成 vw 是小数（约 0.133vw），部分浏览器向下取整成 0 就看不到了。
**解决**：边框仍用 `1px` 写死，或用 `transform: scale(0.5)` 模拟 hairline 边框。

### 场景 3：大屏 Pad 上 vw 放大过头
**为什么**：vw 跟随视口宽度等比放大，在 iPad 上元素会大得离谱。
**解决**：给根容器加 `max-width`（如 750px）并居中，限制最大缩放。
