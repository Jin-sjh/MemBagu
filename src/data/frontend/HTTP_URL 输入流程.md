# 输入 URL 会发生什么

## 8. 输入 URL 会发生什么

## 【问题】
浏览器输入 URL 后发生了什么？

## 【回答】

浏览器输入 URL 后，会按以下流程完成从输入到页面渲染的全过程：

**1. 输入解析与缓存检查**
- 浏览器解析输入内容，判断是 URL 还是搜索词；
- 检查浏览器缓存（Memory Cache → Disk Cache），如果命中且未过期，直接读取缓存资源。

**2. DNS 解析**
- 若未命中缓存，向 DNS 服务器查询域名对应的 IP 地址；
- 流程：浏览器缓存 → 操作系统缓存 → 路由器缓存 → ISP DNS 服务器 → 递归/迭代查询。

**3. 建立 TCP 连接**
- 根据 IP 地址，通过三次握手与服务器建立 TCP 连接：
  - 客户端发送 SYN 包（请求连接）；
  - 服务器回复 SYN+ACK 包（同意连接）；
  - 客户端回送 ACK 包（连接建立完成）。
- 若使用 HTTPS，在 TCP 连接后进行 TLS 握手，协商加密套件、验证证书，建立安全连接。

**4. 发送 HTTP 请求**
- 浏览器构造 HTTP 请求报文（请求行、请求头、请求体），发送给服务器；
- 请求头包含 Cookie、User-Agent、Accept-Encoding 等信息。

**5. 服务器处理请求并返回响应**
- 服务器接收请求，解析请求，匹配后端服务（Nginx 反向代理到应用服务器）；
- 应用服务器处理业务逻辑，生成响应报文（状态码、响应头、响应体），返回给浏览器。

**6. 浏览器解析响应与渲染页面**
- 解析 HTML，构建 DOM 树；
- 解析 CSS，构建 CSSOM 树；
- 结合 DOM 与 CSSOM 生成渲染树（Render Tree）；
- 布局（Layout/Reflow）：计算每个节点的位置和大小；
- 绘制（Paint）：将节点绘制到屏幕；
- 合成（Composite）：将页面分层，交给 GPU 合成显示。

**7. 关闭连接**
- 请求完成后，通过四次挥手关闭 TCP 连接（或保持长连接复用）。

## 9. 输入 URL 到页面加载完成，发生了什么？

## 【问题】
输入 URL 到页面加载完成，发生了什么？

## 【回答】

- **浏览器处理**：判断（搜索词 || URL）；检查本地缓存是否有可用资源

- **DNS 解析**：【域名 -> IP 地址】（检查本地 DNS 缓存，没有就请求 DNS 服务器）；拿到服务器 IP 地址

- **建立 TCP 连接（三次握手）**

- **发送 HTTP 请求**

- **服务器处理请求并返回响应**

- **浏览器接收响应，开始解析**

- **浏览器渲染页面**：解析 HTML 建立 DOM 树；解析 CSS 建立 CSSOM 树；合并为 Render 树 -> 布局（Layout）-> 绘制（Paint）-> 合成（Composite）

- **关闭 TCP 连接（四次挥手）**

## 真实业务 / 面试场景（案例补充）

### 场景 1：输入网址回车后白屏/很慢，怎么定位
**落地**：按流程逐步排查——浏览器/Disk 缓存是否命中、DNS 解析是否慢、TCP+TLS 握手耗时（HTTPS 多一次握手）、首字节 TTFB（服务端慢）、资源加载与渲染（大 JS/CSS 阻塞）。每一步都能在 DevTools Network 时序里看到卡在哪。

### 场景 2：HTTPS 站点首次访问明显更慢
**为什么**：比 HTTP 多了 TLS 握手（证书校验、密钥协商），首次 RTT 多几倍；之后靠会话复用（session resume）/ 0-RTT 提速。

### 场景 3：面试高频——"从输入 URL 到页面展示"全流程
**要点**：必考题。按"URL 解析与缓存 → DNS → TCP 握手 → TLS（HTTPS）→ 发请求 → 服务器响应 → 解析 HTML/构建 DOM → 渲染树/布局/绘制/合成 → 呈现"逐段讲，并说清每步可能瓶颈。

## 【问题】
从 URL 到页面展示，首屏性能可能在哪些环节成为瓶颈？如何优化？

## 【回答】
首屏不是一个单点事件，**网络 TTFB、资源阻塞、解析执行、主线程长任务、布局绘制都可能成为瓶颈**。资源调度上，**Preload 用于当前页面尽快需要的关键资源，Prefetch 更偏未来导航**；错误使用会竞争带宽。

优化顺序：先看 Network 的 TTFB/资源瀑布，再看 Performance 的解析、脚本、Layout/Paint，最后根据 LCP/FCP/INP 选择措施；可用 CDN、压缩、缓存、关键 CSS、代码拆分和延迟非关键脚本，但必须在真实设备和代表性网络下对比。

## 【问题】
async 和 defer 有什么区别？为什么不能只说"下载速度差异"？

## 【回答】
脚本可能暂停 HTML 解析；**`defer` 通常在解析完成后按顺序执行**，**`async` 下载完成后尽快执行且顺序不保证**。常见误区是把两者差异仅理解为下载速度——实际上**执行时机和顺序都不同**：defer 保持顺序且延后到解析结束，async 一旦下载完就执行、顺序不可预期。

可用 Performance/Network 验证二者对解析阻塞的影响。另外，"页面展示等于 HTML 下载完成"也是误区：浏览器可流式解析，也可能等待关键资源。

---

## 【问题】
面试时怎么答"从 URL 到页面展示"？

## 【回答】
按链路逐段讲：**URL 解析与缓存 → DNS → 连接与 TLS → HTTP 获取资源 → HTML/CSS 解析 → 构建 DOM/CSSOM/Render Tree → Layout → Paint → Composite**。重点强调脚本和 CSS 可能阻塞解析或渲染，**性能分析要用 Network 看请求链、用 Performance 看主线程和渲染阶段，不能只背网络七层顺序**。

可补充首屏瓶颈可能出现在 TTFB、资源阻塞、主线程长任务或布局绘制任一环，并用 LCP/FCP/INP 衡量；Service Worker、缓存命中、预连接、HTTP/2/3 和 SSR 会改变具体链路，不应只讲一条默认路径。
