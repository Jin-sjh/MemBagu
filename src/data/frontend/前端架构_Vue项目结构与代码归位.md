# Vue项目结构与代码归位

## 【问题】
Vue3 + Vite 项目的常见目录结构是怎样的？

## 【回答】
典型 `src/` 结构如下：

```text
src/
├── main.ts          # 应用入口
├── App.vue          # 应用壳
├── router/          # 路由配置
├── stores/          # Pinia 状态
├── views/           # 页面级组件
├── components/      # 跨页面复用组件
├── api/             # 接口函数和协议适配
├── composables/     # 可复用组合式逻辑
├── utils/           # 低耦合纯工具
├── styles/          # 全局样式和设计变量
└── assets/          # 参与构建的资源
```

目录的目的不是为了“看起来整齐”，而是表达**所有权、依赖方向、复用范围和生命周期**，限制代码无边界地增长。项目小时可简化，变大后按业务域组织。

---

## 【问题】
每个目录的职责边界是什么？（views / components / api / stores / composables / utils）

## 【回答】
- **views**：页面级业务入口，负责页面接口编排、页面状态、路由跳转与组合业务组件。
- **components**：可复用 UI，通过 Props/Emits/Slots 协作，不直接读某页面 Store。
- **api**：接口适配层，页面调用业务函数而非到处拼 URL。
- **stores**：真正跨页面/跨组件共享、生命周期长、需统一操作调试的状态。
- **composables**：复用响应式状态、生命周期和副作用（行为逻辑）。
- **utils**：低耦合纯工具，输入/输出明确、副作用可控。

判断标准：**删掉某页面后它是否仍属于整个应用的公共壳**，而不是文件名叫不叫 `App.vue`。

## 【问题】
一段代码应该归到哪个目录？决策依据是什么？

## 【回答】
按决策树判断：

```text
它是路由对应的完整业务页面？ → views/
它是可复用 UI 结构？ → components/ 或页面专属 components/
它是跨页面共享状态？ → stores/
它是接口或协议适配？ → api/services/
它是带响应式状态/生命周期的复用逻辑？ → composables/
否则 → utils/ 或当前业务模块内部
```

优先按**所有权、复用范围、生命周期、依赖方向**判断，不要只按代码行数或个人习惯归类。

---

## 【问题】
为什么接口函数不直接写在页面里，而要放 api 层？

## 【回答】
集中到 `api/` 便于**复用、Mock、测试、协议变更和统一错误处理**，让页面调用业务函数而不是到处拼 URL。

请求实例、鉴权、超时、错误规范化和响应转换放在 request 层；具体业务接口放在领域文件。API 层**不应直接操作 DOM 或修改页面 UI**，但可负责协议到领域数据的适配。

---

## 【问题】
什么状态该放 Pinia？页面专属组件放哪里？

## 【回答】
看**共享范围和生命周期**：登录用户、权限、主题、购物车等真正跨页面共享的放 `stores`；局部弹窗开关、表单输入、当前行选择通常留在页面或组件。

页面专属但复杂的组件放 `views/Order/components/`，**稳定跨页面复用后再上移**到全局 `components/`，避免过早污染公共目录、增加维护成本。

---

## 【问题】
面试时怎么答 Vue 项目结构与代码归位？

## 【回答】
Vue 项目通常由入口、应用壳、页面、组件、API、Store、composable、工具、样式和资源组成。**页面负责业务编排，组件负责 UI 复用，API 负责接口适配，Store 负责真正跨页面的状态，composable 负责复用响应式逻辑，utils 保持低耦合**。

目录的目的不是形式统一，而是明确**所有权、依赖和生命周期**。常见错误：把所有代码塞进 `App.vue`、页面专属组件放全局 `components`、所有接口响应放 Store、把请求/DOM/Store 都放进 `utils`。
