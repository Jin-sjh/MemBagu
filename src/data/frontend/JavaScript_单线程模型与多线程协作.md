# 2. JS 的单线程模型与操作系统的多线程如何协作？

## 【问题】
JS 的单线程模型与操作系统的多线程如何协作？

## 【回答】
核心：JS 主线程永远只有一个，但浏览器会使用多个系统线程来完成异步任务，然后通过事件循环把结果返回。

## (1) JS 单线程的原因

- 避免多线程同时修改 DOM 导致状态一致性问题
- 使开发模型更简单：无锁、无竞争

## (2) 浏览器如何用多线程协作

虽然 JS 是单线程，但浏览器内核会启动多个线程来执行耗时任务：

| 任务 | 实际执行位置 |
|------|-------------|
| setTimeout | 定时器线程（Timer Thread）不是 JS 执行线程 |
| 网络请求 | Network Thread，真正用 socket 的是 OS |
| 文件读取 | OS 的 File I/O 线程 |
| 图片解码 | Image Decode Thread |
| Layout / Raster | 由独立 Compositor/Raster Thread 完成 |
| Web Worker | 独立的系统线程 |

当这些线程任务完成时，会把事件加入主线程的 EventLoop 中排队。

## (3) EventLoop 的意义

EventLoop 只是调度中心，不执行异步操作本体。
异步操作本体由浏览器线程或 OS 线程完成。

这是前端理解性能和异步的基础。

## 真实业务 / 面试场景（案例补充）

### 场景 1：setTimeout 计时"不准"
**背景**：`setTimeout(fn, 0)` 想立刻执行，却要等几百毫秒。
**为什么**：JS 主线程正忙着跑一个 100 万次的 for 循环（同步任务），定时器回调只能等主线程空闲、再进事件循环排队执行。
**解决**：把长任务拆成小块、或丢给 Web Worker，主线程不阻塞，回调才能及时跑。

### 场景 2：网络请求/图片解码为什么没卡住 UI
**为什么**：这些耗时操作由浏览器的 Network Thread、Image Decode Thread 等系统线程完成，不在 JS 主线程，完成后把结果通过事件循环丢回主线程。
**应用**：这就是"单线程写代码、多线程跑底层"的协作模型。

### 场景 3：面试——为什么 setTimeout(fn,0) 不是 0 毫秒后立刻执行
**要点**：0 只是"最小延迟"，回调要先等当前同步代码执行完、再等事件循环取到它；真正并发的耗时任务应交给浏览器线程或 Web Worker，而非主线程。
