# 构建前端架构五要点

## 【问题】
什么是前端架构？它为什么在前端进阶（拿更高薪资）中绕不开？

## 【回答】
所谓前端架构指的是：**在前端开发中，设计和组织应用程序的基本结构和组件之间关系的方法和原则**。当想在前端领域拿到更高薪资时，前端架构是绕不过的话题——它关心的不是某一个功能怎么写，而是整个应用如何被结构化、如何保持一致性与可维护性。

## 【问题】
构建前端架构时，系统设计（设计系统）应该包含什么？它和「组件库」有什么区别？

## 【回答】
现代设计系统**远不止于组件库**。大多数设计系统基于流行组件库（Element、AntD、Arco 等，它们都有统一的 Design），但完整的设计系统还应包含一层**设计师和开发都能理解的设计语言**，既作用于结构、也作用于 UI。

设计系统中的 UI 组件范围很广：从**最简单的 UI 元素（按钮、文本框）**，到**复杂组合（小部件、对话框）**，并统一处理**主题、排版、图标**等。任何一个应用都应该有自己的设计系统，避免各页面各写一套。

## 【问题】
前端组件处理（组件组织）的核心原则是什么？传统的共享目录方式在规模变大后有什么问题？

## 【回答】
核心原则：前端要让整个应用保持**一致的外观和感觉**，最自然的方式是**在应用不同部分大量重用组件**。

传统做法是在 `src/components/shared/` 下保留一个共享组件目录（NavBar、Footer、CustomButton、ModalWrapper 等）。随着开发推进，共享目录里的组件会**越来越庞大、越来越难复用**。

超出一定规模后，这种**单体结构**会从几个维度限制生产力：

- **认知负荷更高**：要找到需要修改的组件更费劲。
- **影响面难评估**：改一个组件后，需要测试并理解它对整个项目的影响。
- **跨应用复用困难**：在企业里，跨多个应用复用这些组件很难。
- **调试成本高**：开发/测试每个组件都要跑整个应用才能加载相关 UI。

应对方式是把前端**重组为一个可组合的平台，使用独立组件**（按 `layout/ui/forms/dataDisplay/navigation` 等维度拆，配合 `templates`、`pages`），让架构在长期内可被塑造成不同结构和风格。

## 【问题】
前端资源优化可以从哪些维度入手？各自的关键手段是什么？

## 【回答】
可以按资源类型逐项优化，关键手段如下：

- **图片**：位图（JPEG/PNG/GIF/WebP）用压缩工具减体积，优先 **WebP** 等新一代格式，并用 **srcset 实现响应式图片**；矢量图（SVG）本身可伸缩且体积小，做缩小，必要时**内联 SVG 作为图标**以减少 HTTP 请求。
- **JavaScript**：减少对沉重库/框架的依赖，用 **tree shaking 删除未使用代码**，捆绑+缩小，用**代码分割按需加载**；自定义脚本用 Gzip 或 **Brotli** 压缩，非立即需要的脚本**延迟加载**；可用 **HTTP/2** 更高效地加载资源。
- **CSS**：缩小 CSS，用**关键 CSS 内联**加快首屏呈现；用 **PostCSS** 等做自动前缀和跨浏览器优化。
- **字体与图标**：Web 字体选 **WOFF2**，用 **font-display: swap 保证字体加载期间文本可见**，限制字体变体、只加载所需字符；图标用 **SVG 精灵或图标字体**，React 等框架可内联 SVG 图标组件减少请求。
- **视频与音频**：视频压缩并用 **WebM** 等现代格式在更低码率拿到更好质量，延迟加载、交互前用占位图；音频用 **AAC** 平衡体积与质量，按需加载省带宽。
- **文档**：PDF/Word/Excel 压缩，仅在用户请求时加载。
- **测量工具**：用 Chrome DevTools 的 **性能、网络、Lighthouse** 分析性能与各资产类型影响；React 等框架中可用 **CSS Modules / styled-components** 做作用域与优化。

## 【问题】
前端可以在哪些层级做缓存？各层级分别怎么做？

## 【回答】
缓存能提升性能、减少服务器负载、加快内容交付，可在多个层级实施：

- **浏览器缓存**：为 CSS、JavaScript、图片、字体等静态资源配置 **HTTP 缓存头（Cache-Control、Expires）**，让浏览器本地存储并在后续访问复用；用 **Web Worker / Service Worker** 缓存动态内容和资源，实现细粒度控制并启用离线能力。
- **CDN 缓存**：CDN 在**靠近用户的边缘节点**缓存静态资源，显著降低延迟；要确保 **CDN 配置与缓存失效策略匹配**，避免给出过时内容。
- **DNS 缓存**：DNS 查找可在**浏览器级或操作系统级**缓存已访问域的 IP，减少后续同域请求的 DNS 查找时间。
- **应用级缓存**：在应用内部缓存**频繁访问的数据（如 API 响应、计算结果）**。

## 【问题】
什么是乐观的并发请求处理（乐观更新）？实现时要注意什么？

## 【回答】
乐观的并发请求处理是前端的一种策略：通过**假设操作将成功、不等服务器确认来增强用户体验**。典型例子：用户发表评论时，**直接把评论显示出来，就像已经成功发表了一样**，即使服务器还没返回响应。

注意点：需要配套**撤销操作**。如果服务器最终失败，要**撤销这次更改并通知用户**（例如删除刚加上的评论、显示错误消息）。是否撤销取决于具体需求，但至少要有失败兜底。
