# 登录鉴权与路由权限

## 【问题】
登录系统里认证和授权的区别是什么？

## 【回答】
**认证回答"你是谁"，授权回答"你能做什么"**。前端可以改善体验和隐藏无权限 UI，但最终资源权限必须由服务端校验。常见授权模型包括：**RBAC（用户绑定角色，角色关联权限，适合多数中后台）**；**ABAC（结合用户、资源和环境属性判断，适合规则复杂且安全要求高的系统）**；**数据权限（不仅判断能否进入页面，还要判断能读取哪些记录）**。

---

## 【问题】
常见的身份验证方案有哪些，怎么选型？

## 【回答】
登录系统可能包含账号密码、手机号/验证码、第三方 OAuth/OIDC、SSO、多因素认证等。三种典型方案：

- **Cookie + Session**：登录成功后服务端创建 Session 存自身或 Redis，通过 Cookie 返回 Session ID，后续请求自动携带，适合传统 Web 和服务端主动撤销，但分布式部署需要共享会话、粘性会话或集中式存储。
- **JWT**：带签名的令牌格式，可验证签名、过期时间和声明，便于跨服务传递身份，但令牌体积较大，已签发的 Token 在过期前不一定能立即撤销，通常要配合短有效期、Refresh Token、版本号或撤销机制，**payload 默认不是加密内容，不能放敏感秘密**。
- **OAuth 2.0 / OIDC**：主要解决授权委托与身份层，典型流程是跳转授权页→用户同意回调→服务端校验 `state`、授权码和 OIDC `nonce`→建立本系统会话；前端不应把第三方 access token 当成自己系统的长期登录凭证。

选型要看客户端类型、跨域、撤销需求、XSS/CSRF 风险和合规要求，不能简单用"JWT 更先进"作为结论。

## 【问题】
什么是双 Token（Access + Refresh）机制，刷新时为什么要 single-flight？

## 【回答】
常见模式是**短期 Access Token 加长期 Refresh Token**：Access Token 调用业务 API，过期时用 Refresh Token 请求新 Access Token，失败则撤销会话、清理状态、重新登录。Refresh Token 更适合使用 **HttpOnly、Secure、SameSite Cookie**，并配合旋转、重用检测、设备会话和撤销。

前端刷新要使用 **single-flight**：多个请求同时收到 401 时只发起一次 refresh，其余进入等待队列；刷新成功只重试原请求一次，刷新失败统一登出，防止无限循环。**Refresh Token 本身也会过期、撤销或被重用，不能把"刷新成功"理解为永久登录**。

## 【问题】
应用启动时如何恢复登录状态？

## 【回答】
**不要在应用启动时把"本地存在 token"直接当成"已登录"**。更可靠的流程是：应用启动 → 状态 `unknown`、显示启动占位 → Cookie 静默验证或调用 `/me` → 成功则 `authenticated`，失败则尝试刷新或 `unauthenticated` → 恢复路由和用户数据。

建议使用状态模型区分：`status`（unknown/authenticated/unauthenticated/refreshing）、`userInfo`、`roles/permissions`、`accessToken`、`authExpiry`。如果使用 HttpOnly Cookie，前端不能读取 Cookie，应通过请求验证会话；如果使用内存 Access Token + HttpOnly Refresh Token，刷新页面后需要通过刷新接口恢复短期令牌。

## 【问题】
Axios 请求层如何处理 401 和 Token 刷新？

## 【回答】
请求层通常负责**注入凭证、统一处理 401/403、取消、错误上报和请求重试**；页面层负责具体表单错误、空态和业务提示。请求返回 401 时：判断是否正在刷新，是则进入等待队列，否则发起唯一 refresh 请求；成功则更新凭证、重试原请求，失败则清理状态、跳转登录。

刷新必须是 **single-flight**，同一时间只允许一个刷新请求；重试请求要带重试标记，避免"401 → refresh → 401 → refresh"的无限循环。**`403` 通常表示已认证但无权访问，不能一律当成登录过期**。

## 【问题】
前端路由保护和权限粒度怎么设计？

## 【回答】
Vue Router 可在路由 `meta` 声明 `requiresAuth` 和 `permissions`，`beforeEach` 判断登录状态、等待初始化和重定向，通过 `query` 或受控状态保存原目标路由，要排除登录页、公用页和错误页防止重定向循环。React Router 可用 `RequireAuth` 组件包裹私有路由，未认证时保存 `location` 并跳转登录，恢复后导航到原始位置。

权限粒度分四层：**页面权限（能否进入路由）、菜单权限（是否展示导航）、操作权限（是否启用按钮）、数据权限（能看到哪些记录），最终由服务端执行**。无论 Vue 还是 React，路由保护只是前端体验层，API 必须再次授权；前端权限集合可能过期或被篡改，不能作为安全边界。

## 【问题】
Token 应该怎么存储，登出要注意什么？

## 【回答】
存储选择要结合风险：**localStorage 易用且可跨刷新，但 JavaScript 可读取，XSS 后可能泄露**；sessionStorage 生命周期更短但同样可被脚本读取；**HttpOnly Cookie 不能被脚本直接读取，但浏览器会自动携带，需要 SameSite、CSRF Token 或 Origin 校验**；内存保存短期 Access Token 可缩短持久暴露窗口，但刷新页面需要静默恢复。

SSO 常见流程是跳转统一身份中心，完成 OAuth/OIDC 回调后由应用交换或恢复本地会话，应校验 `state`、OIDC 的 `nonce` 和回调地址，避免回调劫持和 CSRF。登出不能只删除前端变量：应调用服务端登出/撤销接口、清理本地状态、取消未完成请求、清理受保护缓存，并跳转到安全的登录入口；多标签页可通过 BroadcastChannel 或 storage 事件同步登出，但仍需处理竞态。

## 【问题】
关于登录鉴权有哪些常见误区？

## 【回答】
- **误区：有 token 就代表登录成功**。——应通过会话或 `/me` 验证。
- **误区：前端隐藏按钮就完成权限控制**。——接口必须服务端授权。
- **误区：HttpOnly Cookie 可以解决 XSS 和 CSRF**。——它主要降低脚本读取风险，仍需整体防护。
- **误区：所有 401/403 都跳登录**。——403 通常是权限不足，盲目跳转会破坏体验。
- **误区：每个 401 都单独刷新 token**。——应使用单例刷新和等待队列。

反证条件：如果项目只使用服务端 Session 且无前端可读 Token，Access/Refresh Token 的复杂度可能没有收益；如果是跨系统 SSO，则本地自建账号体系可能反而重复建设。
