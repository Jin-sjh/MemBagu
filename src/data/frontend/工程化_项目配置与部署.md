# 项目配置与部署

## 【问题】
前端构建与部署的本质是什么？

## 【回答】
**前端构建通常生成入口 HTML、按 chunk 拆分的 JS/CSS、图片、字体等静态资源**，构建阶段可能执行压缩、Tree Shaking、代码分割、资源指纹和 source map。**上线的本质是可靠地交付构建产物，不是把源码直接放到服务器上**。流程为：

```
源代码 → npm run build → HTML/JS/CSS/图片/字体 → 上传服务器/CDN → 浏览器请求 → 渲染并与后端 API 通信
```

**静态资源服务器负责文件访问，API 请求通常通过反向代理转发到后端**。

---

## 【问题】
脚手架（如 npm create vite）能替代团队的工程规范吗？

## 【回答】
`npm create vite` 等脚手架负责生成目录、入口、`package.json`、基础脚本、开发服务器和构建配置，把初始化模板化。**它提供的是可运行起点，不等于完成团队的版本约束、依赖审查、环境变量治理、产物验收和部署策略**。使用后仍需确认 Node / 包管理器版本、锁文件、依赖来源、环境变量、路径别名、构建输出目录、静态资源 base、source map、CI 命令和回滚方式。

## 【问题】
多环境（开发 / 测试 / 预发布 / 生产）的环境变量怎么管理？密钥能放前端吗？

## 【回答】
环境变量可按 `.env.development`、`.env.staging`、`.env.production` 区分。**只有公开配置才能进入前端 bundle，密钥不能放在前端环境变量中**——进入 bundle 的变量用户都能看到。正确做法是**区分开发与生产配置、把密钥留在后端 / 网关**，这是前端安全的基本边界。

## 【问题】
什么是 CI/CD？为什么 CI 通常优先用 npm ci 而不是 npm install？

## 【回答】
**CI 关注代码能否稳定集成，CD 关注构建产物能否可靠交付；CI 失败时不应进入 CD**。常见步骤：用 `npm ci` 按锁文件可复现安装 → ESLint / Stylelint / TypeScript 检查 → 单测 → `npm run build` 生成 dist → 归档上传 → 发布与健康检查。

**`npm ci` 严格按 lockfile 安装、更快更可复现**；`npm install` 更适合本地更新依赖或缺少锁文件，在 CI 中可能因 lockfile 变化导致环境不一致。

## 【问题】
静态托管下 SPA 刷新 404 怎么解决？Nginx 反向代理负责什么？

## 【回答】
Nginx 用 `try_files` 在静态文件不存在时回退到 `index.html`，让 History 路由由前端接管：

```nginx
location / {
  try_files $uri $uri/ /index.html;
}
```

**它只解决找不到前端路由文件的问题，不修复 JS 资源路径或 API 配置错误**。反向代理可统一域名、转发 `/api/` 到后端、隐藏拓扑、结合 upstream 负载均衡；**它不是跨域唯一方案，浏览器是否放行仍取决于最终响应的 CORS**。

## 【问题】
面试时怎么答前端项目配置与部署？

## 【回答】
我会讲：环境隔离、公开配置与密钥分离、构建可重复（lockfile / 固定 Node）、资源路径与 base、缓存策略与回滚、SPA fallback、HTTPS、监控。**Vite/Webpack 配置不能只在本地可用，要在 CI 和真实 CDN/Nginx 环境验证**；发布脚本要幂等、失败退出、可回滚，不依赖人工 SSH。

## 【考察点】
构建产物认知、环境变量与密钥边界、CI/CD 与 npm ci、SPA fallback 与反向代理、缓存与回滚。
