# TCP 队头阻塞

## 【问题】
为什么会出现 TCP 的队头阻塞

## 【回答】
队头阻塞是指当一个 TCP 连接中的一个数据包丢失或延迟，后续的数据包必须等到这个数据包被正确接收后才能继续处理。即使其他数据包已经到达，仍需要等待队头的数据包。

### 原因：
- **可靠性**：TCP 为了确保数据的可靠传输，会等待丢失的数据包被重新传输并按顺序接收，导致后续数据的延迟。

### 解决方案：
- **HTTP/2** 通过多路复用和流优先级来解决 TCP 队头阻塞，但仍然受到 TCP 固有问题的影响。
- **HTTP/3** 通过 QUIC 协议利用 UDP 减少了队头阻塞的影响。

## 真实业务 / 面试场景（案例补充）

### 场景 1：HTTP/1.1 下某个慢请求卡住后面所有请求
**背景**：浏览器对同一域名最多开 6 个 TCP 连接，6 个请求里有一个在传大图很慢，排在同一连接的后续请求就得排队等它。
**为什么**：单个 TCP 连接内请求是串行的，且 TCP 本身有队头阻塞——丢了一个包，后面的包即便到了也得等重传。
**解决**：域名分片（多域名）、开 HTTP/2。

### 场景 2：HTTP/2 多路复用为何还是没彻底解决？
**背景**：HTTP/2 把多个请求放在一个 TCP 连接的不同"流"里并行，应用层不阻塞了，但如果这个 TCP 连接里**任意一个流**丢包，整条 TCP 连接都要等重传，所有流一起卡——这是 TCP 层的队头阻塞，HTTP/2 绕不过。
**解决**：HTTP/3 改用基于 UDP 的 QUIC，每个流独立，丢包只影响自己那一条流。

### 场景 3：直播 / 视频通话对队头阻塞最敏感
**为什么**：实时音视频每帧独立、可丢弃，但 TCP 坚持"按序到达"，一个包丢了后面的画面全卡，所以这类场景更倾向 UDP/QUIC（HTTP/3）而非 TCP。
