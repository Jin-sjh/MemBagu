# HTTP 与 RPC 对比

## 为什么有 HTTP 协议了？还要用 RPC？

## 【问题】
为什么有 HTTP 协议了？还要用 RPC？

## 【回答】

- RPC 本质上不算是协议，而是一种调用方式，而像 gRPC 和 Thrift 这样的具体实现，才是协议，它们是实现了 RPC 调用的协议。目的是希望程序员能像调用本地方法那样去调用远端的服务方法。同时 RPC 有很多种实现方式，不一定非得基于 TCP 协议。

- 从发展历史来说，HTTP 主要用于 B/S 架构，而 RPC 更多用于 C/S 架构。但现在其实已经没分那么清了，B/S 和 C/S 在慢慢融合。很多软件同时支持多端，所以对外一般用 HTTP 协议，而内部集群的微服务之间则采用 RPC 协议进行通讯。

- RPC 其实比 HTTP 出现的要早，且比目前主流的 HTTP/1.1 性能要更好，所以大部分公司内部都还在使用 RPC。

- HTTP/2.0 在 HTTP/1.1 的基础上做了优化，性能可能比很多 RPC 协议都要好，但由于是这几年才出来的，所以也不太可能取代掉 RPC。

---

## 真实业务 / 面试场景（案例补充）

### 场景 1：公司内部微服务用 gRPC，对外 BFF 用 HTTP
**背景**：订单、库存、用户等内部服务用 gRPC（Protobuf + HTTP/2），性能高、有强类型 IDL；面向前端 / 第三方的网关层用 REST/HTTP + JSON，方便浏览器和多方对接。
**为什么**：RPC 让程序员像调本地函数一样调远端方法，省去手动拼 HTTP 报文；对外则要通用、可调试（curl 就能测），所以走 HTTP。

### 场景 2：浏览器为什么只能调 HTTP，不能直连 RPC？
**为什么**：浏览器原生只支持 HTTP/HTTPS（及 WebSocket），没有 gRPC 的传输能力；所以前端到服务端一定是 HTTP，服务端之间（BFF→微服务）才用 RPC，由网关 / BFF 做协议转换。

### 场景 3：面试——"既然 HTTP/2 性能已经很好，为什么内部还用 RPC？"
**回答要点**：RPC 出现更早、生态成熟（服务发现、熔断、限流一套治理）；HTTP/2 虽快但近年才普及，存量系统迁移成本大；且 RPC 的 IDL 强约束、代码生成体验是 HTTP/JSON 难以替代的。
