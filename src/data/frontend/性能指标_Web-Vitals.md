# Web-Vitals

## 【问题】
什么是 Core Web Vitals？LCP、INP、CLS 分别衡量什么？

## 【回答】
Core Web Vitals（核心网页指标）是 Google 提出的一组直接反映真实用户体验的指标，分别从**加载、交互响应、视觉稳定性**三个维度衡量页面表现，不能用单一指标代表全部性能：
- **LCP（Largest Contentful Paint，最大内容渲染）**：衡量加载速度，观察视口内最大文本或图片内容完成呈现的时间。
- **INP（Interaction to Next Paint，交互到下次绘制）**：衡量响应速度，观察页面交互从输入到下一次绘制反馈的响应延迟，关注整个生命周期中的交互，而不是只看首次点击。
- **CLS（Cumulative Layout Shift，累积布局偏移）**：衡量视觉稳定性，观察非预期布局位移的累积。
三者分别回答"主要内容何时出现、交互反馈是否及时、页面会不会跳动"三个不同问题。

---

## 【问题】
LCP 慢通常是由哪些原因导致的？应该如何优化？

## 【回答】
LCP 差的本质是首屏主要内容出现得太晚，常见原因包括：**TTFB 高（服务端响应慢）**、**关键资源发现晚**、**资源体积过大**、**渲染被 JS 阻塞**。优化思路对应展开：
- **早发现**：使用 preconnect 提前建立关键源连接，preload 当前关键资源，让浏览器尽早发现首屏所需资源。
- **快传输**：压缩图片、使用 WebP/AVIF 等现代格式、启用 CDN 与文本压缩。
- **快渲染**：优化关键渲染路径，CSS 提前、非关键 JS 异步（defer/async），避免主线程被长任务阻塞。
优化后要用 Performance/Lighthouse 与真实用户 75 分位数据验证，而不是只追求单次实验分数。

## 【问题】
INP 是什么？为什么它比"首屏点击延迟"更严格？

## 【回答】
INP（Interaction to Next Paint）衡量的是**页面交互从用户输入到下一次绘制反馈的响应延迟**。它和早期 FID 不同，**关注整个页面生命周期内的所有交互**，而不是只看首次点击，因此更能反映用户在整个使用过程中的真实卡顿感受。会拖慢 INP 的因素主要是：**Long Task（长任务）占用主线程**、**事件处理函数本身工作过重**、以及**布局与绘制耗时**。优化手段包括：拆分长任务把控制权交还浏览器、减少事件处理中的重计算、延迟非关键 JS 的执行、对高频交互严格使用防抖节流。

## 【问题】
CLS 高通常由什么引起？如何避免页面跳动？

## 【回答】
CLS 衡量非预期布局位移的累积，数值越高说明页面越"跳"。常见原因包括：**图片/广告未设置尺寸**、**动态插入内容（如异步加载的 banner）**、**字体替换（FOIT/FOUT）**、以及**样式变化导致重排**。优化手段对应为：
- **为媒体预留尺寸**：给图片、视频显式设置 width/height 或使用 aspect-ratio，提前占位。
- **避免无锚点插入**：不要在用户已可视区域的上方动态插入 DOM（如突然出现的弹窗）。
- **字体稳定**：使用 font-display: swap 并合理控制字体加载，避免文本重排。
- **用骨架屏**替代传统 Loading 闪屏，减少布局突变。

## 【问题】
实验室数据（Lighthouse）和真实用户数据（RUM）有什么区别？如何验证优化？

## 【回答】
两者用途不同，不能互相替代：
- **Lighthouse 等实验室数据**是在受控环境下跑出的指标，适合在开发阶段发现瓶颈、做对照实验，但**不反映真实设备和网络差异**。
- **RUM（Real User Monitoring，真实用户监控）**采集真实用户在不同设备、网络下的体验数据，**反映真实交互和分布**。
验证优化是否有效，应先用 Lighthouse 定位方向，再用 RUM 的 **LCP/FCP/INP 75 分位**等真实数据确认改善，避免把"单次实验分数变好"误认为稳定收益。
