# SDK组件库与微前端

## 【问题】
如何设计一个健壮的前端 SDK？

## 【回答】
SDK **不只是 API 的薄封装**，还要提供一套完整的工程能力：
- **稳定抽象与协议适配**：用 Adapter 把后端协议变化隔离在适配层，公共 API 明确向后兼容策略。
- **错误处理**：统一的错误码、超时、重试、取消机制。
- **可观测性**：内置埋点与可观测字段，方便调用方排查。
- **类型与版本兼容**：提供完整类型定义，并管理好版本演进。
核心结论：SDK 的边界要稳定，变更成本要可控，兼容、错误和观测能力缺一不可。

---

## 【问题】
组件库设计要关注哪些方面？

## 【回答】
组件库应先区分**基础组件和业务组件**，再围绕以下方面设计：
- **可组合 API**：设计清晰的 props/插槽/事件语义。
- **受控/非受控语义**：明确组件谁来掌管状态。
- **无障碍（a11y）与主题边界**：用 Design Token 管理设计变量，支持主题切换。
- **工程能力**：按需加载、Tree Shaking、文档、视觉回归和单元/E2E 测试。
特别注意：**Vue2/Vue3 双版本兼容**会增加构建、类型、生命周期和发布成本，不应只靠条件分支堆在组件内部，而要做构建/类型层面的隔离。

## 【问题】
什么是微前端？它解决什么问题，代价是什么？iframe 与 JS 沙箱怎么选？

## 【回答】
微前端解决**多团队、多应用独立交付和技术迁移**的问题，代价是引入运行时**通信、路由、样式/JS 隔离、公共依赖、监控、性能和一致性**的复杂度。两种隔离方案对比：
- **iframe**：隔离最强（JS、样式、路由天然隔离），但通信和体验成本高。
- **JS 沙箱 / CSS 前缀 / Shadow DOM**：更灵活，但隔离不绝对，需要自行处理副作用。
关键判断：**只有组织和发布边界真实存在时，微前端才值得引入**；否则模块化单应用通常更简单，项目越大不代表越需要微前端。

---

## 【问题】
面试时怎么答 SDK、组件库和微前端的选型？

## 【回答】
我会分别讲重点：SDK 重在**稳定边界、兼容、错误处理和可观测**；组件库重在 **API 设计、主题（Design Token）、按需加载、文档与测试**；微前端重在**独立交付收益与隔离、通信、依赖、性能成本的平衡**。最后落到选型依据：由**团队边界、部署自治和系统复杂度**驱动，而不是"项目大就要上微前端"。能用模块化单应用解决的，就不引入微前端的额外复杂度。
