# Code-Splitting

## 【问题】
什么是 Code Splitting？为什么需要它？

## 【回答】
Code Splitting 是**把一个大产物拆成可按需加载的多个 chunk** 的技术，目的是**减少初始下载体积**，让首屏只加载关键代码，其余代码在用户进入路由或触发功能时再加载。
没有拆分时，所有逻辑被打成一个大包，首屏需下载解析全部代码，浪费带宽并拖慢 LCP。拆分的代价是**异步加载失败、请求瀑布和 chunk 设计复杂度**上升，因此需要权衡而非无脑拆分。

---

## 【问题】
Code Splitting 的核心机制与拆包策略有哪些？

## 【回答】
动态 `import()`、路由边界和 bundler 配置会形成**异步边界**，触发按需加载：
```
入口 → 关键代码立即加载
  ↓ 用户进入路由/触发功能
按需请求异步 chunk → 缓存并执行
```
设计时要关注：**首屏关键路径、用户访问概率、缓存稳定性、共享 vendor、chunk 大小和并发请求**。常见方式包括路由级拆分、把稳定第三方库抽成独立 vendor chunk（利于缓存复用）。HTTP/2/3 降低连接成本，但**不消除下载、解析和主线程成本**，仍需合理控制 chunk。

---

## 【问题】
chunk 是不是越小越好？过度拆分有什么问题？

## 【回答】
**chunk 越小不一定越好**。过度拆分会带来：① **请求数量增加**（即使 HTTP/2 多路复用，仍有调度与握手成本）；② **请求瀑布**（chunk 间存在依赖顺序，串行加载）；③ **运行时开销**（加载、解析、调度模块的成本上升）。
但 chunk 太大又会拖慢首屏。因此要在**首屏体积、请求数量、缓存命中、解析执行和运行时加载**之间取得平衡，而非单纯追求“数量多”或“体积碎”。

---

## 【问题】
面试时怎么答 Code Splitting？

## 【回答】
Code Splitting 通过**动态 import 等异步边界延迟非关键代码**，改善初始加载和缓存命中；典型手段是路由级拆分和 vendor 抽取。它的收益是**减小首屏下载、提升缓存复用**，代价是**异步加载失败风险、请求瀑布和 chunk 设计复杂度**。
应结合 **Bundle Analyzer、Network 瀑布、LCP/INP 和缓存命中率**来决定 vendor 与路由拆分粒度，而不是凭感觉拆。记住：**chunk 不是越小越好**，过度拆分反而增加请求与运行时开销。

---

## 【问题】
如何验证 Code Splitting 的拆包效果？

## 【回答】
验证不能只看“拆没拆”，要观测真实指标：
- **Bundle Analyzer**：查看模块来源和 Chunk 组成，确认 vendor 与业务代码是否分离；
- **浏览器 Network 瀑布**：观察首屏请求数、异步 chunk 的加载时机与是否存在串行瀑布；
- **LCP/INP 与缓存命中率**：衡量首屏与交互表现，以及 chunk 是否能被稳定缓存复用。
结合这些指标调整拆分粒度，避免“拆了但没变快”。
