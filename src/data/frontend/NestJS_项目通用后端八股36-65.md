# 项目通用后端八股36-65

## 【问题】
Node.js 的 Event Loop 与 CPU 密集任务有什么坑？

## 【回答】
**来源题号：Q36–38**

**I/O 等待不占住主线程，但 CPU 密集的同步代码仍会阻塞 Event Loop**。流程是：同步代码 → 发起 I/O → OS/线程池处理 → 回调进入队列 → Event Loop 执行。

**`await` 只暂停当前 async 函数的后续执行，不会自动把同步 CPU 计算变成异步**。CPU 密集任务应考虑 Worker Threads、子进程、任务队列或独立计算服务，否则会拖慢整个事件循环。

## 【问题】
HTTP 方法与接口幂等如何设计？

## 【回答】
**来源题号：Q39–41**

**HTTP 方法应有语义（GET 安全/幂等，POST 非幂等，PUT/DELETE 幂等）；重试敏感接口需 Idempotency Key、唯一索引、事务和状态机**。

幂等下单流程：Idempotency-Key → 查询已处理结果，有则返回原结果，无则事务执行业务 + 唯一约束保存结果。只依赖 Redis `if exists` 不够可靠，最终约束应由数据库唯一索引、事务和业务状态机兜底，避免重复下单。

## 【问题】
数据库索引的原理与代价是什么？

## 【回答】
**来源题号：Q42–44**

**索引减少查询扫描范围，但会增加磁盘、内存和写入维护成本**。联合索引 `(a,b,c)` 通常支持 `a`、`a,b`、`a,b,c`（最左前缀原则）。

是否生效必须结合查询条件、选择性和 `EXPLAIN` 执行计划判断，不能仅凭「建了索引就快」。索引是读写权衡，写多读少的场景要谨慎加索引。

## 【问题】
什么是 N+1 查询问题？如何解决？

## 【回答】
**来源题号：Q45**

**N+1 指循环中对每条记录再发一次查询，造成大量重复 DB 访问**。例如遍历用户列表时逐个查其订单。

解决方式：用 **JOIN、批量 IN 查询、ORM 的 `include`/`eager` 关联加载，或 DataLoader 批量聚合**。核心是把 N 次独立查询收敛为少量批量查询。

## 【问题】
Offset 分页与 Cursor 分页怎么选？

## 【回答】
**来源题号：Q46–47**

**深 Offset 分页成本和稳定性较差**（越往后 `LIMIT offset, size` 扫描越多，且数据插入删除会导致重复/漏读）；**Cursor（游标）分页更适合大数据量连续翻页**，基于上一页最后一条的排序键向后取，稳定且高效。

小数据量、可随机跳页的场景 Offset 更方便；高并发信息流类接口优先 Cursor。

## 【问题】
数据库连接池应该如何配置？

## 【回答】
**来源题号：Q48–49**

**连接池用于复用连接，避免频繁建立/断开**。池大小需结合实例数、数据库上限、并发和 SQL 延迟计算，而非越大越好。

总连接数 ≈ 应用实例数 × 单实例池大小，必须低于数据库 `max_connections`，否则会耗尽数据库连接导致雪崩。改变实例数、池大小和并发观察吞吐与 P95 来调优。

## 【问题】
数据库隔离级别如何取舍？

## 【回答】
**来源题号：Q50–53**

**隔离级别在并发与一致性之间取舍**，需区分三类异常：**脏读**（读到未提交）、**不可重复读**（同事务内两次读不一致）、**幻读**（同事务内范围查询结果集变化）。

级别从低到高对应不同异常容忍度，提升隔离级别会减少并发异常但增加锁开销与阻塞。具体由数据库能力决定，NestJS 只负责调用和组织事务。

## 【问题】
乐观锁与悲观锁如何用于库存扣减？

## 【回答】
**来源题号：Q54–55**

**乐观锁检测冲突（版本号/条件），悲观锁先占用资源**；乐观锁适合冲突较少场景，悲观锁适合冲突高且需要强协调场景。

**库存检查与扣减应是原子操作**，尽量写成原子条件更新：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = ? AND stock > 0;
```

再检查 `affected rows`，避免「超卖」。

## 【问题】
Redis 作为缓存的核心难点是什么？

## 【回答】
**来源题号：Q56–59**

**Redis 快不只因内存，更因单线程模型与数据结构高效**；但 Cache Aside 仍要处理失效、删除失败和一致性。缓存三大问题：穿透（请求不存在数据）、击穿（单热点 Key 过期）、雪崩（大量 Key 同时失效或 Redis 故障）。

更新策略：更新 DB → 删除 Cache → 失败时重试/补偿。Redis 不是数据库的自动替代品，要明确一致性和失效策略。

## 【问题】
分布式锁如何实现才安全？

## 【回答】
**来源题号：Q60–61**

**分布式锁需唯一 value、过期时间、原子校验释放，并考虑超时与网络故障**。释放不能直接 `DEL`——锁可能已过期并被别人获得，必须校验唯一 value，并用 Lua 等方式原子化「校验 + 删除」。

还要处理客户端崩溃、网络分区、锁提前过期等问题，必要时用 Redlock 或更成熟的协调服务。

## 【问题】
接口限流有哪些算法？

## 【回答】
**来源题号：Q62**

**Fixed Window（固定窗口）实现简单，但有边界突发问题**（窗口临界点可能放行两倍流量）；**Sliding Window（滑动窗口）/ Token Bucket（令牌桶）更平滑**，能更好控制平均速率与突发。

选型取决于是否允许短时突发、实现复杂度和精度要求。限流通常结合 Redis 做分布式计数。

## 【问题】
运行时治理：优雅停机与健康检查怎么做？

## 【回答】
**来源题号：Q63–64**

**优雅停机要排空请求**：收到 `SIGTERM` → 停止接收新请求 → 等待进行中请求完成 → 关闭 DB/Redis/MQ → 退出，避免强制杀进程导致请求丢失。

**Liveness 与 Readiness 不能混淆**：Liveness 判断进程是否活着（挂了就重启），Readiness 判断实例是否适合接流量（未就绪则不纳入负载）。

## 【问题】
线上接口变慢如何分层排查？

## 【回答】
**来源题号：Q65**

**用 P95/P99、requestId、Tracing、SQL/Redis 延迟分层定位，不先甩锅框架**。先看客户端、网关和 NestJS 层的 P50/P95/P99，再用 requestId、结构化日志和 Trace 拆分 Service、Redis、数据库和外部 API 耗时。

数据库侧用执行计划检查索引、N+1 和分页；写操作用事务、唯一约束和原子更新；缓存用 Cache Aside 并设计失效补偿；多实例再考虑分布式锁、限流。比较 P50/P95/P99 与错误率，而不是只看平均值。
