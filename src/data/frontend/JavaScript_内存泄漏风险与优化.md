# 内存泄漏风险与优化

## 【问题】
垃圾回收 (GC) 的核心机制是什么？

## 【回答】
JavaScript 采用自动垃圾回收机制，主流浏览器使用标记 - 清除算法：

1. **标记阶段**：从根对象（window、全局执行上下文）出发，遍历所有可达对象，标记为「存活」

2. **清除阶段**：回收所有未被标记的「不可达」对象，释放内存

3. **内存泄漏本质**：对象不再被使用，但因强引用存在，被 GC 误判为「可达」，无法被回收

## 【问题】
哪些操作会造成强引用？

## 【回答】
强引用是指默认的引用关系，只要强引用存在，垃圾回收器（GC）永远不会回收被引用的对象，是内存泄漏的核心诱因。常见场景：

- **全局变量 / 挂载到 window**：`window.obj = {}`，全局对象生命周期与页面一致，无法被回收

- **未销毁的定时器 / 延时器**：`setInterval`、`setTimeout` 回调中持有 DOM / 组件引用，定时器不清除则引用不释放

- **事件监听未解绑**：`addEventListener` 绑定后未用 `removeEventListener` 移除，DOM 被销毁但事件回调仍持有引用

- **闭包持有外部变量**：闭包会保留对外部作用域变量的引用，导致变量无法被回收

- **缓存 / 长列表未清理**：无限滚动列表中，所有数据都存在内存中不做清理

- **第三方库实例未销毁**：如 ECharts、地图实例未调用 `dispose()`，持续持有 DOM 引用

- **Vue/React 组件内不当引用**：Vue 中 `this` 的循环引用、React 中未清理的 `useEffect` 副作用

## 【问题】
内存泄漏的常见泄漏场景有哪些？

## 【回答】
1. **意外的全局变量**：
   ```javascript
   function foo() { bar = 1; }
   ```
   未声明直接赋值会创建全局变量，导致无法被垃圾回收

2. **闭包过度使用**：长期缓存大对象，闭包让外层作用域的变量无法被垃圾回收

3. **DOM 事件未移除**：组件卸载后事件监听仍然存在，导致 DOM 元素无法被回收

## 【问题】
这段代码是否存在内存风险？为什么？

## 【回答】
这段代码本身不存在内存泄漏风险。

1. 代码是典型的闭包实现，内部函数持有外部函数 `createCounter` 的词法环境（变量 `count`）。

2. 闭包本身不会造成内存泄漏，内存泄漏的核心是「不再需要的内存无法被 GC 回收」。

3. 当闭包函数不再被任何变量引用时，其持有的词法环境会被正常回收；只有当闭包被意外长期持有（如全局挂载、未清理的定时器 / 事件监听）时，才会引发内存泄漏。

4. 闭包是前端工程的必需品，用于状态封装、模块化等场景，不能简单认为"闭包会造成内存泄漏"。

## 【问题】
如何避免长列表内存堆积？

## 【回答】
核心是减少 DOM 节点和及时释放引用：

1. **虚拟列表**：只渲染可视区域元素，复用 DOM

2. **分页 / 懒加载**：避免一次性加载全部数据

3. **组件卸载时销毁数据和事件**：及时清理无用引用

4. **用弱引用存储缓存**：使用 WeakMap/WeakSet，不影响 GC

5. **避免全局缓存**：在组件作用域内管理数据

## 【问题】
内存泄漏的优化方案有哪些？

## 【回答】
1. **及时解除引用**：
   ```javascript
   timer = null;
   ```
   将不再使用的变量引用置为 null，帮助垃圾回收器识别

2. **使用 WeakMap 存储临时数据**：WeakMap 的键是弱引用，不会阻止垃圾回收

3. **组件卸载时清理事件监听**：在组件销毁前主动移除所有事件监听器，避免内存泄漏

## 【问题】
V8 的垃圾回收除了标记-清除还用了什么策略？什么是分代回收？

## 【回答】
现代引擎通常**结合标记-清除与分代、增量、并发、压缩等策略**，不能把「V8 使用某一种单一算法」当作完整描述。

典型标记-清除流程：从 GC Root 标记可达对象 → 清除未标记对象 → 必要时整理空间。更关键的是**分代回收**：

- **分代假设**：大量对象很快死亡，因此**新生代收集更频繁、更轻量**；
- **晋升**：长期存活对象晋升到**老生代**，老生代收集成本通常更高；
- 引擎会随版本和对象类型演进实现，具体策略以运行时版本为准。

**关键结论：**

- 短命对象通常在新生代快速回收，长期对象进入老生代；
- 不要以为「GC = 标记清除」就描述完整，分代/增量/并发/压缩都是降低回收成本的重要手段。

## 【问题】
GC 一定会导致页面卡顿吗？什么情况下会卡？

## 【回答】
**GC 会有成本，但是否造成可见卡顿要看对象规模、算法阶段和主线程负载**，不能一概而论。

- GC 需要扫描、标记、清理或整理对象图；现代引擎会尽量**增量化、并发化**，但某些阶段仍可能消耗主线程时间；
- **频繁创建大量短命对象**会增加分配和回收压力；
- **老生代持续增长**可能触发更重的收集。

**关键结论：**

- GC 不是所有卡顿的原因，必须和 **JS Long Task、Layout/Paint** 区分；
- 减少分配压力的方式：限制无界缓存、缩短对象生命周期、避免重复大对象分配；
- 用 Performance 面板观察 GC 活动与长任务，才能定位瓶颈。

## 【问题】
如何用 Chrome DevTools 排查内存泄漏？Heap Snapshot 和 Retaining Path 怎么用？

## 【回答】
排查不能只看代码，要用工具找到实际引用链：

- **Memory 面板**可用 Heap Snapshot、Allocation instrumentation 和 Detached elements 线索；
- **Performance 面板**可观察 GC 活动与长任务。

**标准流程：**

1. 怀疑内存增长 → 重复操作并拍多张 Heap Snapshot；
2. 比较快照中的**对象数量与 retained size**；
3. 查看 **Retaining Path**（保留路径），定位 `Root → 引用者 → 泄漏对象`；
4. 修复生命周期（清理副作用、断开监听器、限制缓存）并同条件复测。

**关键结论：**

- 内存泄漏的核心证据是**重复操作后 retained object 持续增长**，并存在从 Root 到对象的非预期引用路径；
- 实验必须在相同操作次数、数据规模和浏览器版本下比较，强制 GC 后结果需谨慎解读。

## 【问题】
关于内存泄漏有哪些常见误区？

## 【回答】
高频误区需准确反驳：

- **误区：内存使用下降就证明没有泄漏。** 正解：引擎可能延迟回收或保留堆空间，应看**对象数量和 retained size**，而非内存曲线；
- **误区：看到闭包就判定泄漏。** 正解：需找到真实 Root 引用链，只有不必要的长期可达引用才是问题；
- **误区：手动调用 GC 就能修复问题。** 正解：它只能改变观察时机，不能解除业务引用；
- **反证条件**：若增长来自有界缓存、引擎保留堆空间或正常生命周期对象，且快照中对象数量最终稳定，则不能直接称为泄漏。

## 【问题】
把对象设为 null 后它一定会立即被回收吗？WeakMap 为什么能帮忙避免泄漏？

## 【回答】
**不一定。** 把变量引用置为 `null` 只是断开一条路径，对象成为回收候选不等于立刻回收，且可能还有其他引用路径。

**关键结论：**

- `cache = null` 后若无其他路径，`data` 才可能成为回收候选；「可能」很重要，回收时机由引擎决定；
- **闭包不一定泄漏**：只有不必要的长期可达引用才是问题，必要的闭包（状态封装、模块化）是正常需求；
- **WeakMap 为什么有帮助**：它的键是**弱引用语义**，不会因该映射单独阻止键对象被回收，适合给对象附加元数据而不影响回收；
- 但 WeakMap**不能遍历、不能当通用缓存替代品**，也不是所有泄漏的解决方案——仍要清理副作用、断开监听器、限制缓存规模。
