# 从0到1项目启动

## 【问题】
从 0 到 1 启动一个前端项目，第一步应该做什么？

## 【回答】
第一步不是选框架，而是**先明确要做什么、再决定用什么**。要先回答：这是中后台、C 端、活动页、工具还是平台？核心用户和最高频操作是什么？项目是一次性交付还是需要维护多年？团队人数、并行协作、数据规模、权限、兼容性和上线时间有哪些约束？这些约束决定了状态复杂度、组件复用、测试投入、性能预算和工程治理强度。**不能因为"会 Vue"就默认 Vue，也不能因为"高级"就引入微前端或 Monorepo**——选型要由业务约束驱动。

---

## 【问题】
技术选型应该遵循什么方法？有哪些常见决策项？

## 【回答】
选型应按方法推进：**业务需求 → 技术约束 → 候选方案 → 指标比较 → 选择并记录代价 → 小实验验证**。常见决策项包括：Vue/React（团队能力、生态、SSR/SEO、交互复杂度）、JavaScript/TypeScript（类型收益、迁移成本）、局部状态/Pinia/Redux（共享范围、异步数据、持久化）、组件库选型（覆盖、主题、可访问性）、Vite/Webpack（dev 体验、产物、兼容性）、单仓库/Monorepo。关键结论：**选型记录要写清需求、候选、取舍、风险、验证结果和替换成本**，而不是只写"性能好"或"更流行"。

---

## 【问题】
Monorepo 和微前端有什么区别？什么时候该用？

## 【回答】
两者**不是同一层次的替代方案**：Monorepo 解决**多包代码治理**（共享组件/工具/类型、统一版本、测试和发布）；微前端解决**多个独立应用的运行时组合与团队自治**。适用边界：
- **Monorepo**：多个应用需要共享代码、统一版本与发布时值得用；单个小应用没有多包复用需求时，工具链和发布复杂度可能大于收益。
- **微前端**：多个团队**必须独立发布**时收益才明显；否则模块化单应用通常更简单。
默认选择**满足当前约束的最小复杂度方案**。

## 【问题】
工程结构和模块边界应该怎么设计？依赖方向有什么约束？

## 【回答】
目录不是越细越好，关键是明确**谁拥有状态、谁负责请求、谁能依赖谁、哪些变化需要隔离**。典型分层如 `api / components / pages / stores / utils`，依赖方向应为 **`pages → features/components → shared/utils`**，**底层模块不应反向依赖页面**。要点：基础组件不依赖具体业务；业务组件围绕领域概念复用；页面负责数据获取和业务编排；API 层负责协议适配，避免网络细节散落在模板中。

## 【问题】
项目早期如何避免过度技术债？

## 【回答】
早期不需要极限优化，但要避免明显难以挽回的决策：**路由懒加载边界、大列表分页/虚拟列表、高频请求防抖/缓存/取消/竞态保护、重复组件和请求封装、第三方 SDK 首屏影响、全局状态过度更新**。技术债常来自临时方案、模糊边界、重复请求、缺少错误态、环境写死和没有质量门禁。每项重要决策应记录**方案、原因、风险、负责人和复查时间**，并用 Network、Performance、Profiler、Bundle Analyzer 和 Web Vitals 验证，不凭体感判断。

---

## 【问题】
面试时怎么答"从 0 到 1 做项目启动与架构决策"？

## 【回答】
我会按流程讲：先明确**业务场景、用户、生命周期和团队约束**，再选择框架、语言、状态管理和构建工具；随后设计**目录与依赖边界**，建立类型、Lint、提交和 CI 规范；接着**先按业务闭环**完成接口、状态、异常和部署验证，再逐步扩展；每个重要选型都记录**收益、代价和验证结果**。最后补充架构反证：默认选满足约束的最小复杂度方案，Monorepo/微前端只在真实多包复用或多团队独立发布时才上，并用指标而非体感验证决策。
