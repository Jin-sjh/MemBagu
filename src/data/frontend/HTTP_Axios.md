# Axios 详解

## 1. Axios 是什么？解决了什么问题？

## 【问题】
Axios 是什么？解决了什么问题？

## 【回答】
Axios 是一个基于 Promise 的 HTTP 客户端，支持浏览器和 Node.js，对原生 XHR / http 模块进行了封装，提供了统一的请求 API、拦截器机制、自动转换数据、请求取消、并发控制等能力，适合在工程化前端项目中使用。

### 【隐含加分点】
- 浏览器端：基于 XMLHttpRequest
- Node 端：基于 http / https 模块
- 核心目标：统一请求层、可扩展、可维护

## 2. axios 请求失败处理方法

## 【问题】
axios 请求失败处理方法

## 【回答】
我在项目中会封装 axios 统一处理请求异常：

首先创建实例配置超时和基础路径，通过响应拦截器捕获网络错误、超时、4xx/5xx 及业务错误；

然后分类处理：网络异常提示网络问题，401 跳登录，403 提示无权限，服务端错误统一提示；

同时会做自动重试、取消重复请求、错误日志上报，最后返回标准化结果，保证代码健壮和用户体验。

## 真实业务 / 面试场景（案例补充）

### 场景 1：每个请求都手动加 token、手动 try/catch
**为什么**：散落各处重复且易漏。
**解决**：用请求拦截器统一在 `headers.Authorization` 注入 token；响应拦截器统一处理 401 跳登录、统一 toast 错误，业务代码只关心数据。

### 场景 2：用户快速连点，发了重复请求
**为什么**：上一个请求未返回又发一次，造成重复提交甚至重复扣款。
**解决**：用 `AbortController` 做请求取消（新请求进来取消上一个），或用"请求中"集合去重。

### 场景 3：弱网下请求一直转、无反馈
**解决**：配置 `timeout`（如 10s），超时后拦截器统一提示"网络开小差"，并可在 401 刷新 token 后自动重发一次。

## 【问题】
为什么需要在项目里建立统一的请求层？

## 【回答】
直接在组件里写请求很快，但项目变大后会出现：**URL、超时和请求头散落在页面**；**每个组件重复处理 loading、错误和响应格式**；**Token 刷新、权限失效、取消和重试难以统一**；**API 难以 Mock，组件测试与网络细节耦合**；**接口字段或后端协议变化需要修改大量页面**。常见分层是：组件 → 业务 API → 统一 request → Axios adapter，从而统一错误、权限和超时，并方便 Mock、测试和后续协议变化。

## 【问题】
Axios 的完整请求流程是怎样的，拦截器执行顺序如何？

## 【回答】
调用 `axios(config)` 后**先合并默认配置、实例配置和本次请求配置**，再组装请求拦截器，进入 `dispatchRequest` 转换配置并选择 adapter 发送，响应回来后校验状态、转换数据、组装响应拦截器，再返回 Promise。关键对象：`defaults` 默认配置、`interceptors` 拦截器集合、`dispatchRequest` 准备并发起请求、`adapter` 把统一配置转为平台传输实现。**请求拦截器通常后注册的先执行，响应拦截器通常先注册的先执行**。

---

## 【问题】
拦截器里适合放什么，不适合放什么？

## 【回答】
适合放入请求拦截器的逻辑：**Token 注入、请求 ID、统一请求头、参数标准化和耗时起点**；适合放入响应拦截器的逻辑：**统一数据解包、错误上报、登录失效处理和耗时统计**。**不应把所有业务分支塞进拦截器**，页面专属提示、表单字段错误和业务空态仍应在业务 API 或页面层处理，否则全局拦截器会变成不可预测的隐式控制流。多个拦截器要考虑注册顺序、清理和重复注册，热更新场景重复追加会导致同一请求被重复处理。

## 【问题】
Axios 的错误模型应该如何分类处理？

## 【回答】
Axios 错误可分为四类：**response（服务端已返回，含 HTTP 状态错误和业务错误码）**、**request（请求已发出但没收到响应）**、**setup（请求配置、序列化或客户端异常）**、**cancel（主动取消）**。Axios 默认通常会把不满足 `validateStatus` 的响应转为 rejected，但是否算错误可以自定义；**4xx/5xx、业务错误码、网络失败和取消的用户体验不应混成一个"请求失败"**，错误上报也要排除主动取消，避免污染告警。

## 【问题】
如何处理请求取消和请求竞态？

## 【回答】
现代 Axios 支持使用 **`AbortController` 的 `signal` 取消请求**，旧的 `CancelToken` 已不适合作为新代码首选；取消请求主要解决资源和结果处理问题，**不等于服务端一定停止已经开始的计算**。搜索框等场景还要防止旧响应覆盖新响应：用递增序号校验，处理返回时若 id 不等于最新则丢弃；也可在新请求开始时取消旧请求，序号校验和 AbortController 可组合使用，前者保护结果顺序，后者减少无效工作。

## 【问题】
Axios 的并发和重试怎么设计？

## 【回答】
**`Promise.all` 可以聚合多个 Axios Promise**；历史版本中的 `axios.all/axios.spread` 本质上也是类似的组合辅助，**不等于并发限制**，Axios 本身通常不负责限制同时运行的请求数，需要在业务层使用队列、信号量或 `p-limit` 等调度器。重试要区分**网络暂时失败、幂等请求、认证失败和业务失败**，设计最大次数、退避、超时、幂等性和取消，**不能对所有 POST 或所有 5xx 无条件重试**。

## 【问题】
Axios 和 Fetch 怎么选？

## 【回答】
- **定位**：Axios 是工程化 HTTP 客户端库，Fetch 是 Web 平台原生 API
- **非 2xx**：Axios 通常按配置进入 rejected，Fetch 默认需手动检查 `response.ok`
- **拦截器**：Axios 内置，Fetch 需自行封装
- **超时**：Axios 提供配置能力，Fetch 通常结合 AbortController
- **依赖**：Axios 需要引入库并管理版本，Fetch 无额外库依赖

**Axios 更偏统一请求层，Fetch 更接近平台能力**。选择应看拦截器、兼容矩阵、流式能力、包体、团队规范和既有生态，而不是绝对认为一个一定更好。

## 【问题】
关于 Axios 有哪些常见误区？

## 【回答】
- **误区：Axios 能自动解决所有错误**。——它只能统一请求层，业务错误、权限和降级仍需设计。
- **误区：Axios 的并发方法可以限制并发**。——结果聚合不等于调度限流。
- **误区：取消 Axios 就一定停止服务端任务**。——客户端取消和服务端停止是两层协议。
- **误区：所有项目都必须用 Axios**。——小项目或原生 Fetch 已足够时，引入依赖可能增加成本。
