# 前端工程化总览

## 【问题】
什么是前端工程化？它的核心价值是什么？

## 【回答】
前端工程化就是**把大量有依赖关系的源文件，经过可重复的解析、转换和优化，交付成浏览器能够稳定加载、执行和缓存的资源**。`import` 不只是“引入一个文件”，它**声明了模块依赖**，构建工具围绕这张依赖图完成转换、优化和交付。
其核心价值来自模块化：如果没有模块化，多个脚本只能靠**全局变量和标签顺序**协作，会产生命名冲突、隐式依赖和难以维护的加载关系。模块化让每个文件**明确自己的依赖和公开接口，同时隐藏实现细节**，带来**依赖可见、作用域隔离、接口明确、可分析**四大价值。工程化不是单纯的文件拆分，而是对构建、缓存、拆分的统一治理。

---

## 【问题】
从 import 到浏览器执行，整体链路是怎样的？

## 【回答】
链路分开发和生产两个阶段。

开发阶段：
```
浏览器请求 index.html
  ↓ 遇到 <script type="module" src="/src/main.js">
  ↓ 请求 main.js，并继续请求 import 依赖
  ↓ Vite 按请求转换 Vue/TS/JS/CSS 等源码
  ↓ 浏览器解析并执行模块
```
现代浏览器**原生理解 ESM**；Vite 开发服务器主要负责**模块解析、路径处理、源码转换、依赖预构建和 HMR**，而不是把不认识的 import 全部翻译成普通代码。

生产阶段：
```
入口文件 → 解析 import/export 构建依赖图 → Loader/Plugin 处理资源
  → Tree Shaking、压缩、代码分割、资源指纹 → 生成 HTML/CSS/JS/图片
  → 部署到服务器/CDN → 浏览器下载、解析、执行、渲染
```
生产构建的目标**不是“文件越少越好”**，而是在初始下载、请求数量、缓存命中、解析执行和运行时加载之间取得平衡。

## 【问题】
依赖图中的 Entry、Module、Chunk、Bundle 分别是什么？

## 【回答】
把模块看作**节点**，把 `import` 或动态 `import()` 看作**边**，就得到模块依赖图：
- **Entry**：构建起点，构建器从入口开始寻找依赖。
- **Module**：源模块，即被 import 的单个源文件。
- **Chunk**：构建过程中的**模块集合与运行时边界**，静态依赖通常进入同一 chunk，动态依赖形成异步边界、通常生成额外 chunk。
- **Bundle**：最终输出的**文件**。

四者**不能混为一谈**：Entry 是起点，Module 是源单元，Chunk 是构建中间结构，Bundle 是产物。静态依赖可在构建前发现，适合做 **Tree Shaking 和公共模块提取**；动态依赖形成异步边界，通常会生成额外 chunk。

## 【问题】
Webpack 与 Vite 的设计取舍有何不同？

## 【回答】
**Webpack 从入口递归构建依赖图**，使用 **Loader 转换模块、Plugin 参与构建生命周期**，再输出 bundle/chunk。优势是**生态成熟、资源处理统一、流程可控**；代价是开发启动需要先构建较大的依赖图和产物。
**Vite 开发态利用浏览器原生 ESM**，先启动服务器，模块被请求时再转换；**依赖预构建把 CommonJS 或复杂依赖整理成更适合浏览器加载的形式**。生产态仍需要统一构建，以获得压缩、拆分、缓存和部署资源管理能力。
关键结论：**“Vite 快”主要是开发阶段减少全量打包等待**，不代表生产环境完全不打包，也不代表任何项目都应无条件替换 Webpack。两者是不同优化路径。

## 【问题】
脚手架（如 npm create vite）的职责边界是什么？

## 【回答】
执行 `npm create vite` 时，脚手架通常会：① **创建目录和基础文件**；② **选择框架、语言和模块方案**；③ **写入 package.json、脚本和构建配置**；④ **配置开发服务器、入口、别名和基础插件**；⑤ **生成示例代码和依赖安装说明**。
脚手架**不是新的运行时**，它把重复的初始化决策封装成模板。其职责边界是“可运行的起点”，团队仍要审查 **Node 版本、依赖版本、环境变量、构建产物、部署方式和安全策略**，不能把脚手架生成的配置当作最终最佳实践。

## 【问题】
开发阶段（dev）与生产构建（build）的目标有何不同？

## 【回答】
两者是**两条不同的优化路径**，不能互相替代：

| 阶段 | 主要目标 | 典型策略 | 关注指标 |
|---|---|---|---|
| dev | 修改后快速反馈 | 按需模块服务、HMR、依赖预构建 | 冷启动、HMR 延迟、错误定位 |
| build | 用户侧稳定交付 | 打包、压缩、拆分、兼容、资源指纹 | 产物体积、LCP、缓存、请求瀑布 |

**不要用开发服务器启动速度代替线上性能结论**；开发关注反馈速度，生产关注产物体积、缓存命中与真实用户指标（LCP/INP）。

## 【问题】
关于前端工程化有哪些常见误区？

## 【回答】
常见误区包括：
- **误区：构建工具的唯一目的就是把代码变成浏览器能执行的代码**。实际上还包括资源组织、优化、拆分、缓存和开发体验。
- **误区：Vite dev 不打包，所以 Vite build 也不需要打包**。开发和生产目标不同。
- **误区：Chunk 越多越好**。过度拆分会产生请求瀑布和运行时开销。
- **误区：脚手架生成的配置就是最终最佳实践**。它只是可运行的起点。

工程化带来可复现构建、依赖边界、缓存和协作效率，但也增加配置、构建时间、source map、版本兼容和排错成本，应据项目规模、兼容矩阵、首屏预算和团队能力选型。

## 【问题】
面试时怎么答「前端工程化」？

## 【回答】
**30 秒基础回答**：`import` 声明模块依赖，构建工具围绕依赖图进行源码转换、优化和资源输出。Vite 开发态利用浏览器原生 ESM，模块被请求时才转换；生产态仍通过构建流程完成压缩、Tree Shaking、代码分割和缓存友好的资源生成。Webpack 更偏提前构建完整依赖图，Vite 更偏开发阶段按需提供模块。

**1～2 分钟高级回答**：没有模块化时，脚本依赖靠全局变量和加载顺序维持，项目变大后会出现命名冲突和隐式依赖。ESM 通过静态 `import/export` 暴露依赖边界，构建工具据此生成依赖图。开发阶段 Vite 让浏览器请求模块、服务器按需转换并支持 HMR；生产阶段则统一构建，进行 Tree Shaking、代码分割、压缩和资源指纹。Webpack 的提前构建换来生态和流程控制，Vite 的按需开发换来冷启动和更新速度，最终应结合兼容性、产物、缓存和真实用户指标选择。
