# LLM Wiki 团队级外存与知识编译

## 【问题】

什么是 LLM Wiki？它为什么会被提出来？

## 【回答】

LLM Wiki 是 Karpathy 在 2026-04 发布的 gist 概念（至今已攒下五千多 star），核心是让 LLM **增量地构建并维护一座持久的 wiki**——一批互相链接的 markdown 文件，横在使用者和原始资料之间充当中介。人几乎不亲手写 wiki，只负责选源、提问和探索。

提出的背景是团队知识的"最昂贵存在方式"：上百篇文档散落在 iWiki、企业微信文档和工蜂仓库，篇幅长、结构松、彼此孤立、被多人日复一日改写，却没人通读全局、没人负责把碎片连成整体。代价是无论是人还是 agent，想弄懂一块业务都得从原文一页页重新读起，既有认知从未沉淀成可复用形态。

司内普遍基于 Knot 知识库（底层本质是一套 RAG 管线）做 AI 建设，它把"重新解析"自动化了，却没跳出"每次从头"的范式。落到真实业务，RAG 两类老毛病浮出水面：**切分问题**（proto 的 schema 单元被从中间切断，召回只剩两截残片）和**多跳问题**（检索不沿 import 依赖展开，引用全部悬空）。典型问题"这个 proto 某字段到底什么含义、被哪些库表引用"同时踩中两者。更深瓶颈在规模：传统 RAG 的切分/嵌入/向量库/索引重建都是 per-domain 固定成本，每扩一个业务域整套重来。

根因指向一处：知识始终以"原始文档 + 临时检索"形态存在，从没被整理成可直接使用、可搬运的制品。出路是在入库那一刻就把知识**一次性编译成制品**——语义单元与关系一并显式化，经解析、重组、互链，按对象组织成 agent 能沿索引直接导航的页面，且本身就是 git 仓库里的 markdown 文件，读取不依赖任何在线检索设施。

## 【问题】

LLM Wiki 与传统 RAG（以及 GraphRAG）的本质区别是什么？

## 【回答】

本质区别在**时机与产物**。RAG 是"**先撒网召回，再让模型从碎片里拼**"——查询期到索引上检索，图/向量都是查询期的索引结构。LLM Wiki 是"**顺着结构导航，按需精确加载**"——把知识在编译期一次性固化成 agent 可沿链接直接导航的 markdown 页面，**查询期不依赖任何在线检索设施**。一个是把检索做得更聪明，一个是干脆不在查询期检索。

可量化的维度对比：

- **知识形态**：原始文档 + 临时检索 vs 编译好的互链 markdown 制品
- **关键动作**：查询期撒网召回、拼碎片 vs 编译期固化、查询期沿链接导航
- **切分问题**：schema 被切成残片 vs 完整归纳、不切断
- **多跳问题**：引用悬空 vs 依赖显式互链、一跳直达
- **扩展成本**：per-domain 整套重建 vs 增量编译、按需更新
- **在线设施**：向量库、索引服务 vs 无，纯 git + markdown

与 GraphRAG 的区别：GraphRAG 同样不满足于朴素 RAG，用 LLM 从源文档抽实体图再做社区摘要，但落点仍在"查询时到图上检索"，每接入一个语料都要先付一次建图成本；本文把结构在**编译期一次性固化**成可导航页面，查询期零在线检索。

## 【问题】

团队版 LLM Wiki 的架构是怎样的？

## 【回答】

一句话内核："**像软件工程对待源代码那样对待知识**——单一事实来源、不可变、可回滚、编译一次而非每次查询重新推导。"

实现落在一个 git 仓库，知识分三层，数据**只从 raw 单向流向 docs**（整个架构只守一条纪律：不存在反向链路，raw 不接受来自 docs 或 iWiki 的任何回写）：

- **Layer 1 raw/**：iWiki 文档的本地原样快照，**只进不改，唯一事实来源**
- **Layer 2 docs/**：互链的结构化知识页面，人类只读，由 agent 编译写入
- **Layer 3 规则**：目录、页面规范、状态机与工作流的系统提示词（即 CLAUDE.md / AGENTS.md 的位置）

查询时 agent 先打开作为入口的 index.md（按领域组织的目录），顺着索引逐层下钻到对口的那个概念页，**只把命中的页面放进上下文来作答**，而不是整库一股脑读入。这样"某 proto 字段含义及被哪些库表引用"这类问题：字段含义在编译期就随完整 schema 一并归纳过不被切断，页面里指向库表的链接是编译期顺着 import 依赖显式建好的，agent 一跳就落到引用它的库表页——切分与多跳两个坑分别被"完整归纳"和"显式互链"填平。

该分层与 Agent Skills 三层加载同构：元数据与路由对应大入口和索引页，正文对应业务分区，支持文件对应具体词条与 raw。agent 每次工具调用沿页面链接跳到所需文件加载进上下文，必要时用 grep 直接检索，每次检索都带当前上下文出发，从根源避开"相似但无关"的召回噪音。

## 【问题】

把个人 LLM Wiki 升级为团队级知识库，做了哪些关键工程机制？

## 【回答】

由于知识源是持续变动的团队平台、调度依托蓝盾、智能依托 Knot，有两项要求躲不掉：其一是**实时性**（团队源一直在变，要及时跟上），其二是**低人工依赖**（没人逐次审核，系统须每步可判定、可恢复、出错可回滚）。五项决策正面回应：

1. **确定性与语义分离**：机械判定的活（源变没变、raw 是否最新、怎么发布）交确定性脚本在 CI 上做，只依赖 Python 标准库、可测试可复现；需要理解判断的（提炼要点、重写词条、处理矛盾、全局收敛）交 agent。昂贵的智能只花在真正不确定的地方。
2. **状态按写入方分区**：系统状态由三个文件承载、分属三个写入方——CI 独写拉取状态，agent 独写编译状态，同步脚本独写发布映射，三者写集合两两不相交，并发安全靠分区而非全局锁。"需要重编译"不落盘，由版本号与规范化内容哈希实时推导；版本号前进但哈希未变时只记一次空编译，不触发重新派生。
3. **单次原子提交**：docs 产物、编译状态与活动日志写进同一个 commit，消除"产物已提交、状态没回填"的撕裂窗口；刻意不记录编译对应提交哈希以躲开自引用；回退错误编译只需一条 git revert。
4. **非破坏式生命周期**：从不物理删除。过时在页面标 deprecated 并指明继任页（信号），同步脚本据此把平台文档移进回收站标记归档（效果）。矛盾只标注、只降 confidence，绝不自动裁决；不确定内容标 confidence: low 与 !review 留事后抽查；真正清理需人工确认。
5. **两遍同步**：文档发布前没有 docid，正文相对链接无法解析成平台链接，故拆两遍——第一遍为缺号文件调 createDocument 拿 docid 写回映射，第二遍解析完链接再 saveDocument。用**标准 markdown 相对链接**而非双链，因为平台不渲染双链、标准链接却能进入原生反向引用体系。

四条流水线串起闭环：定时拉取（cron 每天 03:00，也可手动）→ 拉源 push raw/；增量编译（push 命中 raw/ 调 agent 增量 ingest）→ push docs/；同步发布（push 命中 docs/ 两遍发布）；周期校验（cron 每周一 04:00 调 agent 全局 lint 收敛：检查跨源矛盾、重复页、孤儿页、断链、旧链接指向废弃页、事实漂移，机械修复直接执行，高置信且可逆的才自动进行，矛盾一律只标注）。

## 【问题】

实践上 LLM Wiki 比 RAG 的效果如何？有对照数据吗？

## 【回答】

文章在相同题集、知识源和底模下，对 Wiki 与 Knot 默认知识问答管线（简称 RAG）做了对比评测：30 道业务题，涵盖字段语义、表结构、协议边界、数据血缘、业务状态判断、SQL 生成；底模 GLM-5.2 与 hy3；30 题 × 2 方案 × 2 底模 = 120 条有效回答，temperature=0.3，每题 10 分上限，Rubric 正向加分 + 独立红线扣分。

结果：**Wiki 胜 19 题、RAG 胜 10 题、1 题持平**，且 Wiki 在两个底模上的总分均高于 RAG。两个代表案例：

- **同名字段的协议归属判断**：RAG 错误召回了国内 QZAP 字段（achived_optimization_goal 等真实存在但不属目标表），GLM-5.2 两组均 0 分；Wiki 沿"业务术语 → 目标表 → owner proto → 计划类型分支 → 结果字段"完成定位，两底模均 10 分。
- **用协议级证据证明字段不存在**：问 pageview_request 是否含 didsha1/didmd5，证明"不存在"需完整检查 owner proto 并说明其真实归属（get_ads_comm.DeviceInfo 等）。Wiki 两底模均形成可审计否定结论（10 分）；RAG 的 GLM-5.2 正确定位得 9 分，hy3 却停留表级说无法确认、推测在 masked 表（1 分）。

结论明确：**不主张以 Wiki 全面替代 RAG**——RAG 仍有 10 题胜出，直接语义召回在部分问题有效。更务实的方向是组合使用：Wiki 承载经过整理的核心知识（跨协议归属、字段血缘、协议级负向判断），RAG 补充对原始资料、新增内容和长尾信息的检索。腾讯 WeKnora 把 RAG 问答、ReAct agent 与 Wiki 模式放在同一平台，正是这种组合的体现。

## 【问题】

LLM Wiki 适合什么场景、有什么限制？

## 【回答】

**较适合当前 Wiki 方案**：知识规模约百个来源、数百个页面；需要**跨文档引用、多跳定位和矛盾标注**；**读多写少**、知识会被重复使用；可接受分钟至一周的最终收敛；来源具有稳定版本号和修改时间。

**需评估其他方案或组合**：知识规模显著超过已验证规模；主要是一次性全文查找或简单片段定位；高频写入、内容很少复用；要求实时更新或强一致读取；缺少可用于漂移检测的版本信号。

具体限制：自动漂移检测目前依赖 iWiki 的 docid/版本号/修改时间，接其他来源需实现源适配模块；页面用相对链接，重命名需原子更新全部入链，规模扩大后需评估稳定 ID 或固定 slug；agent 调用采用串行单锁，并发写入能力有限；增量编译只查受影响页面，跨源矛盾/重复/孤立页由每周全局校验处理，全局问题最长一周收敛延迟；自动编译无逐条人工复核，知识库是最终一致性而非强一致性；index.md 长度随页面增加，单一索引过长可能受上下文长度和位置偏差影响，需按领域拆子索引或加索引层检索。Karpathy 实践在约百源规模可行，该数字应视为已覆盖规模而非通用推荐阈值。

## 【问题】

有哪些同类系统？"知识编译"和"外存"这两个词的来历是什么？

## 【回答】

同一"为模型搭建持久外存"方向、节奏越来越密的产品与规范：llms.txt（2024.09 Jeremy Howard，根目录放 markdown 索引）、DeepWiki（2025.04 Cognition，已索引 5 万+仓库）、Anthropic memory tool（2025.09，跨会话增删改查文件）、Grokipedia（2025.10，自报 600 万+词条但无独立审计、质量受质疑）、AGENTS.md（2025.12 捐 Linux 基金会，6 万+开源项目使用）、Google OKF（2026.06，一个概念一个 markdown 文件）、LangChain OpenWiki（2026.07，GitHub Actions 代码变更后自动更新文档）、腾讯 WeKnora（2025 开源，RAG+ReAct+Wiki 同平台）。各家取舍差异在三个分野问题：**谁来写、人管什么、怎么更新**。本文系统：agent 独占写 docs，人只读、不确定内容标注后事后抽查、删除需人工确认；基于哈希的增量编译事件驱动；confidence 标注、矛盾只标不裁。

"知识编译"词源：Darwiche 与 Marquis 在 2002 年定义为"把知识库离线变换为目标形式，以换取在线查询的可解性"；更早 Anderson 在 ACT 理论用同词指称陈述性知识向程序性知识的转化。"外存"取自 LLM OS 隐喻——上下文窗口是内存、文件系统是磁盘（翁荔把 file system as persistent memory 列为 agent harness 三大设计模式之一）。

背景脉络有两条：知识众包一脉（Bush 1945 的 memex → Cunningham 1995 第一个 wiki → Wikipedia）问"一份共享知识凭什么被一群人持续维护"；LLM 外存一脉问"写不进权重的知识该存在哪、以什么形态复用"（权重训练后固定、上下文会话结束清空，Karpathy 比作《记忆碎片》主角，system prompt learning 主张像人记笔记那样靠编辑文本学习）。2026 年两条线在 Karpathy 的 LLM Wiki 上交汇——互链形式与读写需求被同一个模型合二为一，它既是外存的读者也是整理者，顺手接手了 memex 当年悬而未决的"谁来维护"。
