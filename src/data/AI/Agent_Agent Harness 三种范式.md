# Agent Harness 三种范式（DSH / OpenCode / Pi）

## 【问题】
什么是 Agent Harness？为什么 Agent 时代它如此重要？

## 【回答】
行业已达成共识：**Agent = Model + Harness**。其中模型是「灵魂」（负责推理、规划、生成），Harness 是「身体」（负责执行、边界、拦截）。

Harness 决定了模型**能看到什么、碰得到什么、哪些错误会被拦下**。模型本身只接触文本，真正触碰文件系统、shell、HTTP 的是 Harness。因此 Harness 划定了模型对世界的认知边界——同样的模型，套上不同的 Harness，能力、安全边界、使用体验可能天差地别。文章把「模型之外那层软件」称为 Agent Harness 的三种分岔路：**dsh 答「一切皆插件」、OpenCode 答「开箱即用产品」、Pi 答「最小内核 + 改造钥匙」**。

## 【问题】
一个通用的 Agent Loop 由哪几步构成？Harness 在其中做什么？

## 【回答】
Agent 循环可简化为五步：① 模型决定下一步；② 请求调用工具；③ harness 在现实世界里执行；④ 执行结果作为 observation 返回给模型；⑤ 模型更新自身状态，进入下一轮循环。

关键在于：**模型没有直接的机器访问权，所有对现实世界的操作都由 Harness 代理**。Harness 负责暴露工具、组织上下文、压缩历史、拦截错误，这些工作的质量直接叠加成不同 Agent 产品之间的体验差距。换句话说，Agent 的「质量上限」由模型决定，「质量下限与稳定性」由 Harness 决定。

## 【问题】
DSH（DeepSeek Harness）是什么？核心架构与特性有哪些？

## 【回答】
DSH 是 DeepSeek 于 **2026 年 8 月 13 日**开源的 Harness，核心主张是**「一切皆插件」，包括 agent 主循环本身都是可替换的插件**。它基于 **Cordis 内核**（源自 Koishi 机器人框架的插件运行时，能保证运行时替换的语义安全），奉行「时空可组合性编程」——服务可在运行时被替换，插件通过注入解耦。

关键事实与数字：
- DSH 开源后 **3 小时冲上 2 万多 GitHub star**，爆红速度极快。
- 其底层 Cordis/Koishi 底蕴深厚：**生产环境跑了 4 年，积累超 4000 个社区插件**。
- DSH 提供四种预设 Profile（可自由组合）：**标准**（完整 coding）、**极简**（文件 + 编辑）、**PTC**（将连续工具操作编译成一段 TypeScript 程序一次执行，大幅减少模型 ↔ 工具的往返开销）、**创造**（协助定义新 profile）。
- 代价是学习成本较高：需掌握**十个核心概念**（profile、bundle、seam、scope、preset、turn、step 等）。
- 通过 `dsh-import-agents` 这类跨项目插件可统管其他 Harness 的会话。
- 安全边界靠**权限检查插件**实现。

## 【问题】
OpenCode 是什么？核心特性有哪些？

## 【回答】
OpenCode 是**成熟的产品型 Harness**，主打「开箱即用」，把最佳实践预置为默认行为，用户不需要懂内部机制。

关键事实与数字：
- 内置 **Plan（限制修改）与 Build（放开权限）** 两种 agent 双模式；Plan 模式下只允许改小部分文件，Build 模式放开全部权限。
- 集成 **LSP 智能**（把编译期错误直接注入上下文）与 **75 家以上**模型提供商。
- 用 **AGENTS.md** 作为项目长期指令，可通过 `/init` 命令自动生成。
- 安全边界由**内置权限系统**提供；MCP 即插即用。
- 成熟度：**生产级**，默认权限与完善的内置工作流让它「上手即用」。

## 【问题】
Pi 是什么？核心特性有哪些？

## 【回答】
Pi 走了一条**反直觉的极小内核**路线：核心仅 **4 个工具**（`read` / `write` / `edit` / `bash`），系统提示 **≤ 1000 token**，**没有 MCP、没有子代理、没有计划模式**；可扩展性完全靠 **TypeScript hook** 实现。

关键事实与数字：
- 提供 **25+ 个 TS hook 点**，覆盖输入改写、生命周期等，例如 `input`（改写用户输入）、`before_agent_start`（注入系统提示）、`tool_call`（终止 / 改参）、`agent_start` / `agent_end` / `turn_start` / `turn_end` 等。
- 设计理念：现代模型在训练中已经学过工具调用，Harness 只需提供最低限度的基建，因此 Pi 主动「退到一边」。
- 会话呈**树状结构**，支持分支派生，便于并行试验不同方向。
- 跨平台互通：可借 `opencode-pi` 插件使用 OpenCode 的模型通道。
- 安全边界：**默认继承进程权限**，需自行接入容器 / 沙箱才安全（安全风险由用户自担）。
- 成熟度：**生产级**，但核心极小，适合想「完全拥有并亲手拆装」agent 的人。

## 【问题】
DSH、OpenCode、Pi 三者在核心维度上如何对比？

## 【回答】
从五个核心维度横向对比（数据均来自文章）：

| 维度 | DSH | OpenCode | Pi |
|------|-----|----------|----|
| **核心架构** | 一切皆插件，loop 可替换 | 固定 loop，边缘可扩展 | 最小内核，运行时 hook |
| **定制入口** | 替换插件 / 组合 profile | AGENTS.md / 命令 / 插件 | TypeScript 代码 |
| **内置工作流** | 四预设（标准/极简/PTC/创造） | Plan 与 Build 双模式 | 无（由扩展提供） |
| **安全边界** | 权限检查插件 | 内置权限系统 | 默认无，需自行添加 |
| **成熟度** | developer preview | 生产级 | 生产级（核心极小） |

三者**不互斥、不替代**，对应不同的工程哲学：DSH 追求**系统可重构性**（目标成为 agent 界的 Linux 内核），OpenCode 追求**体验开箱即用**（大多数人的每日首开终端），Pi 追求**认知可理解性**（亲手构建者的第一站课堂）。

## 【问题】
面对 DSH、OpenCode、Pi，应该选哪条路？

## 【回答】
选型本质是在回答「你和 agent 的关系是什么」：

- 想**尽快干完活** → 选 **OpenCode**：成熟、默认权限合理、Plan/Build 双模式、AGENTS.md 一站到位，最省心。
- 做**团队 / 企业基础设施** → 选 **DSH**：可替换的插件槽位带来极强可重构性，但要接受 preview 阶段可能破坏既有变更，且需学习十个核心概念。
- 个人想**完全拥有并亲手拆装 agent** → 选 **Pi**：4 个工具即可跑通，hook 高度自由，但安全要自己负责。

文章给出的浓缩抉择是：「要**开箱即用的工具**、**可重构的平台**、还是**可完全拆开的机器**」。评测侧参考：一份测试显示 Pi 与 OpenCode 任务通过率并列；另一份测试中 Pi **21/30** 对 OpenCode **19/30**。
