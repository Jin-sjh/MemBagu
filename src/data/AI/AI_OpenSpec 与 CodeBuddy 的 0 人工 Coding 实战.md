# OpenSpec 与 CodeBuddy 的 0 人工 Coding 实战

## 【问题】
传统「AI 辅助编码」模式有哪些结构性痛点？为什么效率提升很难超过 50%？

## 【回答】
文章的核心判断：即便团队里的 AI 老手，用 AI 辅助编码的效率提升也很难超过 **50%**，原因不是模型不够聪明，而是**协作方式存在结构性缺陷**。具体有四大痛点：

| 痛点 | 具体表现 | 根因 |
|---|---|---|
| 人机协作无标准 | 效果取决于个人提示词功力，老手提效明显，新手反而更慢 | 没有统一的 AI 交互规范，输入质量因人而异 |
| 流程断点 | 工程师变成「人肉翻译器」，在方案文档和 IDE 之间来回搬运信息 | 设计工具与编码工具之间数据隔离，无法自动传递上下文 |
| 上下文缺失 | AI 不认识项目，可能重复造轮子、违反架构规范 | AI 无法主动读取项目代码库与技术规范，只能看到手动喂的片段 |
| 文档脱节 | 方案写进 Wiki 后就再没更新，新人只能「考古」代码 | 文档和代码不在同一版本控制系统，天然失同步 |

核心认知：把 AI 当**打字员**用，天花板很低；把 AI 当**施工队**用，才有真正的效率革命。

## 【问题】
OpenSpec 是什么？「0 人工 Coding」模式下人与 AI 如何分工？

## 【回答】
OpenSpec 是一套「**机器和人能共同理解的研发契约**」。用「盖房子」类比：AI 就像施工队，工程师不再零散地下指令，核心工作是把「**建筑图纸**」画清楚。

五大阶段的人机分工：

| 阶段 | AI 负责 | 人负责 |
|---|---|---|
| 需求分析 | 提炼需求、发现遗漏、结构化输出需求文档 | 优先级判断，审批需求边界 |
| 方案设计 | 生成技术方案、架构图、接口定义、风险清单 | 技术选型拍板，安全审查 |
| 代码开发 | 根据设计方案进行多文件编码、补充注释和单测 | 评审关键代码，控制合并门禁 |
| 测试验证 | 生成测试脚本、执行回归测试、分析失败原因 | 审核高风险场景，最终放行决策 |
| 发布上线 | 校验实现是否与需求一致，提供发布清单 | 审批发布窗口，处理事故升级 |

人的核心角色只有三个：**决策、审批、把关**。

## 【问题】
CodeBuddy + OpenSpec 实现「0-Coding」的核心三步工作流是什么？

## 【回答】
总原则：**严禁直接让 AI 写大段业务代码，必须先生成规划文档**。核心三步：

- **Step 1 `/opsx:propose`**：一句话生成全套规划文档——`proposal.md`（需求背景与目标：「为什么做」和「做什么」）、`design.md`（技术方案与架构决策：「怎么做」）、`tasks.md`（带复选框的实施清单，即 AI 的「施工单」）、`specs/`（本次变更的「差异记录」）。
- **Step 2 `/opsx:apply`**：AI 读取 `tasks.md`/`design.md`/`proposal.md`，跨文件批量生成/修改代码，每完成一项自动打钩。开发者此时只需要做一件事：**Code Review**。
- **Step 3 `/opsx:archive`**：MR 通过后执行，系统自动将本次规范增量合并回 `openspec/specs` 主目录并清空变更草稿。效果：**项目文档永远和代码保持同步，没有「僵尸 Wiki」**。

关键卡点：**Step 2 的 Review 是质量的生命线**；`tasks.md` 建议控制在 **15 项以内**，避免 AI 因上下文过长产生幻觉。若变更涉及前端页面，在 Step 2 和 Step 4 之间要加「原型审查」环节（先画原型 → 团队确认 → 把截图/链接贴回 `design.md` → 再执行 `/opsx:apply`），因为 Proposal 和 Design 解决不了「页面长什么样」的问题。

扩展工作流命令：`/opsx:explore`（探索模式，和 AI 讨论需求，**只输出文档绝不改代码**）、`/opsx:new`（创建空脚手架）、`/opsx:continue`（步进式生成，Proposal → Review → 再 Design）、`/opsx:ff`（快进生成，一次补全所有规划）、`/opsx:verify`（AI 代码审计，比对 design.md）。

## 【问题】
如何让 AI 真正「懂」项目？知识库 / MCP / Skills 三大武器库分别解决什么问题？

## 【回答】
三者关系的一句话概括：**知识库让 AI「知道」项目，MCP 让 AI「连接」工具，Skills 让 AI「掌握」方法**。

- **知识库**：解决「AI 不知道项目背景与规范」。两个通道：一是 OpenSpec `specs/` 作为项目「活文档」；二是 MCP 外部知识，连接知识库平台存放**业务术语、架构决策历史、踩坑记录**等。
- **MCP（工具连接层）**：把内部系统封装成 AI 可调用的工具——TCS Component（前端组件库，确保风格统一）、TAPD MCP（需求平台，直接查原始需求/Bug 单）、iWiki MCP（文档平台，检索设计/架构文档）、极光流水线 MCP（部署平台，触发构建、查部署状态）。
- **Skills**：团队沉淀的**标准化操作流程 SOP**，封装成 AI 可复用的「技能包」，统一管理在技能仓库。

## 【问题】
`openspec-installer` Skill 的三个关键设计决策（Bridge Rule / Token 交互 / 三级降级）揭示了哪些 AI 研发设计原则？

## 【回答】
该 Skill 把「新项目搭环境」从手动 8 步（找 Wiki 指引、装 Node.js、装 OpenSpec CLI、`openspec init`、改 `config.yaml`、配 MCP、装 Skills、搭知识库）压缩成一句话指令。三个关键决策：

1. **Bridge Rule：只「指路」不「复制」，保持 single source of truth**。`openspec/config.yaml` 可自定义 rules（如归档前检查 MR、归档后更新索引），但 AI 不会主动去读它。解法是安装时生成 `.codebuddy/rules/` 下的 Bridge Rule 文件，内容很简短、只像「指路牌」告诉 AI「执行 OpenSpec 操作时先读 config.yaml 中的 rules」——**不把规则内容复制进去，config.yaml 始终是唯一事实源**。版本迭代教训：v0.4.2 用 `alwaysApply: false` 实测偶发漏判，v0.4.3 改为 `alwaysApply: true` 后彻底解决。
2. **Token 交互放 SKILL.md 而不是 bash 脚本**。原因：CodeBuddy 的 bash 执行环境是**非 TTY**，脚本里 `read -p` 会导致挂起。所以 Token 获取在 SKILL.md 的 SOP 里由 AI 在对话中向用户索取，并允许回复「跳过」；同时无条件、幂等地将 `.mcp.json` 加入 `.gitignore`，防止含 Token 文件被提交到 Git。
3. **版本检查三级降级策略**（MCP 查询 → git clone 获取 → 兜底静默跳过）。核心原则：**辅助功能的失败不应该阻塞核心功能**。

## 【问题】
团队级落地 AI Native（0 人工 Coding）研发，有哪些必须坚持的协同原则？

## 【回答】
- **原子化变更**：一次变更只解决一个需求或 Bug；`tasks.md` 控制在 **15 项以内**，避免 AI 上下文过长产生遗忘或幻觉；**小步快跑**，确保人工 Code Review 可控。
- **规范即文档**：禁止绕过 OpenSpec、不要绕过流程直接手写大量核心业务逻辑，全员坚持 SOP，交付质量标准化、交接与维护成本最低——否则 Spec 会沦为「死文档」。
- **MR 审查双重视角**：审查 MR 时同时看代码和规划文档——代码逻辑对照 `design.md`（是否遵守约束）、架构合规对照 `proposal.md`（技术方案是否符合团队底线）、需求覆盖对照 `specs/`（规范定义的行为是否都已实现）。

更深层的认知：AI 不是来替代程序员的，而是来**重新定义「程序员」这个角色**。类比软件工程史——机器码到汇编不再关心寄存器、汇编到高级语言不再关心内存地址，写代码到 AI Native 则不再关心具体代码实现，而更关心**需求定义与架构决策**。
