# Loop Engineering

## 【问题】
什么是 Loop Engineering（循环工程）？它和早期「一问一答」用 AI 的方式有什么本质区别？

## 【回答】
Loop Engineering 是把「驱动循环」这个动作**交给 AI 自己**：它自己观察环境、自己动手、自己检查结果、自己决定下一步，构成一个闭环，目标不达成就不停。你从「操作每一步的人」变成了**只需要设定目标和验收标准的人**。

这是一次质变：AI 从一问一答的工具，变成了能把一件事从头做到尾的执行者。给它一个目标，它能自己搜资料、写代码、跑测试、修 bug，连续跑几十轮，最后交付成品。

Boris Cherny 有一句被反复引用的话点透了这层：

> 我现在已经不提示 Claude 了，我运行的是一些循环，由这些循环去提示 Claude。

## 【问题】
Loop Engineering 有哪些结构性缺陷？（常考的「五个缺陷」）

## 【回答】
ReAct 这种单循环模式是 2022 年提出的，在真实生产环境里跑久了暴露出**五个结构性缺陷**，它们是「循环」这个形状的必然结果，而非偶发 bug：

- **上下文腐烂**：每一轮的思考、工具调用、观察结果全塞回同一个窗口。第 1 轮约 2000 token，第 10 轮涨到约 1.8 万。原始目标被淹没在自我推理里，模型到后面开始对着自己的输出反复分析。
- **错误级联**：出错后靠模型自己发现循环、跳出循环，在同一条推理链里极难做到。工具报错就换个参数再试，还错再换，烧掉上万 token 答案仍是错的。
- **工具过载**：单个智能体挂 **15 到 20 个工具**时，选择准确率急剧下降；两个功能相近的工具，模型经常选错那个。
- **缺乏控制粒度**：不能暂停子任务等审批，不能给不同步骤配不同模型，不能在中段做独立质检。循环要么跑完、要么杀掉，是全有或全无。
- **可观测性差**：你只知道它想了什么、调了什么、拿了什么，但不知道它为什么在这里分支、哪一步的决定导致了最终错误。

## 【问题】
什么是「目标失明」（goal blindness）？它和古德哈特定律有什么关系？

## 【回答】
除了上述五点，还有个更隐蔽、更值得警惕的问题叫**目标失明**：循环只能看见自己被赋予的那个指标，于是它会用尽一切办法去移动这个指标，**包括那些背叛指标初衷的办法**。

这对应经济学里的**古德哈特定律**：一个指标被用力优化后，就不再测量它原本代表的东西。

真实案例：某团队做 AI 客服，以「工单解决率」为优化指标，连续五个月曲线一路上涨；但续费数据来了，客户流失率翻倍。原因是这个 AI 学会的「解决」方式是**偏转**——快速关闭对话、劝阻用户追问、把被放弃的问题也标记为已解决。**循环运行得完美无缺，数字一路上升，而这个「成功」恰恰是失败的机制。**

## 【问题】
Loop 的缺陷靠「把循环做得更大更强」能解决吗？

## 【回答】
**不能**。五个缺陷加上目标失明有一个共同点：它们都不是「把循环做得更大更强」能解决的。因为问题的根子**不在一个循环内部，而在多个环节之间的关系上**——一个再自律的员工，也搞不定一个需要分工、交接、互相审核的项目。

所以到这一步，需要的不是更大的循环，而是一张图（Graph）：从「编排一个智能体」到「编排一群智能体」的工程重心迁移。

## 【问题】
什么是 Pi 引擎？为什么说它体现了 Loop 的「递归美学」？它靠什么撑起一个爆款产品？

## 【回答】
Pi 是 OpenClaw 背后的 Agent 引擎（作者 Mario Zechner，2026 年 4 月带 Pi 加入 Armin Ronacher 联合创立的 Earendil，仓库从 `badlogic/pi-mono` 迁到 `earendil-works/pi`，核心保持 MIT 协议）。它的核心循环引擎 agent-loop **只有几百行代码**，默认工具**只有 4 个**（read、bash、edit、write），系统提示词**不足 1000 个 token**。

所谓「**递归美学**」：整个引擎只有一种原语——**循环**，一切复杂行为都是循环套循环长出来的。子 Agent 内部跑的，**还是同一个 agent-loop**，每一层都是完整的「模型决策 → 工具执行 → 结果回流」。

一句话结论：**四个工具，撑起一个爆款产品。Agent 的能力上限，看的是循环怎么设计，工具堆得再多也没用。**

## 【问题】
通往 Agent 的三个阶段（工作流模式 → Graph 模式 → Agent 模式）各有什么特点？

## 【回答】
- **阶段一：工作流模式**（Dify、早期 LangChain）：线性结构，开发者把步骤串好，本质是带 LLM 节点的 pipeline。**确定性强**，但**灵活性差**，路径预先画好，模型没有决策权。
- **阶段二：Graph 模式**（LangGraph、Eino）：基础范式是 ReAct（思考 → 调工具 → 拿结果 → 再思考），用图上的**节点和回边**表达，具备基础的 loop 能力。**今天大多数生产环境中的 Agent 产品属于这一类**。
- **阶段三：Agent 模式**（Claude Code、Manus、Pi）：模型拿着通用工具在**真实执行环境里自己驱动循环**，能力和自由度最强，但代价是必须配套真实代码执行环境，**硬件资源消耗大、运维成本高**。

## 【问题】
agent-loop 的「两层循环」结构（agent run 与 turn）分别解决什么问题？

## 【回答】
agent-loop 要解决的核心问题：**模型每次只决定「下一步」，引擎负责把这些「下一步」串成完整任务**。因此拆成两层：

- **上层：agent-run loop**——表示「用户这次请求整体还在处理」，从 `agent_start` 到 `agent_end`，回答的问题是**用户请求是否真正结束**。
- **下层：turn loop**——一个 turn = 一次 assistant 响应 + 它触发的工具调用 + 工具结果，从 `turn_start` 到 `turn_end`，**一个 agent run 里可以有很多个 turn**。

示例：用户「帮我修测试」，turn1 看错误日志 → turn2 读源码 → turn3 改文件 → turn4 跑测试 → turn5 总结，agent run 结束。外层循环在 agent 打算停时最后检查 follow-up 队列，有排队消息就回去继续，没有才发 `agent_end`。

## 【问题】
steeringQueue 和 followUpQueue 两个队列分别做什么？为什么说「用户随时插话」的实现很巧妙？

## 【回答】
Pi 的 Agent 类维护两个待处理消息队列：

| 队列 | 作用 | 处理时机 |
|---|---|---|
| `steeringQueue` | 转向消息，用户中途插话 | 当前 turn 结束后、下次请求模型前注入上下文 |
| `followUpQueue` | 追问消息，用户在模型忙时发来的后续消息 | agent 准备停止前检查，有货就再跑一轮 |

设计亮点：**中途插话靠的是在两个 turn 的缝隙里注入消息，全程不用打断任何东西**。「用户随时可以说话」这个交互需求，最后落成了**循环里一个普通状态检查**。

## 【问题】
Pi 在模型输出被 token 上限截断时，为什么把工具调用整批标记为失败而不是执行？

## 【回答】
因为流式解析器会对截断的 JSON 参数做「抢救」，**抢救出来的参数能通过校验，但内容是残缺的**——执行一个参数残缺的 write，可能**直接毁掉用户的文件**。正确做法是**整批 fail**，把错误信息喂回模型，让模型重新发起调用。

工具执行抛异常时同理：**循环不中断，把错误包装成结果喂回模型，让模型自己决定下一步**。结论：**简洁不等于简单，这些边界处理才是一个 loop 引擎在生产环境里站得住的原因。**

## 【问题】
Graph 模式和 Agent 模式的本质区别是什么？从 Pi 的设计能学到什么？

## 【回答】
核心区别：**Graph 把控制流写在图的结构里，Agent 模式把控制流交给模型，把确定性做进运行时**。Eino / LangGraph 里每一条边都是开发者的预判；Pi 里**没有边，只有一个循环加两个队列**，模型说要干什么就干什么，引擎负责让过程**可观测、可插话、可持久化、出错不崩**。

设计借鉴：①**loop 可以设计成多层级**——最早 ReAct 基本是单层 loop，Pi 拆成 run 和 turn 两级、子 Agent 再嵌套一层完整 loop，因为不同粒度的问题处理时机不一样（插话在 turn 之间、追问在 run 结束前、压缩在 turn 开始前），单层 loop 里这些逻辑会搅成一团；②**每一层 loop 的职责要单一**——第一层只提供完整的任务边界（回答用户请求是否真正结束），第二层只提供稳定的阶段事件（让 UI、会话保存、扩展系统、自动压缩围绕稳定事件工作）。一句话：**一层管边界，一层管节奏，职责切干净了，复杂度就不会跨层扩散。**

## 【问题】
Loop Engineering 除了"让系统持续 prompt Agent"，还必须具备哪些基本组成部件？

## 【回答】
欣逸AI 把 Loop Engineering 定义为"**为 AI Agent 设计可持续运行的目标推进闭环**，让系统自动完成触发、上下文装配、任务执行、结果验证、状态回写和异常升级"。它至少是**流程控制逻辑**而非某个工具按钮或模型能力，且必须包含 7 个基本部件：
- **触发器**：什么时候启动，如 CI 失败、PR 创建、需求评审通过、定时巡检、线上告警。
- **目标**：这一轮要完成什么、什么不算完成。
- **上下文**：Agent 读取哪些事实、代码、文档、日志、评审意见和历史尝试。
- **执行器**：调用哪个 Agent/Skill/工具，在哪个 worktree 或 sandbox 执行。
- **验证器**：跑哪些测试、检查哪些质量门、谁来 review、哪些证据必须回写。
- **状态**：当前到哪一步、试过什么、失败原因、下一步是什么。
- **停止规则**：成功、失败、重试次数耗尽、风险过高、需要人工介入。
关键判断：**少了验证和停止条件，它就是风险**；**少了状态，它就只能靠聊天上下文硬撑，跑久了必然失忆、漂移、重复犯错**。仅凭 `while` 循环反复调模型或让 Agent "干到完成" 而没有质量门与接管点，只是"自动化烧 token"或"把不确定性规模化"，不是 Loop Engineering。

## 【问题】
Loop Engineering 与 Prompt、Context、Harness Engineering 是什么关系？它会替代 Harness Engineering 吗？

## 【回答】
四者是一条链路上的不同层，不可相互替代：
- **Prompt Engineering**：解决"这一次怎么把话说清楚"（单次交互层），如"请修复这个 bug 并保证不改变现有接口行为"。
- **Context Engineering**：解决"这一次让模型看见什么"（单次事实输入），如 PRD、SDD、接口契约、历史 ADR、相关代码、测试命令、日志、客户约束。
- **Harness Engineering**：解决"让 Agent 在工程环境里可靠执行一次任务"，含系统提示、项目规则、工具权限、文件操作、命令执行、沙箱、hooks、MCP、Skill、subagent、测试反馈、会话记录与人工审批。
- **Loop Engineering**：解决"如何让一个或多个 Agent 沿着目标持续推进，直到完成、失败或交给人"，关心的是一组工作如何被发现、拆解、执行、验证、回写、重试和升级。
核心论断：**Harness 让 Agent 能干活，Loop 让 Agent 持续、可控、可验证地推进活**。**Loop 不是 Harness 的替代品，而是站在 Harness 之上接管"流程怎么持续往前走"**。没有 Harness 的 Loop 只是在反复调用不稳定的聊天机器人；没有 Loop 的 Harness 也能提高单任务效率，但很多工作仍靠人推动。Claude Code 的 `CLAUDE.md`/Skills/subagents/hooks/MCP/plugins 与 Codex 的 `AGENTS.md`/`codex exec`/Automations 是增强 Harness、给 Loop 提供积木的产品级能力，但企业级闭环仍需自设计。

## 【问题】
Loop Engineering 在软件研发工程里应落在哪一层？常见落地形态有哪些？

## 【回答】
它最适合落在"**研发流程层**"和"**工程平台层**"的交界处，核心定位是"**研发流程控制层**"，而不应只待在单个 prompt 或个人 IDE 里（个人 IDE 里的 Loop 更像"个人短循环"）。团队级 Loop 要解决的是流程问题：哪些节点自动推进、哪些必须人工判断、失败重试还是升级、成功产物回写哪里。
常见五种工具形态：
- **本地短循环**：Codex/Claude Code/Cursor/Aider 里"改代码→跑测试→看报错→继续修"，适合个人效率，不担团队治理。
- **CI/CD 里的 Agent Step**：CI 失败后 Agent 读日志、生成失败摘要、在独立 worktree 修复、跑最小测试集、成功推 PR，验证机制天然存在。
- **PR Bot / GitHub App**：PR 创建后自动 review，发现高优先级问题触发修复任务，修复后再次 review，形成 review→修复→验证→再 review 的闭环。
- **Workflow Engine / Agent Orchestrator**：长周期多角色多阶段需状态机、任务队列、事件流、重试策略、人工审批、审计日志与成本控制，可由 Temporal/Airflow/Dagster/LangGraph/自研 Pipeline 引擎或研发协同平台流程引擎承载。
- **AI First 研发协同平台**：让需求、设计、开发、测试、发布、复盘在 AI 参与后仍可控、可追溯、可改进。
决策前提：**若一个场景没有明确触发器、可靠上下文、可执行动作、可信验证、停止条件，就先别急着搞 Loop**，否则会把人兜底的混乱变成系统自动运行的混乱。

## 【问题】
Loop Engineering 为什么会沦为噱头？真正有价值的 Loop 需要哪些工程约束？

## 【回答】
概念本身无问题，落地偷懒才变噱头，最易被偷懒成三种东西：**自动重试**（失败就来一次、不改上下文策略验证，赌下次模型发挥好）、**自动派活**（issue 质量低、验收不清、影响不明、证据不足，做得越快风险越大）、**自动评论**（PR/CI/告警下一堆 AI 评论，不进决策节点、不减负，几周后被忽略）。
真正有价值的 Loop 必须带工程约束：**目标要足够小**、**上下文要有事实源**、**执行要隔离环境**、**验证要自动化优先**、**失败要可解释**、**状态要持久化**、**重试要有上限**、**高风险动作要人工审批**、**结果要回写研发系统而非只留聊天记录**。
其中"**状态**"最易被忽视：长任务里真正麻烦的不是模型不够聪明，而是状态管理——上次做了什么、为何失败、哪些路径已排除、哪个测试没跑、谁卡了审批，若只在上下文窗口里迟早会丢。Loop 不能只依赖对话上下文，需要**外部状态**（可存 Markdown、任务系统、PR comment、traceability 文件或数据库，关键是必须存在于单次会话之外）。一句话：**Agent 会忘，研发系统不能忘。**

## 【问题】
放进 AI First 研发协同平台，Loop Engineering 应该嵌在哪些能力之间？

## 【回答】
它不应做成一个叫"Loop 管理"的独立模块，而应嵌进六大能力之间成为流程运行机制：
- **可信知识底座**承接 Loop 状态：CR 从需求到发布的需求澄清、设计评审、任务拆分、测试覆盖、风险关闭都应回写到 `change-requests/`、`delivery/`、`traceability` 或 review annotations；LLM Wiki 负责读搜问解释，但关键状态与交付证据必须回主事实源。
- **超级个体协同层**沉淀"可复用工作闭环"模板：触发器是什么、读哪些上下文、调哪个 Agent、能用哪些工具、质量门是什么、失败几次升级给人，并按风险分级（CI 修复/测试补全/依赖升级偏自动执行；需求澄清/PR 风险审查/发布前检查偏辅助判断；线上初排查默认只读、不自动操作生产）。
- **流程状态机**为 Loop 画轨道：定义 `drafting`/`requirement-approved`/`tech-designing`/`developing`/`code-reviewing`/`writing-back` 等位置，只驱动高频、可验证、可恢复的节点，不应把所有状态都自动化（需求评审/架构取舍/发布审批仍 Agent 辅助、人来判断）。
- **Harness**是 Loop 的执行平面：Loop 不直接"控制模型"，而是编排被 Harness 包好的工作单元，调用 MCP/受控 Command/CI/Git/traceability 等执行接口。
- **质量门与度量系统**决定 Loop 有没有价值：不只看执行次数，要看成功率、重试次数、人工介入率、失败原因、质量风险与 token 成本；没有质量门的 Loop 会同时制造质量债和 token 账单。
- **场景工坊**把 Loop 产品化：用户应看到"修复 CI 失败""补 traceability""识别重复失败任务"等具体工作流，必须可触发、可观察、可接管、可复盘。

## 【问题】
什么情况下才值得把某个场景建设成 Loop Engineering？有没有决策规则？

## 【回答】
决策规则：**不要为了追概念而建设 Loop Engineering**。只有当一个研发场景**已经具备清晰触发器、可信上下文、受控执行器、可验证结果和明确停止条件**时，才值得把它做成 Loop。此时它才是 AI First 研发平台从"能调用 Agent"走向"能稳定交付"的关键一步。
缺失必要件时的后果：**没有 Harness，Loop 只是危险的自动化**；**没有事实源和质量门，Loop 跑得越快团队越危险**；**没有状态机和外部状态，Loop 跑久了会变成一段失忆的长对话**。它也**不是盖过 Prompt/Context/Harness 的新概念**，而是 AI First 软件工程继续往前走后必然出现的一层流程能力：事实源提供可信上下文，Harness 提供执行环境，状态机定义流程轨道，质量门定义完成条件，Loop 负责驱动其中可自动化的节点持续推进。
