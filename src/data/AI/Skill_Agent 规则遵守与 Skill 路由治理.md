# Agent 规则遵守与 Skill 路由治理

（沉淀自微信文章《当 Agent 总是忘记规则，怎么办？》Willis x AI，2026-07-19）

## 【问题】

Agent 经常不主动调用已存在的 Skill、或明明写了规则却不遵守，根因是什么？

## 【回答】

这并非单纯模型能力不足，而是**三层问题叠加**导致的"松动"故障：

1. **Skill 在，但没有进工作流**：以 OpenCode 为例，Skill 是"可被发现、可被加载"的能力，模型初始只看到名字和描述，正文要在调用后才进入上下文。若触发条件藏在 `SKILL.md` 正文而非 `description` 中，路由阶段模型根本看不到，Skill 就不会被稳定调用。
2. **模型会调工具，但不会替你治理流程**：模型（如 Kimi）支持 tool call，但是基于上下文的**概率判断**——可调用也可不调用。在长上下文、多轮对话、规则多、任务有歧义时，模型容易选"直接回答"的短路径。工作流治理不能完全靠模型自觉。
3. **Prompt 太长，规则反而会变软**：不断往 Prompt 加规则会像"内部制度文件"，但模型视之为平铺上下文。规则**重复、冲突、太长、太抽象会被稀释**。

## 【问题】

如何把 Skill 的"主动性"从模型记忆里剥离，强制约束 Agent 行为？

## 【回答】

核心思路是**分层**：能配置化的不写提示词，能变命令入口的不依赖模型选择，能放 `description` 的不埋正文。四个具体改法：

1. **高价值 Skill 做成命令入口（Command）**：固定工作流提供明确 command，直接指定 agent、model 和第一步动作，使 Skill 从"可能被想起"变为"入口即绑定"。
2. **使用 OpenCode 原生 Skill 结构**：不假设其他平台（如 Codex）的 Skill 包直接搬来可用；需配置正确的 skill 目录、frontmatter 和兼容字段，清理专属配置。
3. **触发条件前移到 description**：`description` 应承担路由作用，直接写清什么用户意图、关键词、任务类型、风险场景必须加载。正文可长，**首次触发要短**。
4. **写短小的全局 skill-router 放入 instructions**：在 instructions 放短促、稳定、每会话可见的路由原则（如：回答前先查 Skill；匹配 description 先加载；多匹配选最具体；无匹配再回答）。经验法则：**越像动作越易执行，越像制度越易被忽略**。

## 【问题】

Agent 的规则也要分层处理，具体怎么做？硬边界和软内容分别放在哪？

## 【回答】

- **硬边界进配置**：例如用 `permission` 禁止编辑（而非写"不要修改"）；用 `default agent`、`command`、`task permission` 约束子 Agent 分派入口。
- **Prompt 只写软内容**：角色、判断口径、少量专属动作。

收益在于**错误易定位**——是没看到 Skill？没权限？没命中 command？还是模型选错？而不是混成一句模糊的"Agent 又忘了"。

## 【问题】

换更强的模型能解决 Agent 不遵守规则的问题吗？

## 【回答】

**不能从根本解决，只能作为最后一层加固**。换更强模型（如 Kimi 2.7 Code）可改善长上下文下的指令遵循，但这只是锦上添花。总原则是：**不把必须发生的动作交给模型记忆和自觉；把 Skill/Agent 当运行时资源来设计**——入口清楚、路由短、权限硬、验证可重复。
