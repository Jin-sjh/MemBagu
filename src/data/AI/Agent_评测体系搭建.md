# 评测体系搭建

## 【问题】
AI Agent 的评测体系跟传统软件测试有什么本质区别？一个完整的 Agent 评测体系应该拆成哪几个环节？

## 【回答】
传统软件测试是「输入 A 一定得到 B」的**确定性断言**，而 Agent 的输出是**非确定的、多步骤的、跟环境交互的**，没法用断言一刀切。所以 Agent 评测跟传统测试不是同一个逻辑。

完整的评测体系拆成五个环节，串成一条链路：**目标定义 → 数据集构建 → 打分机制 → 失败分析 → 生产闭环**。

## 【问题】
评测目标应该怎么定义？「测模型」和「测产品」有什么区别？

## 【回答】
最基础的区分是**测模型**与**测产品**：

- **测模型**：选型阶段做的事，用通用 benchmark 回答「这个模型够不够强」；但模型在通用榜跑分高，**不代表**它在你的场景里表现好。
- **测产品**：测你的整个系统（**prompt + 检索 + 工具调用**），回答「能不能完成具体业务任务」。

还要想清楚「为什么测」，不同目的对体系的要求完全不同：

| 目的 | 特点 | 要求 |
| --- | --- | --- |
| **迭代** | 快速反馈 | 可以粗糙 |
| **上线准入** | 高置信度 | 要设明确门槛 |
| **生产监测** | 轻量可持续 | 不能太重 |

**一套体系试图同时满足这几个目标，往往哪个都做不好**；很多团队分数与产品质量相关性低，问题几乎都出在评测目标不明确。

## 【问题】
测试数据（数据集）应该从哪来？不同来源的质量如何排序？

## 【回答】
按质量从高到低排序：**真实失败记录 > 手工构造 > 合成数据**。

| 来源 | 质量 | 说明 |
| --- | --- | --- |
| **真实失败记录** | ⭐⭐⭐ | 每天用产品时遇到的问题，质量最高 |
| **手工构造** | ⭐⭐ | 针对关键行为一条条写，覆盖最在意的场景 |
| **合成数据** | ⭐ | 用模型从真实样例扩写，量大但质量一般 |

大多数团队跳过前两步直接用合成数据或公开 benchmark，但**公开 benchmark 测的是通用能力，不是你的产品，照搬过来的分数没有意义**。

测试用例要**按能力打标签**（如「多轮对话」「工具调用」「检索」），而不是按来源分类，这样分析时能快速定位是哪个能力出了问题。

## 【问题】
打分（评分）机制应该怎么选？代码打分、模型打分、人工打分的优先级是什么？

## 【回答】
优先级原则：**能用代码判的用代码，代码判不了的用模型，最后才上人工。**

| 手段 | 适用场景 | 优势 | 局限 |
| --- | --- | --- | --- |
| **代码打分** | 格式正确性、关键词出现、JSON 解析、数据库状态检查 | 快、便宜、可重复 | 只能判确定性结果 |
| **模型打分** | 语气是否合适、信息是否完整、有没有误导用户 | 可规模化 | 有偏见风险、可靠性存疑 |
| **人工打分** | 黄金标准 | 最可靠 | 贵且慢 |

一条关键原则：**每个质量维度用一个独立的评估器，不要把多个维度揉成一个总分**。例如客服 AI 的「好回答」要同时做到准确、有温度、不啰嗦、符合规定——如果把这四件事加权成一个分数，永远不知道分数变化是哪个维度驱动的；**分开打，才能定位问题**。

## 【问题】
什么是 transcript？为什么失败分析强调「读 transcript」比看分数更重要？

## 【回答】
**transcript** 指 Agent 一次任务从头到尾的完整执行记录——它每一步想了什么、调了什么工具、拿到了什么结果、怎么决定下一步，全部记下来的那份「日志」。它是 Agent「干活的完整过程」，不只是最后那句回复。示例：

```
用户说：帮我查一下订单 #1234 的状态
↓Agent 思考：需要调用订单查询接口
↓Agent 调用工具：query_order("1234")
↓工具返回：{"status": "shipped", "items": [...]}
↓Agent 思考：订单已发货，可以告诉用户了
↓Agent 回复：您的订单已发货，预计...
```

**分数告诉你哪里不对，transcript 才告诉你为什么。** 一个场景通过率低，原因可能是 prompt 问题、检索召回错误、工具调用顺序乱了——这些完全不同的问题，分数看起来却一样，只有读真实对话记录才能找到根本原因。

实操建议：每次做重大改动，花 30 分钟手动看 20–50 条输出，边看边记哪里不对，读到新输出不再带来新的失败模式再归纳类型；**针对真实失败写 eval，不要凭空想象可能出什么问题**。经验法则：**如果某个场景通过率是 0%，先不要怀疑系统，几乎可以确定是评测本身出了问题**。

## 【问题】
什么是评测的「生产闭环」？为什么评测的终点不是报告？

## 【回答】
离线评测只能测到你**提前想到的东西**，上线一定会遇到离线里没想到的问题（用户会怎么用、会问什么奇怪问题、在什么意想不到的场景翻车，提前猜不全）。所以评测不能止步于离线报告，得跟生产环境接上，形成一个转不停的轮子：

1. **线上抓**：用户在真实使用中遇到的失败要能看到（点赞点踩、投诉、对话突然中断、任务完成率掉下来）。
2. **攒下来**：把有代表性的失败 case 捞出来，扔进测试集。
3. **跑评测**：下一轮迭代用更新后的测试集评，看问题修没修好。
4. **再上线**：改完 → 评测通过 → 上线 → 又发现新失败 → 回到第一步。

最容易忽略的是第一步「线上抓」，需要两类「探头」挂在线上：**用户信号**（点赞点踩、投诉、会话中途放弃）和**自动巡检**（拿一小部分实时流量自动跑评估，确认线上表现和上线前没有明显掉档）。

经验：**不是每个线上问题都值得建专门的评估器**——改一次就好的直接修；但如果同一类问题反复冒出来，就该沉淀成一条常驻评估规则，下次再出现时评测先替你拦住。

## 【问题】
AI Agent 评测有哪些常见的踩坑与经验法则？

## 【回答】
① **不要上来就搭大而全的评测平台**：早期靠手测和直觉能走很远，临界点通常是系统开始放量、用户反馈「改完之后变差了」、团队不知道改了有没有变好；没到这个点先把产品做出来。

② **真实失败是最好的测试数据**：从真实使用攒几十条失败 case，比凑 1000 条合成数据更有价值。

③ **同一个任务多跑几次**：Agent 的非确定性意味着「跑了一次通过」几乎没有统计意义，**至少跑 5–10 次，看通过率，而不是单次结果**。

④ **评的是系统，不是模型**：同一模型 harness 不同，成绩可差出几十个点；评测报告必须记清楚用的是哪套 harness。

⑤ **分数不等于质量**：分数与产品质量相关性很低时，问题几乎都出在最前面——评测目标不明确，跑出来的分数根本没拟合你真正想要的效果。

⑥ **评测和训练正在变成同一件事**：涉及模型训练或微调时，设计足够好的评估器本质上就是一个**奖励函数**，你为评测写的 rubric 和 grader 可以直接驱动下一个模型版本的训练方向。

核心一句话：**别追求完美，追求「转得起来」**——轮子转起来了，哪怕第一版粗糙，也会自己越磨越好；轮子没转起来，再漂亮的评测报告也只是一张静态照片。
