# SPEC 为什么会失败

## 【问题】
SPEC 驱动开发是什么？它落地时常见的失败模式有哪些？

## 【回答】
AI 辅助编码正在改变工作方式，开发者重心从**逐行实现代码**转向**更高层次的设计与指导**。SPEC 驱动开发正是**将设计意图精确传达给 AI 的关键方法**。但把新范式成功落地并非易事，实践中常见**五个典型的失败场景**：

1. **背景缺失**——缺少项目级指导原则的 SPEC。
2. **评审缺位**——对 AI 生成的 SPEC 缺乏严格审查。
3. **过度设计**——在 SPEC 阶段陷入「分析瘫痪」。
4. **规约与实现解耦**——在「意外」产生时绕过 SPEC 直接修改代码。
5. **流程形式化**——为赶进度而牺牲 SPEC 流程。

## 【问题】
失败点 1「背景缺失」：为什么直接让 AI 写 SPEC、不给项目背景会失败？正确做法是什么？

## 【回答】
**失败原因**：团队只给 AI 一句简单指令（如 `/speckit.specify`）就期望它自动理解项目背景，这种做法**混淆了 AI「搜索信息」和「理解知识」两种能力**——SPEC 工具通过 `codebase_search` 只能告诉你「代码里有什么」，**无法告诉你「当初为什么要这么设计」**。大量隐性知识（业务目标、过去技术选型的原因、重要设计决策如为何用软删除、团队开发规范如日志格式）无法直接从代码里看出；基于不完整信息的 SPEC 只会被 AI **忠实地变成同样有问题的代码**，最终让开发者误以为「SPEC 模式没用」。

**正确策略：先定好规则，再开始干活**。为任何功能编写 SPEC 之前，先建立项目的「指导原则」（spec-guide，类似 speckit 里的 `constitution.md`），作为团队共识，记录代码本身无法表达的信息，至少包括：

- **产品与业务背景**：项目是做什么的、核心功能是什么。
- **技术设计原则**：用什么技术栈、架构怎样、过去的关键决策。
- **结构与开发规范**：代码目录组织、文件命名、API 风格、测试要求等。

编写这份文档本身就是一个系统学习过程，可让 AI 扮演**提问和补充**的角色帮你完善。只有当这份基础文档足够清楚、为 AI 提供稳定上下文后，才能真正开始高效可靠地编写 SPEC。

**工具实践**：用 `/speckit.constitution` 初始化项目「宪法」constitution.md，随后可重复运行补充内容，如 `/speckit.constitution 增加测试规范: mock 文件通过 go:generate mockgen 生成，并与测试代码放在同一个 package 文件夹下面`。

## 【问题】
失败点 2「评审缺位」：开发者把 AI 当架构师、不审查 AI 生成的 SPEC 会怎样？「审阅-挑战-修正」循环如何操作？

## 【回答】
**失败原因**：开发者对业务或技术不熟时，容易搞错角色——把自己当**提需求的**、把 AI 当**解决所有问题的架构师**，希望 AI 自动补上自己不懂的地方。结果 AI 可能生成一份看起来很详细但**充满逻辑漏洞**的 SPEC，开发者未严格审查就采纳，AI 就精确地把错误方案变成错误代码，最终得出「SPEC 不可靠」的结论。

**正确策略**：角色反过来——开发者必须承担**架构师责任**，把 AI 当作高效辅助工具；AI 生成的初版 SPEC 只是**讨论的起点**，而不是最终指令。整个流程遵循「**审阅-挑战-修正**」循环：

1. **仔细审阅**：把初版 SPEC 当作需要严格检查的草稿。
2. **发现问题**：主动找出描述模糊的地方、逻辑漏洞、自己不懂的技术点。
3. **交互式学习**：模糊点通过追问明确需求；逻辑漏洞与 AI 讨论其他方案看哪个更可靠；技术盲区当作学习机会补短板。

通过循环把粗糙草案迭代成**逻辑清晰、细节明确**的 SPEC。SPEC 的真正价值在于提供一个框架，通过与 AI 的反复沟通**系统思考并加深对问题的理解**。

**工具实践**：首推 `/speckit.clarify` 做澄清，可指定关注点（如「哪些模块需要解耦？目标测试覆盖率是多少？如何 mock tRPC 服务？」）；也可用**反问模式**挖掘隐性上下文与潜在风险：「生成一份问题清单，帮助我思考其中未明确说明的方面」。

## 【问题】
失败点 3「过度设计」：SPEC 阶段的「分析瘫痪」是什么？如何通过拆分和追求确定性解决？

## 【回答】
**失败场景**：陷入宏观与微观的**双重矛盾**——宏观上担心未来变化、想设计应对所有情况的「完美」架构，导致设计阶段无限拖延；微观上规范描述又充满「优化性能」「返回必要信息」等**模糊话术**，人大概能懂，但需要精确指令的 AI 无法执行，生成的代码充满不确定性，**SPEC 失去作为验收标准的作用**。

**正确策略**：通过**拆分**和**追求确定性**解决：

1. **拆分 SPEC，把大事化小**：把大需求不断拆解，直到每个子 SPEC 满足两个条件——**目标单一明确**、**能在很短时间（如半天到一天）内完成**，避免宏观过度设计，始终聚焦小的、可交付的功能点。
2. **追求确定性，消除模糊**：SPEC 必须是可执行、可验证的，可用「**角色扮演测试**」检查质量：
   - **需求（requirement.md）**：一个测试工程师只看它，能否写出包含边界和异常情况的完整测试用例？必须有**可量化的标准**。
   - **设计（design.md）**：一个下游开发者只看它，能否直接开始对接而不需要再问问题？API 约定、数据结构、交互协议必须**精确**。
   - **任务（tasks.md）**：一个不了解背景的程序员只看它，能否在几分钟内开始写代码？每个任务都应**独立、具体、可操作**。

**工具实践**：基于 tapd 需求做初步分解（需 tapd MCP），如「请分析 tapd 需求并将其拆分为多个独立的子需求」。

## 【问题】
失败点 4「规约与实现解耦」：为什么「遇到意外直接改代码」是 SPEC 实践中最致命的错误？变更应如何走流程？

## 【回答】
**失败原因**：当出现需求变更、设计遗漏或严重 BUG 时，团队为了图「快」绕过规范直接改代码，抱着「先改代码、有空再补文档」的想法。**一旦第一个补丁直接打上，代码就和 SPEC 不一致了**；随着改动越积越多，SPEC 很快就变成没人维护的过时文档，SPEC 驱动开发的基础不复存在，**之前所有投入全部白费**。

**正确策略：把变更本身也当作一个需要通过 SPEC 管理的需求**——遇到任何意外都先调整 SPEC，而不是直接改代码：

1. **评估变更影响**：先判断 SPEC 执行到哪一步；若正在执行任务（Tasks），**立即停下**，避免基于旧规约产生更多无用代码。
2. **选择变更路径**：
   - **继承式修改**：变更只是局部调整或修复时，在原 SPEC 基础上修改扩展，**保留历史版本**、清楚标出改了什么，形成**可追溯的变更记录**。
   - **开启新 SPEC**：变更导致核心目标完全改变时，果断开启全新 SPEC 重新设计，并**明确废弃旧的 SPEC**。
3. **同步更新**：若变更引入新的设计原则或技术（如新加消息队列），必须**同步更新项目「指导原则」（Constitution）**，让顶层设计保持最新。

管理变更的核心思想：**保护和复用之前在规约上花费的精力**，通过规范变更流程把所有改动纳入 SPEC 管理，确保 SPEC 始终是项目的「**活文档**」。

**工具实践**：用 `/speckit.analyse` 自动检测文档中的冲突和模糊点（生成一致性报告）并据结果修正；对执行到一半的 tasks.md 可发终止声明 prompt：「结合新的需求变更描述，请对 Tasks.md 文档执行终止操作，并生成更新后的完整内容」。

## 【问题】
失败点 5「流程形式化」：赶进度时牺牲 SPEC 流程为什么反而更慢？紧急需求下正确思路是什么？

## 【回答】
**失败原因**：交付时间突然缩短时，规范的流程最先被放弃，团队误把写 SPEC 和评审当成多余流程负担，走「捷径」直接让 AI「快速搞定」。这种**因恐慌而放弃规则**的做法短期看似更快，但大量未经充分设计和评审的 AI 代码会在**集成阶段集中爆发问题**，导致更长的调试和返工，**想快也快不起来**。

**正确思路：把 SPEC 看作高压下的决策工具，而不是开发的累赘**——紧要关头的价值不在「写得更快」，而在「决策更准」：

1. **用 SPEC 量化影响，不做口头承诺**：结构化 SPEC 让你快速评估变更影响和工作量，拿出事实沟通，如「增加这个功能需要修改 3 个模块，预计增加 2 人天」，而不是凭感觉说「可能来不及」。
2. **用 SPEC 做取舍，而不是全盘接受**：时间不够时，在需求层面与产品负责人**有策略地砍掉或推迟低优先级功能**，是主动的范围管理；好过在代码层面硬扛所有需求导致质量彻底失控。
3. **用 SPEC 拆解任务，实现高效并行**：拆分得当、任务独立的 `tasks.md` 让任务可分给不同的人甚至多个 AI Agent，因为**任务间依赖和边界已定义清楚**。

**核心原则：不要自己加速，而是驱动 AI 加速；不要打破规则，而是在规则内寻找最优路径。**

| 错误逻辑（执行者） | 正确逻辑（指挥者） |
|---|---|
| 「没时间写文档，直接改代码」 | 「用 30 分钟规划，节省 2 天返工时间」 |
| 「AI 生成什么就用什么」 | 「用提示词驱动 AI 生成最优方案」 |
| 「先实现功能，规范以后再说」 | 「用 Urgency Mode 在规范内快速实现」 |
| 「测试太慢，上线后再补」 | 「Test-First 确保一次成功」 |

**工具实践**：`/speckit.plan` 阶段强制简化实现（「需求 URGENT，实现求简求快，忽略非关键问题，除非必要否则配置都用默认值」）；`/speckit.tasks` 阶段最小化任务、最大化并行（「最小化任务数量、最大化任务并行度，并为每项任务提供大致时间估算」）。

## 【问题】
对 SPEC 驱动开发应建立哪些正确认知？SPEC 与 Vibe Coding 是对立关系吗？

## 【回答】
四点关键认知：

1. **SPEC 是保证 AI 编码质量的「规矩」**：别把它看成简单任务列表，它是一套**保证代码质量的流程和标准**——前期定好规则、中期严格评审、后期管理好变更，就能确保 AI 生成的代码靠谱。
2. **SPEC 不是银弹，它也有自己的问题**：写详细文档**很费 Token**；现在**缺少好用的管理工具**，很多事靠人自觉；流程本身也容易导致**想得太多不敢动手**，或一忙起来团队只是**形式上遵守**标准。
3. **想用好就得在实践中摸索和迭代**：这套方法论及工具（如 speckit）都还在快速变化，必须**边用边总结**、跟上新工具新方法的节奏。
4. **SPEC 与 Vibe Coding 并非对立，而是互补**：探索新技术栈、摸索新业务、快速验证产品想法时，Vibe Coding 的自由探索依然不可或缺；关键是要**有意识沉淀 Vibe 过程中的成功经验和踩坑教训**——先沉淀为具体规范（Rules），再用 Rules 指导生成更靠谱的 SPEC，把自由探索的成果变成未来规范开发的基础。
