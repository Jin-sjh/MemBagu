# 知识复利与知识治理

## 【问题】
什么是"知识复利"？Spec-First 对它的核心判断是什么？0→1→N 分别指什么？

## 【回答】
核心判断：**知识复利不是把一次经验永久保存，而是让经过验证的事实和方法，在明确来源、版本、权限与适用范围下进入下一次 Context，并接受新现场的再次检验**。

0→1→N 定义了知识的演进状态：
- **0**：现场信号还没有成为知识。
- **1**：经过 Evidence 与 Gate，形成第一份可信知识。
- **N**：被后续任务按需装配、验证、修正、降级或淘汰。

## 【问题】
为什么"写下来了""能搜到""很多人复用"都不等于知识有效？团队反复踩坑的真正缺失是什么？

## 【回答】
- **"写下来了"只证明内容存在**：内容存在不代表能被正确使用，缺统一身份和来源。
- **"能搜到"只解决发现，不解决信任**：检索不自动判断有效性。例如"支付回调必须重试三次"可能是正式规范、临时绕过、已废弃设计，单凭搜到无法区分。
- **"很多人复用"也不等于知识正确**：错误做法同样可以高频复制。
- **真正缺失的是知识的生命周期**：必须能回答四个问题——它从哪里来？凭什么相信？在什么范围内使用？何时更新、降级或撤回？

## 【问题】
第一步不是"沉淀知识"，而是区分 Signal、Evidence 与 Knowledge。三者如何区分？Candidate 又是什么？

## 【回答】
- **Signal 只是值得关注的变化**：如 Bug 描述、群聊反馈、指标异常，只触发调查，本身不是知识。
- **Evidence 把观察绑定到对象、版本和时间**，至少包含字段：
  `sourcework_id / run_id`、`contract_version`、`repo / commit / artifact`、`environment`、`observed_at`、`scope`、`result`。
- **Candidate 是流程状态，不是可信等级**：进入 Candidate 只表示"值得治理"，不表示"已经可信"。
- **Knowledge 必须能够被反驳和更新**：应保留当前结论、来源、可信等级、适用范围、版本、Owner、生效与失效条件，以及被哪条新 Evidence 更新。

## 【问题】
什么是 K1-K4 统一可信语言？各自能怎样使用、不能怎样使用？

## 【回答】
- **K1 已验证事实**：可追溯到源码、正式规范、Accepted Evidence，有版本边界。
- **K2 已验证经验**：经真实交付验证的 RCA、方案等，回答"某类条件下怎样做可靠"。
- **K3 候选知识**：未过 Gate 的 AI 摘要、外部材料等，显式标记为线索。
- **K4 推断内容**：模型形成的解释/假设，**不得冒充企业事实**。

可信等级决定使用资格：

| 等级 | 可以怎样使用 | 不能怎样使用 |
|------|--------------|--------------|
| K1 | 作为有版本边界的任务事实 | 脱离版本和权限永久沿用 |
| K2 | 作为有适用范围的推荐方法 | 自动变成全局强制规则 |
| K3 | 作为调查、澄清和评审线索 | 直接改变权威工件和状态 |
| K4 | 作为待证伪的推断 | 冒充事实或自动驱动执行 |

## 【问题】
组织知识至少包含哪两条不同的生产链？为什么不能混成一份万能文档？

## 【回答】
- **代码知识回答"系统现在是什么"**：以已发布 `master` 为基线生成全局代码知识。
- **交付知识回答"团队怎样改变这个系统"**：来自 PRD、方案、测试、RCA 等。
- **两条链不能混成一份万能文档**：需保留各自真相源、版本和 Owner。
- **全局代码知识不能提前相信开发分支**：只在合并发布后基于 `master` 增量更新。

## 【问题】
0→1：第一份可信知识怎样产生？Archive Gate 是什么？

## 【回答】
- **现场经验先留在当前 Workspace**：写入 `solutions/`，至少包含问题与触发条件、根因、修复、Evidence、关联 commit。
- **节点 Gate 先判断内容质量**：各节点准出后，归档阶段读取权威版本。
- **Archive Gate 决定能否进入长期知识**：在 `Archive Running` 中校验指纹、来源、权限、路由等，全过才进 `Archived`。
- **第一份知识必须保留可追溯身份**，字段包括：`source_work_id`、`source_workspace_revision`、`contract_version`、`archive_id`、`document_version / source_path / content_digest`、`Owner / archived_at`、`repo / commit / PR / release_id`，以及适用产品、模块、场景与权限。

## 【问题】
1→N：复用不是复制 N 次，而是持续验证。怎么理解？

## 【回答】
- **下一次只装配相关知识**：按 Work Object、角色、阶段装配 Context Snapshot。
- **复用必须产生新的 Evidence**：新任务产生 Build/Test/Review 结果来验证旧经验。
- **不匹配不是失败，而是知识更新信号**：记录差异，进入更新/降级/撤回。
- **N 的价值来自复用后的修正**：知识复利的本质是对适用边界的理解更精确。

## 【问题】
知识进入 Context 必须经过"装配"而不是"倾倒"，具体怎么做？

## 【回答】
- **先由任务定义信息需求**，而不是先把全库倒进上下文。
- **再按权威性和时效过滤**：K1/K2 进主输入，K3/K4 进待确认线索。
- **最后冻结为本次 Snapshot**：执行中 Contract 变化则标 `Stale`/`Blocked` 并重装配。
- **引用不是装饰，而是回到事实的路径**：每条引用都应能回溯到具体来源。

## 【问题】
Knowledge、Rule、Skill、Test、Template 各固化什么？主要区别？

## 【回答】
- **Knowledge** 固化事实、决策、经验和适用范围；**Rule** 固化不可突破的稳定约束；**Skill** 固化可执行的专业方法；**Test** 固化可自动验证的不变量；**Template** 固化稳定的工件结构。

| 资产 | 固化什么 | 主要准出条件 |
|------|----------|--------------|
| Knowledge | 事实、决策、经验和适用范围 | 来源与 Evidence 可追溯 |
| Rule | 不可突破的稳定约束 | 跨任务稳定且违反代价明确 |
| Skill | 可执行的专业方法 | 多次复用有效且失败出口清楚 |
| Test | 可自动验证的不变量 | 能稳定复现并防止回归 |
| Template | 稳定的工件结构 | 多场景字段一致且不夹带结论 |

## 【问题】
低成本治理怎么做？怎样避免变成更大的文档官僚主义？

## 【回答】
- **复用交付过程已有工件**，不另建一套运动。
- **自动化处理机械判断**，让人只处理冲突。
- **Owner 负责边界**。
- **从高价值闭环开始**，如故障 RCA。
- 反方（官僚主义）成立的三条件：沉淀分离、只存不删、只统供给不验结果。
- **治理最小必要集合**：来源、版本、Owner、可信等级、适用范围、权限、Evidence、更新条件。
- **最低成本让治理贴着事实发生**：从 Git/测试/发布系统读，人只处理冲突，而不是把治理做成独立文档生产。

## 【问题】
怎样判断"知识复利"真的发生了？

## 【回答】
用五个信号衡量：
1. **看从发现到可行动的时间** 是否缩短。
2. **看重复问题是否减少**。
3. **看知识被使用后是否产生 Evidence**。
4. **看更新和撤回是否及时**。
5. **看能力是否跨人和跨项目迁移**。

关键强调：若第 3 问（复用后是否产生新 Evidence）无答案，只完成了"发布"而**未形成复利**。

## 【问题】
完整链路是怎样的？用哪十二个问题可以自检知识是否真能反哺下一次交付？

## 【回答】
完整链路：**现场 Signal → 现实 Evidence → Knowledge Candidate → K1/K2 准出 → Archive Gate → 按角色装配进下一次 Context Snapshot → 新任务验证 → 更新/降级/撤回/再归档**。

十二问自检：① Signal/Evidence/Candidate 还是已准出知识？② K1-K4 归属与使用资格？③ 能否追溯 Work Object/Contract/代码版本/Owner？④ Evidence 证明什么、不能证明什么？⑤ 适用产品/模块/环境/版本是否明确？⑥ 应进 Knowledge/Rule/Skill/Test/Template 哪类？⑦ 是否保存原始工件而非仅 AI 摘要？⑧ 是否完成重复/冲突/权限/时效检查？⑨ 下次按角色装配还是倾倒全库？⑩ 复用后是否产生新 Evidence 验证修正？⑪ 不适用时能否更新/降级/撤回并定位影响？⑫ 衡量减少返工还是仅统计文档量？（若第⑩问无答案，只完成"发布"未形成复利。）
