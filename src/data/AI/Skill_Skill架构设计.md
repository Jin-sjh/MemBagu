# Skill 架构设计

## 【问题】
用软件工程「分层解耦」思路设计领域知识密集型 Skill（K 池 / A 池 / E 池三层知识池）为什么会踩坑？

## 【回答】
把 Skill 拆成 K（Knowledge 业务知识）、A（Analysis 分析方法）、E（Expression 输出）三个独立知识池、层间用标准化接口契约通信，看似职责分明，但 V1 上线不到两周就暴露三个结构性问题：

- **上下文爆炸**：一个行业的知识被打散到多个子目录，一次分析要跨三层拉十几个文件，context 窗口装不下。根因是知识碎片化——LLM 需要在**一个视野内看到连贯的行业知识**才能做准确推理，而分层架构把它们分散在几十个文件里。
- **过度工程化**：接口契约、版本解析器、schema 校验在传统软件里是好实践，但 LLM 不是微服务，它不需要序列化的数据包在层间传递，它需要在**一个 context 里看到足够信息做推理**。
- **流水线假设不成立**：K→A→E 假设信息单向流动，但真实分析是交织的——分析到一半要补知识，输出时发现结论要修正，流水线切断了这种交互。

核心认知转变：**LLM 的知识组织范式和传统软件架构根本不同**。传统软件追求模块化、接口标准化、关注点分离；但 Skill 里分层的目的是让模型在需要时能拿到完整上下文，这与微服务「每个服务只看自己的数据」正好相反。Skill 的能力上限不取决于模型，取决于你喂给它的**知识架构**。

## 【问题】
Skill 架构演进到 V2 做了什么重构？为什么需要「路由层」，它是怎么工作的？

## 【回答】
V2 围绕三条原则重构：**知识收拢**（一个行业的所有知识收拢到一个独立文件，加载一个文件即得全貌）、**按需加载**（不在启动全量灌入，按用户问题动态决定加载哪些文件）、**做减法**（砍掉接口契约、版本解析器、schema 校验，文件从 100 多个精简为 40 多个）。

按需加载的前提是可靠的**路由层**。入口从「三层 orchestrator」变为单一路由入口，承担三级职责：

1. **域路由**：判断用户问的是哪个业务域（不同域有不同分析框架和指标体系）。
2. **行业路由**：在域内映射到具体行业，通过关键词匹配和歧义消解规则定位行业知识文件。
3. **问题分类**：判断问题类型——「是什么」（知识类）/「为什么」（分析类）/「怎么做」（方法论类），决定加载哪些 reference 文件。

路由层真正有技术含量的是**处理歧义和兜底**：关键词重叠时先看上下文有没有行业锚点，有就走行业路由，没有走横向职能，还判断不了就问用户，完全没命中则加载通用兜底文件。本质是用路由逻辑换 context 效率——用少量路由 token 换取大幅减少无效知识加载，这是** token 经济性的第一个体现**。

## 【问题】
V2 的「知识收拢」很快又出问题了，V3 为什么要把知识按变更频率分层（稳定 / 时效分离）？

## 【回答】
因为收拢后行业文件越写越胖：经营框架、核心公式是稳定的，但季度策略、竞争格局、运营抓手、关键事件持续变化，全追加进同一个文件，部分行业文件膨胀到数百行，维护者翻找困难、更新时不知道该改什么。

V3 的核心决策是**按变更频率分层**：

- **稳定知识（低频）**：经营框架、核心公式、指标定义、业务模式，可能一两年才调一次。
- **时效知识（高频）**：策略打法、竞争格局、运营抓手、关键事件、口径规则，每季度甚至每月在变。

两者混在一个文件会导致：更新时效内容时容易误改稳定内容；文件膨胀让维护者看不过来、不知道哪些该改。V3 的拆法：

- **瘦行业文件（稳定层）**：每行业一个文件，只保留低频内容，精简到百行级，一眼看全貌。
- **主题文件（时效层）**：按**知识主题而非行业**组织高频内容（如所有行业的策略打法在一个主题文件，内部按行业分段）。

直接收益：写入效率（更新某类时效知识只开一个主题文件逐段改，不用翻几十个行业文件）、维护清晰度（行业文件瘦身超 60%，10000+ 行压缩到 3000+ 行）、生命周期独立（策略刷新只改主题文件，经营框架调整只改行业文件）。

关键洞察：**写入和读取的最优粒度不一样**——维护者想「一个文件改完所有行业」（写入效率），LLM 想「只看一个行业的段落」（读取 / token 效率）。同一个物理文件通过**分段加载**同时满足两边：单次请求只加载目标行业的那一段，token 控制在几百以内。

## 【问题】
分析方法层（A 池）如何做减法？从 20+ 个方法压缩到 9 个的关键做法是哪些？

## 【回答】
V1 的 A 池平行陈列 20+ 个方法，导致路由错误频发（方法边界模糊，LLM 选错）且消耗推理资源。V2 压缩到 9 个，做了三件事：

1. **合并同类项**：多个细粒度方法合并为一个大类的子场景。例如因果推断领域的 DID、RDD、PSM、合成控制法，对 LLM 都是「归因问题」的不同手段——合并后先判大类再内部选具体方法，一级选项从 20+ 降到 9。
2. **建立路由优先级**：9 个方法有标准顺序——异常检测 → 归因 → 趋势 → 预测，LLM 顺优先级走，遇到匹配信号就停，不做全局选择题。
3. **后置触发机制**：在分析框架知识文件里预埋触发标记，模型分析到某维度、发现特定模式（如「供给数量上升但单位产出下降」= 典型结构迁移信号）时才按需加载对应方法文件。决策点从「分析前选方法」变成「分析中遇到问题再加载」。

核心原则：**让 LLM 的每一步决策都是少选项、强信号**。从 token 经济性看，20+ 方法全量预加载 vs 9 个按信号触发按需加载，token 占用差距是数量级的。

## 【问题】
方法压缩到 9 个后，关键词仍有重叠，「选项少」就够了么？这跟 NLU 意图识别有什么关系？

## 【回答】
不够。减少选项只是第一步，**消除选项之间的歧义是第二步**。例如用户说「结构变化」可能触发分层分析（识别不同群组差异）或结构迁移分析（衡量结构占比变化对总指标影响），二者关键词重叠。

做法是给每对易混淆方法设计**消解规则**，例如：

- 关注「结构占比变化对总指标的影响有多大」→ 结构迁移分析
- 关注「哪些个体 / 群组贡献最大」→ 分层分析
- 两个信号同时命中 → 默认走结构迁移（更聚焦因果归因），分析中按需追加分层

类比 NLU 意图识别：**意图数量越少不一定越好，意图之间的边界越清晰才越好**。减少选项降低选错概率，消解歧义才能从根本上稳住路由准确率。

## 【问题】
输出表达层如何从 20+ 模板压缩为 4 类框架？为什么作者强调「不要用 few-shot 示例」？

## 【回答】
输出层从 20+ 模板压缩为 **4 类输出框架**：监控 / 诊断 / 预测 / 汇报。设计思路是**约束结构，释放内容**：

- **只定义一级骨架，二级让模型自由发挥**。例如诊断类一级骨架固定：诊断结论 → 定位路径 → 归因分析 → 建议行动；每步具体表述由模型按问题自行组织。比刚性模板灵活，又比完全不限制可控。
- **通用规则抽取**：置信度声明、数据约束说明、受众适配规则从每个模板重复段落中提取，只写一次，所有输出类型共享，改一处全局生效。
- **受众适配内置**：给高管看结论和数字，给中层看趋势和行动项，给执行者看操作细节，一套框架覆盖。

关于 few-shot：很多人第一反应是塞几个示例「参照这个格式输出」，但作者试过效果不好——模型会**过拟合到示例的表面形式**（用词、句式、段落长度都在模仿），而非学到结构约束，换行业换问题类型就跑偏。「约束骨架但不约束填充内容」的框架式设计比 few-shot 更稳定：告诉模型「必须有哪些部分」，但不告诉「每个部分怎么写」，给模型留出按场景灵活调整的空间。

## 【问题】
给 LLM 设计 Skill 架构，有哪些「反直觉」的经验？

## 【回答】
方法层（做减法到 9 个方法）和表达层（做减法到 4 类框架）共同指向一组反直觉经验，可总结为一句话：**Skill 架构设计是找到「最少的约束产生最稳定的输出」的那个平衡点——给 LLM 的架构要做减法，给 LLM 的知识要做加法。** 即对架构（流程、选项、模板）要不断收敛，对知识（行业框架、指标体系、时效内容）要持续充实，二者方向相反却互补。

## 【问题】
什么是「知识腐烂」（Knowledge Decay）？为什么它比 Skill「功能不够」更致命？

## 【回答】
Skill 上线只是起点。代码逻辑不会自己变，但**业务知识会随时间过期**——口径变更、组织调整、策略刷新、竞争格局变化、行业政策出台。若没有系统化更新机制，Skill 输出质量会随时间持续下降。

它比「功能不够」更致命，原因在于：功能不够，用户会反馈「能不能支持 XX」；**知识过时，用户看到的是「结论不对」「口径对不上」「建议和现在打法矛盾」，但他们不会告诉你「是因为知识过时了」，只会默默离开不再使用**。代码可以 CI/CD，知识腐烂却是传统软件不存在、LLM 应用特有的问题。

## 【问题】
Skill 的知识保鲜机制有哪些？「评测驱动的更新闭环」和「反馈自演进」分别是什么，二者什么关系？

## 【回答】
两套互补机制，解决同一个问题——让知识保鲜：

**评测驱动的更新闭环（维护者主动巡检，把知识当代码管）**，六步：

1. **评测（Eval）**：定期用标准化测试题集验证输出质量，覆盖各行业 / 问题类型 / 场景，产出结构化差距清单。
2. **诊断（Diagnose）**：基于差距清单结构化分析——错误属于哪个知识模块、影响范围、优先级、预期提升。
3. **登记（Register）**：最易被忽略但最关键。修改前先登记即将变更的事实：旧值、新值、在哪些文件中出现过。因为同一业务事实可能被多处引用，只改一处会留下内部版本不一致，对分析类 Skill 致命。
4. **修改 + 校验（Review）**：按计划改完跑校验脚本，扫描所有知识文件检查旧值已清除、新值已到位、禁用表述无残留，零错误才允许提交。
5. **复测（Re-eval）**：跑同一套评测题验证分数提升；没提升或出现回归则回到诊断。

理念与代码 CI/CD 一致，只是管理对象从代码变成知识。

**反馈自演进（日常免疫系统，实时）**：设计静默反馈采集机制，对话中自动识别用户纠错（「不对，应该是 XX」）、追问补充、重复提问、放弃对话等信号，采集不打断节奏、用户无感知。反馈先进**候选区**观察（单次反馈可能是个例，避免一次纠错就改坏行为），同一类反馈被多次确认才晋升到正式区，命中足够高最终从运行时记忆**固化到正式知识文件**变成永久知识。重要约束是**弱模型友好**：信号识别、去重、晋升决策全用关键词匹配和规则判断，不依赖 LLM 语义理解，避免和主任务抢 context 推理资源。

二者关系：评测闭环是**定期体检**（系统化、全面、有时期）；反馈自演进是**日常免疫系统**（实时、精准、覆盖有限）。互补缺一不可。大部分 Skill 失败不是架构不好，而是上线三个月后知识过时，既没人定期评测，也没机制从用户行为捕获退化信号。

## 【问题】
这篇实践最终提炼的「六条 Skill 架构设计原则」是什么？

## 【回答】
1. **收拢优于碎片化**：一个分析场景需要的知识收拢到尽量少的文件。LLM 需要连贯上下文做推理，不是碎片化数据包拼装。
2. **按变更频率分层**：半年不变的知识和每月在变的知识不要放一起，变更频率不同的内容混合存储，维护成本指数级增长。
3. **选项少、信号强**：路由选择、方法选择、输出选择都做减法，每步决策都应低歧义，选项越少模型选对概率越高。
4. **约束结构，释放内容**：定义骨架让模型填充，比穷举模板更稳定更灵活——告诉模型「必须有哪些部分」，不告诉「每个部分怎么写」。
5. **知识保鲜靠机制不靠人**：评测、登记、校验、复测，没有更新机制的知识是有保质期的。
6. **Token 经济性是架构的硬约束**：每个设计决策都要回答「消耗多少 context 窗口」。收拢减少跨文件加载开销，按需加载只占用必要 token，主题文件按行业分段而非全量加载精确控制 token 粒度。Skill 架构本质是在有限 token 预算内最大化知识密度。

## 【口诀】
软件思维会踩坑（上下文爆炸+过度工程），收拢按需加路由；稳定时效要分离，选项少来信号强；约束骨架放内容，知识保鲜靠机制；架构做减法、知识做加法，Token 经济是硬约束。
