# Harness 可观测性

## 【问题】
为什么 Agent 在 Demo 阶段能跑通一次，真正上生产却依然容易翻车、长期不稳定？

## 【回答】
根因**不是某一个 Prompt 没写好，而是长链路执行过程不可见**。普通聊天机器人答错一句最多是回答质量差，但 Agent 会规划任务、调用工具、读写状态、改文件、发请求、触发工作流，**每一步输出都会变成下一步输入**，于是**错误会沿执行链路传播**：第一步目标理解偏了→后面计划全偏；第二步工具选错→后面证据就是错的；第三步参数传错→工具返回异常→Agent 还可能基于异常结果继续推理，最后结论看着还像那么回事，中间过程已经乱了。

Demo 阶段看的是"它能不能跑通一次"，生产阶段看的是六件事：**能不能稳定跑很多次、异常下能否恢复、能否控制成本、能否解释过程、能否复盘失败、版本迭代后是否退化**——没有可观测性，这些只能靠猜。面试里应把视角从"模型会不会幻觉"切到**系统工程视角**：生产级 Agent 必须把计划、上下文、工具调用、状态变化、成本和评估结果全部纳入观测，否则出错无法定位、也无法持续改进。

## 【问题】
怎么理解 Agent Harness 可观测性？它到底要观测什么？

## 【回答】
定义：对 Agent 执行过程中的**目标、计划、上下文、工具调用、状态变化、成本、风险和结果质量**进行全链路**记录、度量、回放和评估**的能力。关键点在于**不只记录输入输出**，更要覆盖 Agent 真正麻烦的"中间过程"。一次复杂任务至少覆盖七类对象：

- **目标**：原始任务是什么，过程中有没有被改写。
- **计划**：Agent 怎么拆任务，每步是否服务原始目标。
- **上下文**：哪些信息被塞进模型，来源是什么，是否过期或污染。
- **工具**：调了什么工具、参数、返回、耗时。
- **状态**：任务状态、记忆、文件、数据库记录发生了什么变化。
- **成本**：每步消耗多少 Token、时间、工具资源。
- **评估**：最终结果是否正确，中间轨迹是否合理。

核心判断：**可观测性不是为了事后甩锅，而是让 Agent 的每一次执行都变成可分析、可复现、可改进的工程数据**——让 Agent 从"会干活"走向"可治理"。

## 【问题】
Agent 可观测性和普通日志 / 监控有什么区别？为什么已经有了日志还要单独做？

## 【回答】
普通日志记录的是"**发生了什么**"：接口何时被调用、请求参数是什么、返回状态码、服务耗时、异常堆栈——这些对传统后端很有用，但 Agent 最常见的问题（为什么选这个工具、为什么忽略关键上下文、为什么跑偏到子任务、为什么理解错返回、为什么重复规划 5 次）普通日志**回答不了**。

举例：用户让 Agent"分析最近 7 天订单异常原因"，普通日志可能全是 success（`POST /agent/run 200`、`call search_orders success`、`call query_refund_rate success`、`LLM response success`），但最终结论错了。Agent Trace 才能看到：**原始目标被改写成"退款率异常"、检索只查了退款没查支付失败、工具返回里有"支付通道超时"但模型没纳入结论、最终只归因到退款策略**。也就是说**HTTP 状态码可能全 200，但任务已经偏了**。

结论：传统日志关注**服务状态**，Agent 可观测性关注**执行意图和决策过程**。生产级 Agent 需要结构化 Trace，把 **Plan / Action / Observation / State Diff / Context Source / Eval Result** 串起来，而不是只打输入输出日志。

## 【问题】
一个 Agent Trace 里到底要记录哪些字段？

## 【回答】
设计成**任务级 Trace**和**步骤级 Step**两层。

任务级记录全局信息：`trace_id`（唯一 ID）、`user_goal`（用户原始目标）、`normalized_goal`（系统改写后目标）、`agent_version`、`model_version`、`policy_version`（工具权限/成本预算/审批策略版本）、`start_time`/`end_time`、`final_status`（成功/失败/降级/人工接管）、`total_tokens`/`total_cost`、`final_eval`。

步骤级记录每步发生的事：`step_id`、`step_type`（规划/工具调用/观察/总结/评估）、`current_goal`、`context_refs`（本步用了哪些上下文来源）、`model_input_summary`/`model_output_summary`、`tool_name`、`tool_args`、`tool_result_summary`、`state_before`/`state_after`、`latency_ms`、`tokens`、`risk_level`、`eval_result`。

三个特别重要的字段：①**`context_refs`**——很多错误不是模型变差，而是上下文给错/给多/给旧，必须知道本步推理用了哪些文档、历史消息、记忆；②**`state_before`/`state_after`**——Agent 会改变环境（写文件、改库、建工单、发邮件），没有状态差异记录就不知道它动了什么；③**`eval_result`**——不要等最终答案才评估，长链路里**中间步骤就要评估**，越早发现偏差修复成本越低。

## 【问题】
长链路任务里，怎么发现 Agent 已经跑偏（漂移）了？

## 【回答】
漂移通常不是突然发生的，而是**慢慢偏**的：一个小问题→变成子任务→抢走主线→最后忘了最初要干什么。常见五个信号：**①当前动作与原始目标相关度下降**（如目标是分析订单异常，却连续几步在优化报表格式）；**②子任务耗时超预算**（格式修复占掉 70% 步骤=主线被挤压）；**③重复步骤增多**（反复查同接口/重写计划/调同工具=卡住了）；**④目标表述变化**（订单异常→退款率→退款建议=目标漂移）；**⑤关键证据未被使用**（工具返回有重要异常信号但后续没引用）。

工程上做三类机制：**目标锚点**（每 N 步把原始目标、当前计划、最近动作放一起判断是否还在推进）、**检查点评估**（每完成子任务评估它对原始目标的贡献，而非只看完没完成）、**漂移告警**（低相关/重复率高/超预算时触发 Re-Planning、降级或人工确认）。注意**不是每步都自我反省**（成本会爆），合理做法是在关键节点轻量检测，如每 3–5 步，或在工具失败、重复调用、预算超限时触发。

## 【问题】
工具调用失败，怎么判断问题出在模型、参数、权限，还是工具本身？

## 【回答】
不能笼统归因成"模型不稳定"，要拆成五类故障并分别修：

- **工具选择错误**：问订单却调了知识库搜索→优化工具描述、路由策略、工具候选集。
- **参数生成错误**：工具选对但参数错（日期格式/字段名/必填缺失）→靠 JSON Schema、参数校验、错误反馈、少量示例。
- **权限边界错误**：用户只是问退款规则，Agent 却尝试执行退款→**不能靠 Prompt 兜**，要靠 Tool Registry、权限策略、高风险动作审批。
- **工具服务异常**：超时/500/依赖挂→走重试、熔断、降级、告警。
- **结果理解错误**：返回是对的但模型看错（"支付失败率升高"归因成"退款率升高"）→记录返回摘要、证据引用、输出校验、评估结果。

可观测性要记录完整链路：调用前记"为什么选这个工具"、调用中记工具名/参数/权限/耗时/重试、调用后记返回/模型如何解释/结果是否被最终答案引用。实用排查顺序：**工具是否存在 → 权限是否允许 → 参数是否过 Schema → 工具服务是否成功 → 模型是否正确理解返回**，按这个顺序能把大部分问题拆开。

## 【问题】
Agent 成本失控，应该监控哪些指标？怎么控？

## 【回答】
Agent 不是一次模型调用，而是多次规划、多次工具调用、多次上下文拼接、多次自检、多次重试，背后可能烧掉几十次 LLM 调用，所以**不能只看总 Token，要拆到步骤级**。至少监控七类指标：

- **总 Token 与单步 Token**：总 Token 只看贵不贵，单步才知道贵在哪步。
- **上下文长度**：很多成本来自把历史记录、检索文档、工具返回原样塞进去。
- **工具重试次数**：反复失败才可怕，每次失败都触发新分析和重试。
- **重复规划次数**：不断 Re-Planning 说明任务状态不确定或前面没推进。
- **无效步骤占比**：执行了但对目标无贡献=空转。
- **模型路由成本**：是否所有步骤都用大模型，简单分类/格式转换/规则判断能否用小模型或规则。
- **端到端延迟**：生产里时间也是成本，跑 3 分钟才出结果很多业务接受不了。

控制**不是简单砍 Token**（会连质量一起砍没），更合理的是**预算分层**：简单任务低预算、复杂任务中预算、高价值任务才高预算；超阈值时不直接失败，而是触发策略——压缩上下文、换小模型、减少候选工具、停止低价值子任务、要求用户补充、转人工或降级输出。

## 【问题】
线上失败一次之后，怎么保证下次不再犯同样的错？

## 【回答】
很多团队处理失败是"查日志→改 Prompt→上线→祈祷下次别出事"，这不叫工程化。真正的 Harness 改进要把**失败样本变成资产**，至少沉淀四类：

- **失败归因**：到底错在目标理解、上下文缺失、工具选择、参数、权限、模型误读还是评估漏掉——没有归因就没有方向。
- **评测样本**：把这次失败任务变成固定测试用例，以后 Prompt 改了、模型换了、工具描述改了都跑一遍。
- **Harness 规则**：结构性错误补进 Harness，如高风险写操作必须审批、连续三次工具失败必须停止、目标相关度低于阈值必须重规划。
- **监控指标**：把这次失败的早期信号变成告警，如重复调用、成本异常、关键证据未引用、工具返回错误率升高。

核心精神：**不要只修这一次错误，要把错误修进环境里**。Agent 犯错不可怕，可怕的是每次都靠人肉记忆、换个版本又犯。生产级 Agent 的进步靠持续积累失败样本、评测集、规则、监控和回归流程，而不是写一个完美 Prompt。

## 【问题】
如果从 0 设计一套生产级 Agent 可观测系统，你会怎么答？

## 【回答】
先讲目标再讲架构。目标很简单：**让每一次 Agent 执行都可追踪、可解释、可复盘、可评估、可改进**。架构拆六层：

1. **Trace 采集层**：在 Harness 的关键节点打点（任务开始、计划生成、上下文组装、工具调用、状态更新、评估、任务结束），注意采集点应放在 **Harness 里而非散落在各 Agent Prompt 里**，否则后面一定乱。
2. **事件存储层**：把运行事件结构化存储，原始输入输出脱敏，结构化字段（trace_id、step_id、tool_name、tokens、latency、status、risk_level、eval_score）用于查询分析。
3. **指标计算层**：从 Trace 算任务成功率、平均步骤数、平均 Token、工具失败率、重试率、漂移告警率、人工接管率、评测通过率。
4. **可视化与告警层**：研发看 Trace 回放、业务看成功率和成本、运维看延迟/失败率/异常工具；高风险动作、成本超限、连续失败触发告警。
5. **回放与评测层**：失败任务一键回放，固定输入/上下文/工具返回判断新版本是否修好旧问题。
6. **改进闭环层**：把失败归因沉淀到 Prompt、工具描述、权限策略、上下文策略、评测集和 Harness 规则。

渐进建设：先跑通 Trace→补工具调用和成本指标→做失败样本回放→做评测闭环和自动告警。方向一定要对：**不要把 Agent 可观测性做成日志大屏，要做成 Agent 改进系统**。
