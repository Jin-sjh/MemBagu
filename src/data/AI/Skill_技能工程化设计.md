# 技能工程化设计

## 【问题】
技能开发为什么需要工程化流程？五个阶段是什么？

## 【回答】
软件工程早就总结过一套方法，把「**在我的机器上能跑**」变成「**谁用都靠谱**」，核心流程分为五个阶段：**需求分析 → 设计 → 实现 → 测试 → 上线与发布**。

逻辑很朴素：做任何事之前**先想清楚**（需求分析），然后**规划怎么做**（设计），再**动手做**（实现），接着**检查做得对不对**（测试），最后**交付给别人用**（上线与发布）。工程化要做的是把直觉变成习惯，并补上最后一环。

## 【问题】
需求分析阶段怎么把「想清楚」落地？什么是「技能需求卡」？

## 【回答】
需求没想清楚的根源，往往是**压根儿没想过别人会怎么用**：没想过多语种、多样化触发需求；没想过私有环境配置要转为公开通用约束；没想过要对 PDF 文件、非文本素材做异常防护。

一个技能的诞生通常经历以下过程：
**反复手动做一件事 → 发现每次都在重复相同的步骤 → 尝试用提示词固定下来 → 发现提示词的局限 → 封装成技能。**
所以建议是：**先用提示词解决问题，反复踩坑后再封装成技能。**

落地工具是「**技能需求卡**」，回答 6 个问题（以「文章生成小红书信息图」为例）：

| 项 | 内容 |
| --- | --- |
| 1. 问题 | 把文章自动拆分为小红书风格的系列信息图 |
| 2. 场景 | 用户说「帮我做一组小红书图片」 |
| 3. 输入 | 一篇文章（Markdown 文件或直接粘贴） |
| 4. 输出 | 每张图的大纲文件 + 生成的图片文件 |
| 5. 规则 | 竖版 3∶4，卡通手绘风，每张只传达一个核心信息 |
| 6. 禁止清单 | 不能用写实风格，不能跳过大纲确认直接生成 |

**这 6 个问题的答案，基本就是该技能 SKILL.md 的骨架**——就像盖房子前先画草图：不需要精确到每块砖放哪里，但至少得知道有几个房间、怎么布局。

## 【问题】
让技能更靠谱的「四个设计技巧」是什么？

## 【回答】
针对「用着用着才暴露」的问题，四个技巧视角从过去到未来：

- **踩坑点**：把那些事先想不到、用多了才暴露出来的教训，作为专门的补充写进文件——让技能**记住过去的教训**。
- **可容错**：假定一定会遇到意外，给智能体预留好开头检查、人工确认和中间结果存盘的应急方案——让技能**扛得住当下的意外**。
- **可扩展**：让技能支持组合或外挂配置，以后增加新需求时**不需要修改原来的主文件**——让技能**适应未来的变化**。
- **跨对话记忆**：单独维护一个记录文件，让智能体下次接着上次的进度继续跑——让技能**长期积累**。

## 【问题】
为什么 Anthropic 认为踩坑点（gotchas）是技能里信息密度最高的部分？它和禁止清单有什么区别？

## 【回答】
Anthropic 内部几百个技能的实践表明：**一个技能里信息密度最高的部分，往往不是流程说明，而是踩坑点（gotchas）**——记录智能体在使用这个技能时反复犯的错。

建议在每个 SKILL.md 里**预留一个「踩坑点」部分**，第一版哪怕是空的也没关系，后面用的时候**发现一个加一个**。示例：

```markdown
踩坑点
- 生成图片时容易忽略用户指定的宽高比，每次生成前重新读取尺寸参数
- 中文标点和英文标点混用，所有标点统一用中文全角
- 总以为把模板放到 references/ 目录下，智能体自己就会去找，结果发现它根本不会主动跨文件读取。
  每次生成前必须加一句强提醒：智能体不会自动发现外部文件。
  如果调用了 references/ 目录下的文件，必须在这里明确给出指令：先读取 report-template.html，再生成 HTML 报告
-（持续补充）
```

**与禁止清单的区别在时间线**：禁止清单是你**事前设计时就能想到的硬性底线**（管「不许做什么」）；踩坑点是**事后使用中才暴露的意外盲区**（管「容易在哪里栽跟头」）。两者并行不悖，共同决定智能体的行为边界。

## 【问题】
可容错设计从哪三个方面着手？

## 【回答】
软件开发领域的铁律：**永远不要假设用户会按你期望的方式使用你的产品。**（用户会给空文件、特殊格式的文件、超长的文件，会用你想不到的说法触发技能。）

1. **开头检查输入**：你控制不了用户给什么文件，但可以让智能体**动手之前先看一眼**——文件是不是空的？格式对不对？内容是不是太长了？发现不对就提醒用户，别继续往下执行。示例：
   ```markdown
   第一步：检查输入
   - 如果没有提供内容，询问用户
   - 如果内容少于 100 字，提醒"内容较短"
   - 如果文件格式不在支持列表中（如上传了 PDF 但技能只支持 Markdown），提醒用户转换格式
   - 如果内容超过 10000 字，建议先指定重点
   ```
2. **关键步骤人工确认**：让智能体在**容易走偏的地方停一下**，等你确认完再继续。例如小红书信息图技能最初没有确认环节，智能体分析完内容直接生成所有图片——一旦发现方向不对，生成的图片全白费；加入人工确认后少了很多浪费。
3. **中间结果随手存文件**：别让所有生成结果都存在对话里。图片生成失败时，前面写好的提示词文件还在磁盘上，重跑不需要从头来；翻译技能中途出错，已译完的段落存在文件里，下次从中断的位置继续。

## 【问题】
可扩展设计怎么做？什么是「用维度组合替代穷举」和扩展文件机制？

## 【回答】
对应软件开发经典的**「开闭原则」**（对扩展开放，对修改关闭）：后续新增功能、适配新场景，尽量不去改动已经稳定可用的代码，只在原有框架之外叠加补充。目标是**让技能在不改 SKILL.md 的前提下，也能适应新需求**，方法方向大体一致：**把「稳定的流程」和「变化的细节」分开**。

- **用维度组合替代穷举**：不去穷举风格，而是把「风格」拆成六个独立的维度——**构图类型、色彩方案、渲染风格、元素密度、情绪调性、文字布局**，每个维度各有几个可选值，互不干扰。**总共只维护 32 个选项，排列组合却能产生 18900 种变体**；新增一个维度值（如加一种「蒸汽波」色彩方案），自动适配所有其他维度，扩展成本极低。这个思路特别适合「个性化定制」类技能。
- **扩展文件机制**：所有技能支持通过扩展文件（`EXTEND.md`）进行自定义，无须修改原技能。查找顺序（优先级从高到低）：
  1. `.baoyu-skills/<技能名>/EXTEND.md` ← 项目级（团队/项目专用配置）
  2. `~/.baoyu-skills/<技能名>/EXTEND.md` ← 用户级（个人偏好）
  
  智能体执行技能时会先读取扩展文件，用其中的配置**覆盖默认值**，团队里每个人可以有自己的扩展配置，互不干扰。
  **注意**：扩展文件要放在项目目录或用户目录下，**不要放在技能安装目录下**——技能升级时安装目录会被覆盖，自定义的部分就丢了。

**注意避免过度设计**：对于还没经过真实场景验证的技能，**把核心流程跑顺、把异常情况防住，永远比预留扩展点重要**。过早为「将来可能出现的需求」做设计，往往会增加不必要的复杂度（YAGNI：You Aren't Gonna Need It）。先把核心流程跑通，等新需求真的出现了再修改文件、提升扩展性。

## 【问题】
跨对话记忆怎么实现？

## 【回答】
好的设计不仅要考虑「空间」上的扩展，还要考虑「时间」上的连续——有些技能每次运行的效果，取决于它「记不记得」上次做了什么。

做法是让技能「记住」上次做到了哪里：在项目目录下按群建文件夹，把每次生成的精华**按日期存成文件**（如 `2026-03-12.md`），同时维护一个 **`history.json` 记录上次汇总最后一条消息的时间**。下次运行时，技能先读这个时间，**只拉取这个时间之后的新消息**——用户说「接着上次汇总」，技能就知道从哪里继续。

## 【问题】
技能的设计检查清单包含哪 8 项？

## 【回答】
1. **单一职责**：这个技能只做一件事吗？
2. **按需加载**：SKILL.md 的 name、description、正文是否符合最佳实践？详细内容是否拆到了 `references/`？
3. **可预测**：有没有明确的输出格式和示例？
4. **可容错**：输入为空或异常时会怎样？关键步骤有没有人工确认？
5. **可扩展**：稳定的流程和变化的细节是否分开了？
6. **跨对话记忆**：有没有单独维护一个记录文件？
7. **踩坑点**：有没有预留踩坑点部分？
8. **禁止清单**：有没有写清「不要做什么」？

## 【问题】
技能的文件夹结构通常经历哪四个阶段？

## 【回答】
软件开发中叫「**演进式架构**」——**先跑通，再演进**，无须一开始就搭一个「完美」的架构。先用最简单的结构跑起来，不够了再加。

1. **阶段一：跑通 MVP**。核心指标只有一个：**能用**。第一版越简单越好，与其闭门造车花一周设计「完美规则」，不如花一天写个极简版让智能体先跑起来。
2. **阶段二：功能补齐**。核心动作：**做加法**。在真实使用中发现原设计的缺失（少考虑了一种文件格式、漏掉一个输出要求），高频修改 SKILL.md，把补丁一个个打上去。
3. **阶段三：架构重构**。核心动作：**做拆分**。补丁越打越多，SKILL.md 必然臃肿，此时必须整理结构、拆分文件——把复杂的背景知识抽离到参考文档目录，或将过度膨胀的技能拆分为两个独立技能（讨论分析技能就是这么从会议纪要技能拆出来的）。
4. **阶段四：持续优化（长期进行）**。核心动作：**打磨**。功能和架构稳定后，处理边界情况、消除提示词歧义、降低词元消耗、偶尔加几条新规则。这个阶段没有明确终点，目标是让技能从「能跑」蜕变为「靠谱」。

实例：小红书信息图技能最初只是一份手动粘贴的提示词模板，让智能体封装成**约 200 行的初版 SKILL.md**，经过 **20 多次迭代**，才发展成 **641 行的主文件外加 26 个参考文档**的多文件结构。
