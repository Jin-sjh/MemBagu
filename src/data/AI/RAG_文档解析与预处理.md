# 文档解析与预处理

## 【问题】
RAG 离线阶段要做文档解析，常见格式（PDF/Word/HTML/Markdown）分别用什么工具？

## 【回答】
解析是把二进制或标记格式变成**可切分的纯文本**，并尽量保留标题层级、表格位置等结构信息：

- **PDF**：`PyPDF2`/`pypdf`、`pdfplumber`（表格友好）；纯文本 PDF 效果好，扫描版需 OCR。
- **多格式**：`Unstructured` 统一分区（标题/列表/表格），适合流水线。
- **JVM 生态**：`Apache Tika` 服务端批量解析 Word/PDF，适合 Java 栈或 Python 子进程配合。
- **Word**：`python-docx` 读 .docx 段落与表格。
- **HTML**：`BeautifulSoup4`、`readability-lxml` 去导航栏等噪声、抽正文。
- **Markdown**：直接文本读入 + markdown 库转 AST，**结构清晰，最适合 RAG**。

原理要点：**PDF 本质是排版指令，不是"自然段落"**，同一页可能多栏、页眉页脚混入，解析后必须按逻辑顺序重组，否则分块会乱序。

## 【问题】
PDF 解析在 RAG 里常见的坑有哪些？怎么应对？

## 【回答】
常见坑：1）**扫描件无文本层，必须 OCR**；2）**多栏、脚注、页码混入正文**；3）**表格被拆成无序碎片**；4）**字体编码异常导致乱码**。
对策：版面分析（layout）、表格专用解析、人工抽检与清洗规则。

## 【问题】
OCR 出来的文本对 RAG 检索有什么影响？

## 【回答】
OCR 会引入**错字、断行、丢标点**，导致**检索词不匹配**与 **embedding 语义偏移**。需要在清洗阶段做规范化，并考虑**关键词 + 向量混合检索**提高鲁棒性。

## 【问题】
表格和图片为什么难做 RAG？分别怎么处理？

## 【回答】
- **表格**：语义依赖**行列关系与表头**，固定长度切分易切断行列。对策：保留为 Markdown/HTML 表格字符串，或转 JSON 行记录存两份索引（自然语言版 + 结构化版），也可用**表头感知分块、SQL/结构化检索或专用表格问答模型**辅助。
- **图片**：含流程图/架构图时纯 OCR 不够，需用**多模态模型（如 BLIP、多模态大模型）生成描述文本**再入库，或对关键图做人工标注；图文混排按阅读顺序拼接"图注 + OCR/Caption + 相邻段落"为一个块或父子块。

## 【问题】
为什么很多团队推荐用 Unstructured 做解析？

## 【回答】
因为它把文档分成**带类型的元素**（Title、NarrativeText、Table 等），便于**按结构分块**和后续**路由**（表格走表格策略、正文走正文策略），比"一刀切"纯文本抽取更利于后续流水线。
