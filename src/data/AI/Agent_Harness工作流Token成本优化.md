# Harness 工作流 Token 成本优化

## 【问题】
一个由多 Agent 调度的 Harness 工作流，token 成本主要烧在哪？如何把成本拆开看清？

## 【回答】
腾讯广告研效团队用 `tech-leader` 这个 harness Skill 调度前后端协同开发：一次中等需求要经历 **5-6 个 Wave、20+ 次子 Agent 调用、数百轮工具调用**。token 消耗可拆成**六类来源**：

1. **系统提示词**：系统固定提示词、Skill 描述、MCP 工具 Schema，每轮必带，随 Agent/MCP 数量倍增。一个 **40 工具的 MCP Server 每轮增加约 10-15KB Schema 开销**。
2. **工具返回的信息**：MCP 调用返回的需求 JSON、设计稿节点树、截图 base64，体积不可控，塞进 context 后后续几十轮都要重复计费。
3. **读取的文件信息**：代码文件、知识库文档，盲搜式探索往往要 3-5 轮才定位，每轮匹配行、整段文件都会累积。
4. **长期记忆**：加载的历史经验/技术方案沉淀，一旦加载常驻会话，用不上的部分也占位。
5. **历史消息**：多轮会话累积，是**真正的大头**——append-only 且滚雪球式增长，越往后轮次越贵。
6. **用户提示词**：每轮增量、体量最小，六类中最便宜。

看清成本的前提是**先建度量**：CodeBuddy 把每轮 token 消耗上报至 **AgentLens**，通过 `agentlens-mcp` 可按 **TraceId** 追踪单次调用链路，也能按 **SessionId** 聚合一个完整需求的消耗分布，从而定位最贵的环节（如测试 Agent、主调度 Agent）。

## 【问题】
优化多 Agent 工作流 token 成本的核心方法论——“三原则十方向”是什么？

## 【回答】
团队把可下手的动作归纳为**三大原则**，并落地了**十个方向**：

- **① 让 AI 只看到当前需要的上下文（按需加载）**：渐进式披露（L2/L3 分层）、确定性操作脚本化、MCP 数据获取子 Agent 化、长期记忆按需索引加载。
- **② 减少无关的上下文（一开始就不带入）**：单 Agent 拆分为多 Agent、Agent 专属配置（工具白名单+模型分层）、代码图谱替代盲搜。
- **③ 减少重复的上下文（同一份内容不在多轮反复计费）**：稳定前缀设计（状态外化）、避免重复加载 Skill、rtk 压缩 CLI 输出、工具调用并行化。

动手前更前置的架构判断是**规模预判（S/M/L 模式）**：小需求走单 Agent 直接处理；只有**中大型需求**才进入多 Agent 并行调度。因为拆分本身有成本（多份系统提示词并行计费），只有需求规模足够大，拆分的后续收益才能覆盖这笔开销。

## 【问题】
渐进式披露（Progressive Disclosure）如何降低 token？

## 【回答】
源自 Anthropic Agent Skill 规范：不是所有内容都常驻 context，只有真正需要时才加载。三层结构下，**即使装了 20 个 Skill，初始加载也仅 1000-2000 token，上下文使用量减少约 90%**。

团队的两类改造：
- **条件性内容外移**：只在特定场景用到的内容（如自动化测试 Skill 的 spec 模板代码约 40 行、DB 前置操作规则约 38 行）外置到 `references/`，按需读取。改造后该 Skill 正文从 198 行降到 128 行（**-35%**）。
- **步骤详情外移**：以 `tech-leader` 主调度 Skill 为例，把 S/M 模式完整工作流、Wave 1~5 派发 prompt 等执行细节从正文移到 `references/`，正文只留骨架（核心职责、规模预判维度表、分流规则、进度追踪、容错）。骨架决定“下一步走哪”，具体“怎么走”按需 `read_file` 资源文件。

## 【问题】
“确定性操作脚本化”和“CLI 替代 MCP”为什么能省钱？

## 【回答】
两点：

- **CLI 驱动确定性环境/校验操作**：把数据库迁移、编译、服务启动、健康检查等确定性命令收进 `dev-env.sh`，AI **只提供参数、不自己拼接命令**（如不让 AI 拼 `mysql -u root -p`），消除反复查找参数命令的 token 浪费。
- **能用 CLI 就不用 MCP**：MCP 工具调用每次都是一次完整 LLM 推理轮次——含 LLM 决策、JSON Schema 常驻 context（每轮 10-15KB 额外 input）、返回结果进 context、LLM 再处理。以 Playwright 为例，用 MCP 实时控制浏览器，点一个按钮就是一轮对话，10 步=10 轮；换成 **Playwright CLI** 后，大模型只做“把用例翻译为 spec 文件”的推理，实际执行交给 CLI 批量跑——还带来**可重跑、可并行**的额外收益，耗时也缩短。

## 【问题】
MCP 数据获取“子 Agent 化”是怎么降本的？

## 【回答】
问题：主 Agent 自己调 MCP，原始 payload 会永久卡在**生命周期最长**的 Agent 的 context 里。tech-leader 工作流里需求分析要读 TAPD 需求、Figma 设计稿，TAPD 返回完整需求+关联缺陷+任务列表，Figma 返回完整节点树 JSON+截图，这些动辄几千字/上万行，会留在 TL 的 context 里被后续几十轮反复计费。

改法：给 TAPD/Figma 各建**专属子 Agent**，主 Agent 只拿到**结构化摘要**。实测同一工作流单轮 input token 从 **1,030,000 降到 634,905（-38.4%）**；首次调用两种方式消耗基本一样，真正收益在后续多轮不再带着原始 payload 滚雪球。

## 【问题】
单 Agent 拆成多 Agent，省钱的真正逻辑是什么？为什么不能盲目拆？

## 【回答】
最早的单体 Agent 把前/后端/测试/视觉规范混在同一段历史，全程一条会话无重置时机，历史只会越滚越大。

拆法的真实收益有两点（注意：拆分**不是**靠“减少历史堆叠”直接省钱——6 个 Agent 并行等于同时有 6 份系统提示词在计费）：
1. **分散滚雪球效应**：短生命周期子 Agent 跑完即销毁，历史滚雪球被切段；
2. **为后续优化打开空间**：稳定前缀、工具裁剪、模型分层、子 Agent 化都建立在“已经拆分”的前提上。

这也解释了为什么要先做**规模预判**——小需求不做无谓拆分，否则多份系统提示词并行计费反而亏。

## 【问题】
Agent 专属配置（工具白名单 + 模型分层）如何降本？

## 【回答】
以前每个子 Agent 默认带上所有已注册 MCP Server 的工具 Schema（用不到也带着），是隐藏成本漏洞。改法：
- 用 TeamCreate 创建**自定义子 Agent**，在定义文件 frontmatter 用 `tools` 字段指定工具白名单，未列出的 MCP 工具对该 Agent 完全不可见（如 `backend-dev` 只需 读/写/搜索/执行命令，不需要任何 MCP）。
- 顺带把派发提示词里的大段稳定指令迁移到子 Agent 系统提示词（更易命中缓存），TL 的派发提示词从 10-15 行精简到 2 行动态内容。
- **模型分层路由**：规则性强、推理要求低但轮次最多的角色（自动化测试、视觉还原对比）换成 **GLM-5v**（成本约 Sonnet 的 36%），测试/视觉 Agent 成本 **-64%**。

## 【问题】
代码图谱（graphify）替代关键词盲搜，效果如何？

## 【回答】
传统 `search_content` 盲搜每次返回的匹配行都进 context，且常常多轮搜索才定位，探索过程本身就是 token 消耗。代码图谱用 AST+语义建立文件索引和依赖关系，搜代码前先搜图谱锁定文件范围再 `read_file`，能**节省几十倍 token**（官方预估）。

实测（同任务对比）：总 token **从 875,352 降到 676,987（-22.7%）**，输入 token -22.8%，主要靠减少探索过程带入的冗余文件内容。缓存命中率从 94.4% 略降到 91.0%（-3.4pp），但总账仍省约 19.8 万 token。graphify 可 `uv tool install graphifyy` 安装，并绑定 Git Hook（`graphify hook install`）在 commit/checkout 后增量更新图谱。

## 【问题】
稳定前缀设计（KV Cache 命中）为什么能省钱？

## 【回答】
LLM 处理每个 token 要对之前所有 token 做注意力计算，产生 K/V 矩阵（KV Cache），计算量 O(n²)。**Prompt Cache** 的本质：若本次请求前缀与上次完全一致，服务商直接复用上次 KV 矩阵，跳过重复计算，只收约正常价 **10%** 的缓存读取费。

团队的两处破坏前缀的隐患与修复：
- 派发子 Agent 的提示词里稳定指令与动态内容（技术方案文档）交错，导致前缀无法命中 → 把**动态内容统一后置**。
- 主 Agent 进度状态不断在会话里输出累积，堆积在历史里使历史无法压缩 → 把**进度状态外化到文件中**，每次唤醒先 `read_file` 进度文件而不是回放历史；阶段切换改单行输出（如 `✅ Wave 1 完成 → Wave 2 🔄 已启动`），额外收益是会话中断后可直读文件恢复现场。

## 【问题】
rtk 压缩 CLI 输出、工具调用并行化，分别如何减少重复上下文？

## 【回答】
- **rtk 压缩 CLI 输出**：`git status`/`npm test`/`docker ps` 等原始输出夹带大量噪音，在修复循环里反复出现。rtk 是命令执行前拦截并重写为压缩版的开源 CLI 代理，官方实测降幅 **60%-90%**。幅度因命令而异（`ps aux` -98.9%，纯 `git status` 仅 -31%），不能拿固定值。接入踩的坑：①官方 `--agent` 不支持 CodeBuddy，改用 PreToolUse Hook 自实现拦截；②rtk 输出字段是 `updatedInput`，CodeBuddy 要的是 `modifiedInput`，字段名不一致会静默失效，需写几行转换脚本。评估时要直接对比命令行输出（100% 可复现），别用“跑两遍完整工作流”对比（大模型路径不确定，噪声比效果还大）。全局配置一次（`~/.codebuddy/settings.json`）所有子 Agent 自动获得压缩。

- **工具调用并行化**：无数据依赖的多次调用若串行，每次都是一轮独立 LLM 推理，前面所有轮次历史都要重新打包计费。原则：**两次调用之间没有数据依赖（后一次不需要前一次的输出）就该并行**。典型场景：TAPD 与 Figma 摘要互不依赖，改由 Task 工具在同一轮消息内并行派发两个子 Agent，主 Agent 一轮就拿两份摘要；测试用例同理用 Playwright CLI 一次收多个 spec、内置多 worker 并行跑，LLM 侧只 1 次调用+1 次读汇总。

## 【问题】
这套优化落地后的核心指标与全流程收益是什么？

## 【回答】
核心指标：主 Agent 端到端 token **从 708,783（17 轮）降到 315,266（9 轮），-55.5%，轮次 -47%**；子 Agent 命令行输出经 rtk 压缩后 **-60%~90%**；测试/视觉子 Agent 模型成本 **-64%**。

分项收益：渐进式披露使 SKILL.md 体积 -35%；MCP 数据子 Agent 化单轮 input -38.4%；代码图谱总 token -22.7%。以实测 Wave 消耗分布为基准反推，**一个中型需求跑完全流程 token 成本大致降低 50%~65%**。

落地优先级：先做规模预判和 Agent 拆分（架构前提）→ 度量 + SKILL.md 重排 + 全局接入 rtk（一个下午见效）→ 条件内容移出 SKILL.md、状态外化、排查无依赖调用改并行（逐步推进）→ 代码图谱、CLI 替代 MCP、工具裁剪、子 Agent 化、长期记忆索引化（中长期系统性梳理）。

## 【问题】
长期记忆（知识沉淀文档）如何做到“按需索引加载”而非全量常驻？

## 【回答】
`context-keeper`（知识沉淀 Skill）在方案设计前会加载历史经验/技术方案沉淀文档。最早的做学法是把匹配到的候选文档**全量读入** context——即使一份文档里只有一两条经验跟当前任务相关，剩下几十行也会一起进 context 常驻到会话结束，属于“加载了但用不上”的常驻 token。

改法引入一层轻量 **INDEX.md 目录索引**，把“查目录”和“读正文”拆成两步：
1. 先 `read_file` **INDEX.md**（几十行的标题+标签+摘要表格）；
2. 按关键词匹配标题/标签/摘要，结合类别权重计算相关度；
3. 取 **Top 3** 命中条目，才对这些篇 `read_file` 正文；
4. INDEX 不存在时才回退到全文 `search_content`（兜底，非常态路径）。

INDEX.md 是所有历史文档的目录，体量通常只有几十到一两百行——用几十行的索引筛出真正相关的 2-3 篇，比一次性全量加载几十篇文档的正文便宜得多。**相关度评分低于阈值的文档从一开始就不会进入 `read_file` 候选列表**，从源头减少了常驻 token。这是“让 AI 只看到当前需要的上下文”原则的体现。

## 【问题】
为什么下游子 Agent 要避免“重复加载 Skill”，跨 Agent 的信息该怎么传递？

## 【回答】
排查「前端 Agent」context 膨胀时发现，“调用知识沉淀 Skill 加载项目上下文”这一步其实没必要——主 Agent 做方案设计时**已经加载过历史经验并写入技术方案文档**，前端 Agent 直接读文档就能拿到结论，不需要重新 `use_skill` 把 200 行 SKILL.md 再次加载进 context。

核心原则：**信息应该在最上游收集一次，通过文档传递给下游，而不是让每个 Agent 各自重复获取**。这消除了重复常驻的 SKILL.md 开销，也是“减少重复的上下文”原则的具体落地之一。
