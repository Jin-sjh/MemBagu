# 一套工具解决多场景AI Coding的痛点

## 【问题】

AI Coding 在落地大型、多场景研发（架构升级、跨语言重构、大型新功能、日常开发）时，普遍卡在哪些痛点上？

## 【回答】

腾讯广告研效团队基于一站式研发平台 AMS（nex-code）的实战总结：AI Coding 已经不是"能不能写"的问题，而是"怎么写得好、写得稳、写得省"的问题。落地时普遍卡在三道坎：

- **上下文黑洞**：大仓 / 多语言 / 历史包袱，AI 看不全项目全貌，只能凭片段上下文动手，容易跑偏。
- **流程失序**：没有统一研发流程，不同人不同做法，质量靠运气，难复用、难评审。
- **成本失控**：全程用强模型，Token 烧钱，单轮长上下文是消耗大户。

解法不是换更聪明的模型，而是搭一套"会干活的系统"——用「一条主流程 + 两套引擎」统一兜住这三道坎。

## 【问题】

如何用"一条主流程 + 两套引擎"系统性地解决多场景 AI Coding 的痛点？

## 【回答】

**一条主流程：SDD + TDD（规格驱动 + 测试驱动）**，把质量从个人手感变成系统能力。

- **SDD（Spec-Driven Development）**：先写规格书（需求 / 接口 / 边界 / 验收），作为人与 AI 的契约，也是后续测试与审查的共同依据。
- **TDD**：先写测试再写实现，用测试作可机械判定的验收门禁，把质量卡在合入前而非靠"人觉得差不多"。
- **Skill 固化**：把"怎么干活"沉淀成可复用技能链（如 `@plan-stub-tdd-execute-verify`：规划→打桩→测试→执行→验证），一次沉淀多次复用，不随对话消散。
- **并行 Agent**：复杂任务用 `dispatching-parallel-agents` 拆分子任务并行协同，主流程负责编排与汇总，避免单 Agent 长上下文失控。
- **强制审查节点**：在编译 / 测试 / 人审等关键节点插门禁，AI 产物须通过（尤其人审）才允许合入，把"人"放在关键决策上做最后兜底。

**引擎一：代码知识图谱，解决"理解瓶颈"（上下文黑洞）**。Understand-Anything 静态抽取符号 / 调用 / 依赖，生成可导航的代码知识图谱；Graphify 把图谱按需注入上下文，让 AI 动手前先看懂项目。其思路与 Graph Engineering 同源——图谱比"把全文塞进上下文"更可检索、可推理，是应对大仓/多语言/历史包袱的可行载体。

**引擎二：模型路由 + 文本压缩，解决"成本失控"**。9Router 按任务难度路由：补全 / 格式化 / 样板生成走便宜小模型，架构 / 重构 / 疑难 bug 走强模型，在质量不受损前提下大幅省 Token；再配 Cavenman（文本压缩）、RTK（运行时压缩）对长上下文先压缩再喂模型，直接削掉单轮消耗大户。

**核心判断**：AI Coding = 流程（SDD+TDD）+ 知识（代码图谱）+ 模型编排（路由）三者协同，模型聪明只是其中一环；工具是手段，人和流程才是核心。

## 【问题】

这条"一条主流程 + 两套引擎"的方法论，在真实大规模场景上被验证过吗？效果如何？

## 【回答】

文章用四类实践验证，覆盖从大型重构到日常开发的跨度：

- **wpa 项目 OC→Swift 重构**：约 12 万行，AI 独立完成约 85%、人工介入约 15%。
- **cgi 后台 C++→目标语言重构**：约 8 万行。
- **大型新功能**：从 0 搭建。
- **日常开发**：修 bug 等。

最终量化效果：接入 AMS 后，相关团队 Token 成本平均降幅约 50%、PR 合入率提升约 40%。结论可落到一句话——AI Coding 不是换更聪明的模型，而是搭一套会干活的系统，人和流程才是可持续解。

**面试要点**：当被问"AI Coding 怎么落地到真实大项目"，不要只讲 prompt 技巧或换模型，而要从"理解（知识图谱）、流程（SDD+TDD+门禁）、成本（模型路由+压缩）"三维度给出系统化框架，并强调人在关键节点的把关价值。

## 【衍生问题】

- 代码知识图谱（Understand-Anything + Graphify）和单纯"把整个仓库塞进上下文"相比，优势具体在哪？为什么图谱更适合大仓 / 多语言场景？
- 9Router 按难度路由时，如何界定"简单任务 / 复杂任务"的边界？路由错了（简单任务误走强模型、复杂任务误走低模型）会带来什么后果？
- 强行在 AI 流程里插"人审"节点，会不会拖慢研发节奏？如何平衡"门禁保质量"与"速度"？
