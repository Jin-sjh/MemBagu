# Subagent 与 Skills 对比与选型

## 【问题】
什么是子智能体（Subagent）？什么是子 Skills？两者的本质区别是什么？

## 【回答】
这是 Agent 架构里的经典选型题，本质区别在于「**能力从哪里来**」：

- **子智能体（Subagent）**：由主 Agent 派发的**独立 Agent 实例**——有**自己独立的上下文窗口、工具权限和执行循环**，能自主探索、自主决策，最后只把**结果摘要**交回主 Agent。
- **子 Skills（技能包）**：**静态知识/指令包**——本质是「操作手册 + 参考文件 + 可选脚本」，按需**加载进主 Agent 上下文展开成提示词**，不产生新的 Agent 执行循环，由主 Agent 照着执行。

一句话定性：**Subagent 是「分一个人去干活」，Skills 是「给干活的人递一份手册」——一个产生独立的执行循环，一个只是注入知识。**

## 【问题】
子智能体与子 Skills 各自的优缺点是什么？

## 【回答】
关键维度对比如下：

| 维度 | 子智能体 Subagent | 子 Skills |
| --- | --- | --- |
| **上下文隔离** | ✅ 独立窗口，大量检索/探索不污染主上下文 | ❌ 直接占用主上下文，长 skill 提示词很占 token |
| **并行能力** | ✅ 多个 Subagent 可同时跑 | ❌ 只能串行，在主 Agent 内 |
| **成本** | ❌ 每次派发是整套 Agent 循环，总 token 不一定省 | ✅ 只是文本展开，开销极低 |
| **可控性/确定性** | ❌ 有自主性，可能偏航、幻觉放大，需验收环节 | ✅ 指令明确、行为可复现、结果稳定 |
| **编排复杂度** | ✅ 能承载多轮规划、探索决策、事件驱动、独立失败/重试 | ❌ 复杂编排力弱，本质是「照着规则执行」 |
| **可维护性/复用性** | ❌ 每个要单独配 prompt/工具/权限，跨项目复用难 | ✅ 就是个文件夹（md+脚本），版本管理、分享、评测都方便 |
| **调试/追踪** | ❌ 行为发生在子上下文里，出问题难查 | ✅ 逻辑在主流程里，链路清晰 |
| **失败隔离** | ✅ 子 Agent 崩了不影响主流程 | ❌ 主 Agent 出错整个执行受影响 |

**核心结论**：Subagent 的优势是**上下文隔离、可并行、失败隔离**，代价是**开销大、有偏航风险、不好调试**；Skills 的优势是**轻量、低成本、确定性强、易维护复用**，代价是**占主上下文、无并行、做不了复杂编排**。

## 【问题】
子智能体和子 Skills 分别在什么情况下使用？（面试选型题）

## 【回答】
判断标准一句话：**任务「边做边决定怎么做」用 Subagent；「知道步骤、只求做得对」用 Skills。**

**优先选 Subagent，满足任意一条即可**：
- **探索量大**：要读大量文件、跨模块检索、梳理整个代码库——一个 Subagent 能省下海量主上下文；
- **需要并行**：多个互不依赖的方向同时推进；
- **子任务有独立成败标准**：适合单独评估、单独重试、需要隔离风险（如独立部署、独立校验）；
- **输出只需精简回传**：只需把结论带回主流程。

**优先选 Skills，满足任意一条即可**：
- **领域流程固定**：做标书、API 操作、格式整理等步骤稳定、高度依赖规则的领域任务；
- **追求可复现、低成本**：团队协作、跨会话复用、需要质量稳定；
- **主 Agent 能力够、只是缺知识**：缺的不是执行能力，是操作手册；
- **需要打包工具/脚本**：如附带解析器、格式校验脚本等。

## 【问题】
实际工程中子智能体和 Skills 是二选一吗？最佳实践是什么？

## 【回答】
两者不是互斥的，成熟的做法是**分层组合**：

```
主 Agent（编排者）
 ├─ 加载 Skill：注入领域方法论/SOP（骨架知识）
 └─ 派发 Subagent：并行探索、长任务执行、独立调研
     └─ 回传结果摘要 → 主 Agent 再调用对应 Skill 做格式/规则处理
```

- **编排层**（主 Agent）：掌握目标拆解与最终决策；
- **执行层**（子智能体）：并行跑探索/采集类脏活，定义好输入输出契约；
- **知识层**（Skills）：沉淀规则、格式、领域 SOP，供各层按需加载。

典型例子：研究型工作流中，主流程加载「领域方法论」Skill 武装自己，同时派多个 research Subagent 去并行读不同方向的资料——**Skill 提供骨架知识，Subagent 负责并行执行探索性工作**，既有深度又有广度。面试加分表达：这是目前 Agent 工程里最实用的组织方式。

## 【衍生问题】
- 被追问「Subagent 不是更耗 token 吗」？（答：单看子任务是的，但要看全链路——探索量大会挤爆主上下文导致关键信息丢失/重整理时，Subagent 把上下文隔离在子窗口、只回传摘要，综合成本反而更低，换的是「主上下文的确定性」；Anthropic 实测多智能体系统 token 约为普通对话 15×，只值得用在价值足以覆盖成本的任务上。）
- 被追问「Skill 提示词太长怎么办」？（答：拆粒度 + 延迟加载——skill 描述要短，让主 Agent 判断要不要加载，主体内容按需读参考文件而非全量灌入上下文；同领域 skill 尽量合并减少重叠。）
- 被追问「子 Agent 结果不可信怎么办」？（答：验收闭环——给子任务定义结构化输出格式与自检步骤；关键路径不外包——决策权与最终校验留在主 Agent，子 Agent 只做采集与初加工。）

## 【口诀】
- **探索并行派 Subagent，固定流程用 Skill**
- **Skill 定骨架，Subagent 跑并行，主 Agent 做编排**
