# 自进化飞轮方法论（评测·记忆·落地·控制）

> 本文沉淀自腾讯内部 KM 文章《评测→记忆→落地→控制：一篇讲透 Agent 自进化飞轮怎么搭》（km.woa.com/articles/show/667656，作者 ethanytzhou / yannisyang，更新于 2026-08-17）。核心论点：自进化的瓶颈不在单个技术点，而在**环节之间的衔接**——评测是飞轮的"眼睛"（感知问题）、记忆是"大脑"（积累经验）、落地（Self-Improve/工程化）是"手脚"（把经验变改进）、人机协作是"方向盘和刹车"（保方向不跑偏）。拆开来做每块都能说"我做了"，但环节间数据通路断了，飞轮就不产生复利。

## 〇、先对齐：自进化改的到底是什么

## 【问题】
"自进化"分哪三层？当前最具性价比的主战场是哪一层？

## 【回答】
按"改什么"分三层，决定了进化的持久性和价值：
- **Artifacts 层（改输出产物）**：代码写三版越来越好、方案改几稿越来越靠谱。**任务结束 Agent 本身没有任何改变**，下次遇到同类问题不会更快——这不是进化，是打草稿。已成熟（Self-Refine、Test-time Compute Scaling）。
- **Harness 层（改配套系统）**：改**记忆、Skill 文件、Prompt、工具配置、工作流**——这些改动持久化到文件/数据库，**跨会话生效**，改一次后续所有任务都受益。这是**当前最具性价比的主战场**。
- **Model 层（改模型参数本身）**：通过 Agent RL、自对弈微调把经验写入权重，持久性最强但成本最高、风险最大，目前仍在研究阶段（MiniMax M2.7、Dola 团队在探索）。

**为什么 Harness 是主战场？** 四个字：**即时、可控**——改完 Skill/Prompt 立刻生效，改错了一键回滚，不造成不可逆损害。实测佐证：TCS EvoLoop 通过 Harness 层进化**迭代次数减少 70%、Token 消耗降低 84%**；TencentDB Agent Memory **Token 节省 61%**——收益全部来自"改配套系统"，一个模型参数都没动。

## 【问题】
三个核心立场是什么？

## 【回答】
① **自进化的瓶颈不是任一技术点，而是环节衔接**：评测信号必须流进记忆和 Skill 更新；更新后必须能被评测验证；验证结果必须反哺下一轮进化。断任何一环飞轮都转不起来。
② **评测的可信度 > 系统的复杂度**：简单但评测可信的系统，远好于复杂但评测失真的系统。错误的正反馈让 Agent 加速开往悬崖。
③ **记忆系统的核心不是存储能力，而是治理能力**：版本控制、主动遗忘、冲突解决、来源溯源，这些"不性感"的能力才决定记忆帮忙还是添乱。

## 一、齿一：信号——评测

## 【问题】
评测在自进化系统中承担哪三重职责？

## 【回答】
传统评测只承担"质量门控"（上线前达标放行）。自进化系统里评测至少三重职责：
1. **方向指引**：告诉系统"哪里有问题"，决定进化朝哪走。
2. **质量门控**：更新 Skill/Prompt 前验证"改了是否更好"，防退化。
3. **经验筛选**：判断一次执行结果是"好经验"值得沉淀，还是"坏经验"该丢弃。

后两者是新角色——评测信号会直接流入记忆和 Skill 更新链路。传统评测打错分顶多是"上线不够好的版本"；自进化评测打错分是"Agent 学到错误经验并持续污染后续所有任务"。所以**评测的可信度 > 系统的复杂度**。

## 【问题】
评测体系的七大核心难题是什么？

## 【回答】
精度 × 成本 × 覆盖面三难困境下，七个具体问题（最致命→最常见）：
1. **弱评估器**：LLM 给 LLM 打分有系统性偏差（偏好长文本、偏好编号列表、偏好表面正确性），会让 Agent"学会"骗评估器——错误的正反馈比没反馈更可怕。
2. **维度缺失**：Agent 输出是"推理过程+工具调用+中间结果+最终答案"的组合，只评最终答案会漏掉幻觉碰巧答对、工具冗余、推理链有错靠记忆力强蒙对等问题。
3. **粒度选择**：粗粒度（整任务成败）便宜但不知错在哪；细粒度（每 step/tool call）精确但成本指数级增长（一轮几百到上千次 LLM 调用）。建议日常粗粒度筛选、失败 case 再细粒度归因。
4. **开放式任务难量化**：写作/规划/方案设计无确定性对错，人工审查不可扩展，纯 LLM Judge 有偏差。建议用偏好排序替代绝对打分，或 AI 初筛+人复核流水线。
5. **评测集漂移**：业务在变但评测集半年不更新，Agent 在旧集刷高分，线上真实体验却持续下降。没人会在评测全绿时怀疑评测本身。
6. **预算公平性**：很多"提升"仅来自多花预算（Best-of-N、多次重试取优），关掉额外预算就打回原形。真正的进化应在相同 Token 预算下也更好。
7. **评测成本**：每改一次跑全量评测 Token 成本失控。解法：每次改动跑轻量回归（核心 case），定期跑全量。

## 【问题】
怎么搭一套可信的评测体系（建设要点）？

## 【回答】
**手段分层组合**（把成本花在刀刃上）：
- 底层：**规则/自动化校验**（代码能跑、测试通过、SQL 结果匹配、格式正确）——零成本、100% 客观，是基石，多数团队没充分利用。
- 中间层：**LLM-as-Judge + 对照实验**，关键原则：生成与评估模型**必须分离**（否则触发自洽偏差）；评估 **temperature 设为 0**（可复现）；输出**结构化**（Pydantic/JSON Schema）；**分维度独立评估**（不要一个调用同时评判正确性+完整性+格式+效率）。
- 顶层：**人工抽样 + 元评测集**，定期人审抽检，维护几十条"绝对正确/错误"样本做元评测——评估器连极端 case 都判错就该告警。

**评测集三分法**（严格职责分离，互不泄漏，定期更新防过拟合）：
- **train 集**：只用于诊断（告诉系统哪类失败率最高、失败模式是什么），可暴露给生成修复的 LLM，但不用于"判断谁更好"。
- **val 集**：只用于筛选（判断候选变体是否比基线更好），**绝不暴露**给生成修复的 LLM（否则它会"记住"答案）。
- **test 集**：只用于最终验证（上线前最后把关），独立存在捕捉"在 val 上过拟合但对新问题无效"。
- 比例建议：train 50-60% / val 20-30% / test 15-20%；val 每 2-4 周更新 20-30%，test 每 1-2 月更新，train 持续追加线上新失败样本。

**终点不是打分是诊断归因**：按失败类型走不同链路——系统性问题→触发 Skill/Prompt 更新+写 Playbook；偶发个例→写入记忆反例；能力缺失→触发工具/能力补充（Auto-Research）；回归问题→立即回滚标记 blocked 人工介入；全部通过→合入生效进灰度。**血泪教训**：某场景连续 3 轮失败率 80%+ 不降，先查工具实现层（API 参数错、服务端异常、数据没回来），别在配置层打转——这是 Cube-Harness AutoEvol 20+ 轮无效迭代才换来的教训。

## 【问题】
Skill 评测要通过哪四层验证？

## 【回答】
Skill 是 Harness 层核心产出物，但"存在"不等于"有用"（很多 Skill 只是和模型能力碰巧重叠）。至少四层验证：
1. **对照实验（模型本来就会做吗？）**：有/无 Skill 两组跑同批 case，无 Skill 也能做对则 Skill 贡献为零——很多团队跳这步积累了大量"看起来有用实则无用"的 Skill。
2. **难度校准（任务是否太简单？）**：case 太简单模型不需要额外知识就做对，对照看不出差异。需设计难度梯度，让"无 Skill 做对一部分做错一部分"才能看出增量价值。
3. **轨迹追踪（运行时真的调用了 Skill 吗？）**：Skill 在上下文里、最终答案也对，但 Agent 可能根本没 follow 步骤（靠自身能力完成）。需追踪执行轨迹检查是否出现 Skill 定义的关键步骤。
4. **路径验证（结果对了，但路径对吗？）**：Agent 绕过了 Skill 定义的关键校验步骤碰巧答对，下次数据异常就翻车——路径不对意味着下次会翻车。

工程化建议：上线前必跑对照实验、case 要有难度梯度、引入轨迹评测（不只看输出看路径）、定期复评（防 Skill 因环境变化过时）。

## 二、齿二：积累——记忆

## 【问题】
记忆系统的核心认知转变是什么？三环十大难点指什么？

## 【回答】
**核心转变**：记忆的难点不在"存储"而在"治理"——像 Git 的价值不在"能存代码"而在版本控制、分支、冲突解决、审核这些治理能力。把记忆当"治理系统"而非"存储系统"来设计。**一组矛盾数据**：多个团队加长期记忆后因检索噪声过高降级回无状态（记忆模块被默默关掉）；而有效长期记忆的 Agent 体验和留存显著更优——说明记忆难度被严重低估，"加个向量库存起来"不行。
三环十大难点：
- **写入环**（什么值得存）：①价值判断难（大量中间信息是噪声，有价值经验藏在细节）②正负反馈不对称（成功不知因何成功，归因易错）③粒度选择（太粗无法复用、太细信息过载）④隐性知识难捕获（"什么不能做"的负空间知识最难识别）。
- **存储环**（存了怎么不腐烂）：⑤记忆污染（一条错记忆影响数百次任务，错误蔓延远快于修复）⑥时效性衰减（半年前信息过时仍被引用）⑦记忆冲突（不同来源/时间写入矛盾，多 Agent 并发更严重）⑧存储成本失控（无遗忘策略线性增长）。
- **读取环**（怎么用不出问题）：⑨检索噪声（向量相似≠语义相关，"查订单状态"可能召回"取消订单"）⑩上下文预算分配（注入太多挤压工作空间、太少漏关键背景）。

## 【问题】
记忆系统的建设要点（写入 / 存储 / 读取）？

## 【回答】
- **写入——策展而非全存**：Agent 是策展人不是录音机。正信号（用户确认/评测通过/任务成功）才写入长期记忆；失败也提取经验但标"反例/陷阱"（一个明确反例比模糊正例更有价值）。**三层晋升机制**：临时记录→工作记忆→长期记忆，低门槛解决"忘记记录"、再层层筛选升级。非对称淘汰：好经验强化 +0.05 **远慢于**坏经验淘汰 -0.12（淘汰是强化 2.4 倍）——一条错记忆的伤害 > 一条对记忆的收益，宁可慢积累好经验也不让坏经验扩散。
- **存储——分层架构 + 生命周期管理**：业界共识（Hermes 56K+ Star、TencentDB Agent Memory 已开源、混元 Hy-Memory）。如 TencentDB 四层 L0 原始对话→L1 原子事实→L2 场景块→L3 用户画像，核心"默认 L3，按需钻取 L1/L0"。生命周期：版本控制（每条带版本号+来源标记）、演化能力（沿时间线更新/合并/分裂/衰减）、主动遗忘（TTL/低频衰减/负反馈快速淘汰）、冲突解决（后入优先+人工仲裁+乐观锁）。结论：**"团队记忆首先是一套治理系统"**。
- **读取——渐进披露 + 严格预算**："从粗到细、按需钻取"——默认只注入顶层（Persona+Skill 前言约 500-800 token），任务到来语义检索中层（语义向量+全文+精确三路并行取 Top-K），遇困惑才通过 node_id 钻取底层原始对话。**严格预算**：Skill≤2000 / Facts≤800 / Profile≤500，单条≤200 Token，最多注入 6 条。反直觉发现（Anthropic Dreaming）：记忆建模为**文件系统**让 Agent 用 Bash/grep 管理比硬造专用 API 更有效；符号化压缩（TencentDB 用 Mermaid 编码任务状态、日志卸载外部）Token 节省 61%、通过率 33%→50%。

## 三、齿三：落地——工程化

## 【问题】
为什么说"自动化 ≠ 全自动"？完整链路有哪八环节？

## 【回答】
当前阶段"Agent 自己发现→自己改→自己上线"是危险幻想：①LLM 生成修复质量不可控（看不到历史决策/业务约束/API 规范，可能覆盖上次人工精心调的逻辑）②单点修复缺全局视角（改 Skill A 解决 X 却悄悄破坏 Skill B 触发逻辑）③"总结→生成 Skill"需专门优化（SkillOS 研究证明训练过的小模型策展人优于冻结大模型策展人）。所以：**自动化覆盖"生成候选→评测验证→门控筛选"，关键决策必须有人把关**。

完整八环节（本质是 "Agent CI/CD"）：
1. **诊断归因**：失败 case 分组、识别模式、定位到具体环节（Prompt 不清？Skill Bug？工具异常？数据问题？）。归因粒度决定修复精度。
2. **信号汇聚**：修复方向不能只看"这次错什么"，需三路——本轮诊断结论 + 历史 Playbook（什么改法有效/踩过什么坑）+ Auto-Research 外部知识（防平台期停滞，Cube-Harness 曾自发现两条初始配置外的新方向）。
3. **生成候选**：LLM 产出 N 个候选，**用 Diff 模式**（只输出需改片段）而非全文重写；注入背景知识（API 规范、历史决策）避免"看似合理实则有害"的修改。
4. **独立评测**：每个候选在隔离环境验证（互相干扰会污染结果），成本最高，故生成环节要控 N。
5. **安全门控**：语法检查→回归检测→统计显著性→Playbook 一致性→人工确认。前四层自动过滤 **95%** 低质变体，人只审"大概率有效"的少量候选。
6. **灰度发布**：通过门控≠全量。标准 **10% 流量 × 7 天观测期**，监控成功率/Token/延迟/反馈，P0 退化**一键自动回滚**（回滚还需人决策则半夜无兜底）。
7. **监控回流**：灰度期新失败样本自动进下一轮种子池——上线不是终点而是下一轮起点。无回流则进化是一次性活动。
8. **经验沉淀**：本轮有效方向/踩坑写入 Playbook（服务于"怎么改 Agent"，与通用记忆互补独立）。无沉淀则每轮从零开始。

## 【问题】
落地的其他关键建设要点（版本化 / Diff / Dreaming）？

## 【回答】
- **版本化一切**（生存基础设施）：Skill/Prompt/记忆每次变更必须有版本号（可回滚任一历史版）、变更日志（谁改/为什么/改什么 diff）、来源标记（哪次评测触发、自动还是人工）、关联评测结果。出问题排查链路：线上异常→定位引入版本→看变更内容→看关联评测→决定回滚到哪版。
- **Diff 模式**：全文重写 Skill 风险极大（覆盖无关逻辑、无法 review、无法精准回滚）。Diff 只改目标区域，改动一目了然、可精准回滚。多文件联动修改需 **AST 签名验证**确认跨文件函数/接口签名未因单侧修改不兼容（Cube-Harness 教训：多 Skill 联动改写的隐蔽回归最难排查）。
- **Dreaming 异步"做梦"式进化**：同步评测一次只看单任务，抓不到跨会话系统性模式（如 100 次会话 30 次都在"时间格式转换"栽小跟头，单次看是偶发、合看是短板）。Dreaming 是专职异步进程（空闲时运行），定期审阅历史会话轨迹，发现反复失败模式 / 低效模式（成功但走弯路耗 Token）/ 知识缺口，输出修订建议列表（最终由人决定）。类比：同步评测是"作业批改"，Dreaming 是"期中总结"。建议每天/周跑一次，高价值建议进正式八环节流水线。

## 四、齿四：控制——人机协作

## 【问题】
人的角色是什么？分级自主模型怎么设计？

## 【回答】
**人的角色是教练和裁判，不是操作者**——按场景分级自主、渐进放权、动态升降级。完全放手危险（Anthropic《When AI builds itself》2026.6 警告：AI 自主改自身配置会隐蔽累积偏移）；完全人工太慢。分级：稳定领域高度自主、新领域和高风险必须有人。**动态升降级**：升级条件（通过率持续>95%、连续 N 周期无回归、抽检无问题）；降级触发（P0 回归自动降 Level 1 直到修复）；**不可逆红线**：安全边界/拒答逻辑/付费相关变更永远不能到最高自主级**。

## 【问题】
哪五个节点永远必须有人？

## 【回答】
无论自主级多高，这五个节点是设计刚性约束（非技术做不到）：
1. **规则级记忆写入前**：规则级记忆（"这类问题永远用方案 A"）被无条件遵循、影响面全局，错一条会长期不被发现——写入前必须人工确认（成本几秒但避免巨大损失）。
2. **Prompt/Skill 更新的最终确认**：尤其涉及安全边界、拒答逻辑、权限控制。Agent 不应有能力修改自己的安全约束（像程序不能改自己的权限配置文件）。
3. **评测发现回归时的决策**：回滚到哪版？优先级？阻断全部还是冻结一块？涉及业务影响面判断，Agent 缺上下文。
4. **新领域冷启动的初始经验种子**：无历史数据飞轮转不起来，需人提供首批评测 case（什么叫好）、初始 Skill（大致怎么做）、安全边界（什么绝对不能做）——"手推第一圈"，之后可自转，但第一圈必须人推。
5. **安全边界的设定与调整**：Agent 能改到什么程度（能改 Prompt 不能改安全规则？能增 Skill 不能删？）这些线必须人画，否则会出现"隐蔽累积偏移"——Agent 逐步扩大自身权限，每步合理但累积失控。

## 【问题】
审核疲劳怎么解？什么是对齐漂移？

## 【回答】
**审核疲劳**（落地最常见失败）：什么都弹审核，人三天后不看直接通过——比没有审核更危险（虚假安全感）。本质：到人手上的东西质量差、数量多。解法三层：①自动化前四层门控过滤 95% 低质，人只审机器判不了的；②**批量异步审核**而非逐条弹窗——攒一批附评测数据/影响面/对比示例/AI 推荐理由，让人做"这 5 个哪些能上"的选择题；③渐进放权+自动降级——稳定 3 个月可申请升 Level 2（只事后抽检），出回归自动降回。
**对齐漂移**：Agent 自进化方向缓慢偏离人类长期意图（如你希望"准确且简洁"，但评测无意奖励"详细"，多轮后越来越啰嗦，每步评测分在涨但累积偏了）。技术门控抓不住——门控查"这次是否引入回归"（局部），不查"整体方向偏了一小步"（全局）。三层防护：①**定期方向性审计**（每月半天人工看 Skill 库/记忆/输出风格变化是否仍合初衷）②**设置方向性约束指标**（平均输出长度、工具调用次数、拒答率不能持续恶化，超阈值告警）③**评测集显式包含"意图对齐"维度**（专查简洁性/格式/语气）。

## 五、飞轮咬合与落地

## 【问题】
四个齿之间的数据通路怎么咬合？启动与持续动力是什么？

## 【回答】
飞轮转起来的前提是"每个环节的输出恰好是下一环节的输入"，断任何一条通路就卡住：
- **通路一：评测→记忆**：评测产出"好经验"信号触发记忆写入（策展式，非全存）。断了→做对不记住，下次从零开始。
- **通路二：评测→落地**：评测产出"问题/差距"信号驱动修复生成。断了→知道有问题但不去改。
- **通路三：落地→控制→生效**：修复经五层门控+人工确认后灰度上线。断了→方案停在"候选"永不生效。
- **通路四：生效→下一轮评测（回流）**：更新后新表现被下一轮评测捕获，成功正例入金标集、新失败回流为种子。**这是飞轮持续转动关键**——无它进化是一次性，有它每转一圈信息更多。

**启动能量（人工推力，不能省）**：高质量初始评测集（飞轮眼睛，值得花 1-2 周设计）、人工注入首批 Skill/记忆（白板期给初始方向）、清晰安全边界（越早画越好，错误扩散速度与转速成正比）。
**持续动力（自动回流）**：线上新失败样本自动回流为种子、成功经验按晋升规则自动升级 Skill、异步 Dreaming 发现跨会话模式、Auto-Research 引入外部知识防方向枯竭。
**最易跑通的场景特征**（TCS EvoLoop 修复率 29.5%→89.8%、微视标题自进化 Agent、Cube-Harness）：①评测信号来自**真实业务指标**而非人工构造（微视用真实 CTR、TCS 用真实工单修复率，天然无评测集漂移）②闭环链路短、反馈延迟低（TCS 经验 5 轮内能看到显著提升，跑 20 轮才见效团队早放弃）。

## 【问题】
从零到一的落地路线？

## 【回答】
分四阶段，核心建议**先跑通 Phase 1**（一个能手动转一圈的粗糙飞轮，好过精美但静止的蓝图）：
- **Phase 1 最小闭环（1-2 周）**：50-100 条评测 case + Markdown 记忆 + 手动跑完整闭环。核心验证闭环本身是否成立，**人工占比 80%**。
- **Phase 2 半自动化（2-4 周）**：Skill 自动生成管线 + CI 评测门禁 + 版本管理 + 评测集三分法，目标"能自动改进且不退化"，人工 40%。
- **Phase 3 飞轮运转（1-2 月）**：灰度发布 + 回流机制 + 异步 Dreaming + 渐进放权，目标"飞轮自主转动"，人工 15%。
- **Phase 4 元进化（持续探索）**：Auto-Research + 进化策略自优化 + 多 Agent 协同，人工 5%。

## 【问题】
全文收束的三条原则？

## 【回答】
1. **评测的可信度 > 系统的复杂度**：先擦亮"眼睛"再让"手脚"动，评测不可信的系统自动化越高犯错越快。
2. **记忆系统是治理问题不是存储问题**：向量库不是记忆系统，版本控制/主动遗忘/冲突解决/来源溯源/晋升门控才是关键，存 100 条低质记忆不如治理好 10 条高质量。
3. **闭环价值在环节衔接而非单个环节先进性**：评测信号必须自动流进记忆和 Skill 更新、更新后必须被评测自动验证、验证结果必须自动反哺下一轮——这些"箭头"而非环节本身决定飞轮转不转。自进化不是功能，是**系统设计范式**：把"评测—记忆—落地—控制"工程化进 Harness，让每次执行不白费、每次教训不白吃、每次改进经验证。
