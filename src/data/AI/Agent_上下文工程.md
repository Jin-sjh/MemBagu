# 上下文工程

## 【问题】
什么是「上下文（Context）」与「上下文工程（Context Engineering）」？

## 【回答】
- **上下文（Context）**：指在从大语言模型（LLM）采样时包含的一组 token——**不仅是提示词，还包括系统提示、工具定义、对话历史、检索到的文档等所有进入模型的信息**。
- **上下文工程（Context Engineering）**：**在 LLM 推理过程中，策划和维护最优 token 集合的策略集合**。
- 核心指导原则：找到**「最小可能的高信号 token 集合」**，最大化期望结果的可能性。
- 本质规律：**AI 的决策质量 ∝ 可用信息的完整性 × 信息的信噪比**。

背景判断（Anthropic）：**AI 的上下文管理，决定了 AI 能否在长流程中稳定工作**——如果上下文缺失或过载，模型输出再强的能力也发挥不出来。

## 【问题】
提示词工程（旧范式）与上下文工程（新范式）有什么不同？

## 【回答】
| 提示词工程（旧范式） | 上下文工程（新范式） |
|---------------------|---------------------|
| 关注如何编写有效的提示词 | **管理整个上下文状态** |
| 主要针对一次性分类或文本生成任务 | 针对**多轮推理和长时间运行的智能体** |
| 「找到正确的词语和短语」 | 「**什么样的上下文配置最可能产生期望行为？**」 |

在工程层级中的定位：Prompt Engineering（这一次怎么说）→ **Context Engineering（这一次让模型看见什么）** → Harness Engineering（在工程环境里可靠执行一次任务）→ Loop Engineering（持续推进直到完成、失败或交给人）。

## 【问题】
什么是「上下文腐蚀」和「注意力预算耗尽」？为什么长上下文会让模型「变笨」？

## 【回答】
- **上下文腐蚀**：**随着上下文窗口中 token 数量增加，模型准确回忆信息的能力会下降**。这不是断崖式下降，而是**梯度下降**——模型在长上下文中仍然能力强大，但**信息检索和长程推理的精度会持续降低**。
- **注意力预算耗尽**：**每引入一个新 token 都会消耗注意力预算**；低质量的 token 会「稀释」高质量信息；**关键信息可能被噪声淹没**。

由此推论：**并不是「塞进去的信息越多越好」**——上下文里满是低信号 token 时，模型「看」到了所有内容，却难以聚焦真正重要的那一行。类比（Anthropic）：一个软件项目由轮班工程师负责，每个新工程师到来时对上一班发生的事情毫无记忆——**不加管理的上下文，让 AI 像一个永远失忆的轮班工程师**。

## 【问题】
有效的上下文工程有哪些原则？「即时（Just-in-Time）上下文」指什么？

## 【回答】
四项原则：

1. **分层式信息组织**：按概要层 / 技术层 / 经验层组织信息，而非一锅端。
2. **「即时」上下文策略（Just-in-Time Context）**：**维护轻量级索引，运行时按需动态加载，而非预加载全部内容**——这是与「把整个仓库塞进上下文」的根本区别。
3. **上下文压缩与笔记系统**：压缩时**保留架构决策 / 未解决 bug / 实现细节，丢弃冗余输出**。
4. **工具设计的上下文效率**：工具要**自包含、返回精简、边界清晰、发挥模型优势**。

反面案例（Anthropic）：**臃肿的工具集，覆盖过多功能或导致「用哪个工具」的决策点模糊不清**；**如果人类工程师无法明确说出在给定情况下应该使用哪个工具，AI 智能体也不能做得更好**。

落地类比（经验沉淀时机）：把历史经验写进 `context/experience/`（如「商品发放」的历史问题），Agent 执行对应需求时**自动加载、主动提醒**——而不是写一份「注意事项」文档期望大家会看。沉淀演进节奏：同类需求做 5 次以上 → 封装 Skill；Skill 被调用 10 次以上 → 封装 Command。
