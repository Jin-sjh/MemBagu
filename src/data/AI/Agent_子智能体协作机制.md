# 子智能体协作机制

## 【问题】
子智能体有哪三个关键特性？

## 【回答】
- **独立上下文**：每个子智能体的对话是**从零开始**的，它不知道主智能体之前和你聊了什么，只知道主智能体传给它的那段任务描述。这既是**优势**（不被无关信息干扰），也是**限制**（需要的信息必须显式传入）。
- **过程隔离**：执行任务过程中的所有工具调用、中间结果、思考过程，**全部留在自己的上下文里**。主智能体可以只接收最终结果的摘要或文件路径（需在指令中明确要求），从而节省空间——一个子智能体可能读了几十个文件、跑了几百行代码，但回到主智能体这边只多了一段简短的「汇报」。这正是「**上下文窗口快满了，有没有比清空更优雅的解法**」的答案。
- **同时开工**：子智能体有各自独立的上下文，因此可以独立运行、互不打扰，这是**并联**组合方式得以实现的基础。

## 【问题】
给子智能体派活，要解决哪三个实操问题？

## 【回答】
1. **怎么触发？两种方式**
   - **自动委派**：你不需要点名，主智能体根据每个子智能体的 description 自行判断并委派（在 Claude Code 里会看到它自动使用 Agent 工具）。内置三个主要子智能体：**Explore**（专门搜索和分析代码，只读不写）、**Plan**（在规划模式下做调研，只读不写）、**general-purpose**（通用，能读能写能执行命令）。
   - **显式调用**：你直接在对话中点名（如「用 code-reviewer 子智能体检查我最近的提交」），部分平台支持 `@子智能体名称`。
   
   不管哪种方式，触发后流程都一样：**接收任务 → 在独立上下文中工作 → 把最终结果返回给主智能体**。
2. **怎么传信息？** 它不知道主智能体之前聊了什么，缺的信息必须**显式传入**，或存成文件让它去读。
3. **怎么描述任务？** 好的任务描述要包含**四个要素**——
   - **目标**：按叙事风格写一篇文章，将其保存为 draft-a.md；
   - **约束**：加载 writing-style 技能，开头用故事场景切入，不用「首先/其次/最后」；
   - **输入**：读取 source.md（原始素材）、analysis.md（素材分析结果）和 outline-a.md（大纲）；
   - **验收**：① 字数 2000~3000；② 每个论点有素材支撑；③ 文件保存到当前目录。
   
   四个要素全齐，子智能体拿到任务不需要追问就能开工；否则它不知道写什么主题、什么风格、篇幅多长、素材在哪里，**只能猜，大概率猜不准**。

## 【问题】
子智能体有哪些局限？使用时要注意什么？

## 【回答】
- **信息在交接时会丢失**：主智能体派任务时，子智能体并不知道主智能体之前和你聊了什么。你们讨论过的偏好、达成的共识、前几轮迭代积累的经验**全不在子智能体的上下文里**。如果这些上下文很重要，你得在任务描述里显式写清楚，或者**把关键信息存成文件让子智能体去读**。
- **子智能体之间信息隔离**：子智能体 A 和 B 各有独立上下文，A 发现的关键信息 B 不会自动知道。它们之间**不能直接通信**，必须通过主智能体中转，或者通过文件系统间接共享（A 把发现写入文件，B 去读那个文件）。

简单规则：**一个上下文能搞定的事，别派子智能体。拆分带来隔离优势，也带来信息传递成本。**

## 【问题】
复杂环节该加技能让智能体自己干，还是派子智能体出去干？

## 【回答】
两者的核心差异在于：**在什么场景下、由谁来做、是否共享上下文**。

- **用技能（轻任务，要看过程）**：任务不重，主智能体自己就能搞定。比如会议纪要分析，读一份转录稿、提取有价值的信息，中间推导过程不会太长，主智能体的上下文窗口完全放得下，且**你能全程看到它的思考过程**。
- **用子智能体（重任务，只要结果）**：任务极耗资源、中间过程很长、会产生大量中间结果或需要多路并行。比如写一篇三千字的文章，中间有好几轮思考和修改，过程产物可能有上万字——全堆在主上下文里会挤占后续任务空间。派子智能体去做，并要求**只返回文件路径和一句话摘要**，就能解决。

判断标准：**对于复杂任务拆出来的子任务，你需不需要了解其执行的中间过程？只要结果、不看过程，就用子智能体。**

## 【问题】
什么时候该用智能体团队（agent teams）而不是多个子智能体？

## 【回答】
如果子任务之间**需要协调**，比如全栈开发中后端改了接口格式、前端得知道，这种情况就需要智能体团队——**团队成员之间可以直接发消息、共享任务列表，不需要主智能体当传话筒**。

判断只问一个问题：**子任务之间需要互相通信吗？需要 → 智能体团队；不需要 → 子智能体。**

子智能体方案简单又省资源，智能体团队更适合工程开发这类需要多角色紧密协作的场景。
