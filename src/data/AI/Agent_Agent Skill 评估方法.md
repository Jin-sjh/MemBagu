# Agent Skill 评估方法

> 来源：agentskills.io/skill-creation/evaluating-skills（Agent Skills 官方文档 — Evaluating skill output quality）
> 补充来源：Anthropic，《Improving skill-creator: Test, measure, and refine Agent Skills》（2026-03-03），https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills
> 适用场景：编写完一个 Skill 后，如何系统性地验证它是否跨提示可靠、是否优于无技能状态，并持续衡量、比较和改进。

## 【问题】
什么是技能评估（skill evaluation）？为什么写完 Skill 后还需要专门的评估？

## 【回答】
写完技能后在某个提示上“似乎可用”并不代表**可靠**。结构化评估（evals）用于回答三个核心问题：是否**跨多种提示可靠工作**、**边缘情况如何处理**、**是否优于无技能状态**。评估的真正价值在于提供**系统改进的反馈循环**——把“感觉能用”变成可度量、可迭代的客观依据。

## 【问题】
一个测试用例（test case）由哪几部分组成？应该存放在哪里？

## 【回答】
一个测试用例包含三部分：

- **Prompt**：真实的用户消息，即用户实际会输入的内容。
- **Expected output**：成功状态的人读描述（首轮不写断言，先描述期望）。
- **Input files**（可选）：技能需要处理的文件。

测试用例写在技能目录内的 `evals/evals.json` 中（例如 `csv-analyzer` 技能附带 2 个用例：销售 CSV 制图、清理客户 CSV 缺失邮箱）。注意：除 `evals/evals.json` 需手动编写外，其余 JSON 都由评估过程自动生成。

## 【问题】
编写良好的测试提示有哪些技巧？

## 【回答】
从 **2–3 个测试用例**开始，不要过度投入；随后注意以下几点：

- **变化提示**：用不同措辞、细节程度、正式度（随意 vs 精确）覆盖多样性。
- **覆盖边缘情况**：至少包含一个边界条件，如畸形输入、模糊指令。
- **使用真实上下文**：提及具体文件路径、列名、个人情境，避免“处理这些数据”这类模糊提示。
- **暂不写 pass/fail 检查**：先看首轮输出长什么样，再据此添加断言（assertions）。

## 【问题】
运行评估的核心模式是什么？工作区（workspace）应如何组织？

## 【回答】
核心模式是**每个测试用例运行两次**——**有技能**与**无技能**（或旧版本），提供**基线对比**，这样才能判断技能到底带来多少收益。

推荐的工作区结构：

- 技能目录 `csv-analyzer/` 含 `SKILL.md` 与 `evals/evals.json`。
- 工作区 `csv-analyzer-workspace/iteration-1/` 下，每个测试用例有 `eval-xxx/` 目录，内含 `with_skill/` 与 `without_skill/`（改进现有技能时用 `old_skill/`）。
- 子目录内含 `outputs/`、`timing.json`、`grading.json`；顶层 `benchmark.json` 聚合统计。

关键约束：每次运行都要从**干净上下文**开始（子代理环境天然隔离，否则用独立会话）；基线运行使用相同提示但不给技能路径；改进时先用 `cp -r` 把旧版快照为 `skill-snapshot/` 再对比。

## 【问题】
什么是断言（assertion）？好的断言和弱的断言有什么区别？

## 【回答】
断言是**可验证陈述**，在首轮输出之后添加（先见“好的样子”再写）。

- **好的断言**：“输出是有效 JSON”、“柱图有标签轴”、“报告至少 3 条建议”——**可程序化 / 具体 / 可数**。
- **弱的断言**：“输出好”（模糊）、“精确使用某短语”（脆弱，易误判）。

并非一切都需要断言：风格、视觉设计等主观项更适合**人工审查**而非断言。

## 【问题】
如何对输出评分（grading）？有哪些原则？

## 【回答】
对每条断言评 **PASS/FAIL** 并附**具体证据**（引用实际输出内容，而非仅给意见）。

- 简单做法：交给 LLM 评判；能用代码校验的（合法 JSON、行数、文件尺寸）用验证脚本更可靠。
- **评分原则**：PASS 必须给出具体证据，不给“怀疑”好处（有“Summary”标题但内容空洞即判 FAIL）；同时审查断言本身，若太易 / 太难 / 不可验证则应修正。
- **盲比较**：把两个版本的输出隐去版本号交给 LLM 裁判，评整体质量（组织、格式、可用性），以补足断言评分的盲区。

## 【问题】
如何汇总结果（benchmark.json）？delta 和 stddev 分别代表什么？

## 【回答】
`benchmark.json` 汇总 `with_skill` 与 `without_skill` 的 `pass_rate`、`time_seconds`、`tokens` 的均值与 stddev，以及两者的 `delta`。

- **delta**：体现技能的**成本**（更多时间 / token）与**收益**（更高通过率）之间的权衡。
- **stddev**：仅当多次运行时才有意义；早期应聚焦**原始通过数**和 **delta**，不必过度关注方差。

## 【问题】
分析模式时，针对“两配置都过 / 都败 / 有技能过无技能败”这三类结果分别该如何处理？

## 【回答】
- **两配置都过**的断言：移除或替换（无用，只会虚增通过率）。
- **两配置都败**的断言：调查根因（断言写破 / 题目太难 / 查错了对象）。
- **有技能过、无技能败**的断言：重点研究（这是技能的明确价值点，理解它为何有效）。
- 结果不一致（高 stddev）：收紧指令或排查 flaky（随机性失败）。
- 时间 / token 异常（如慢 3 倍）：读执行 transcript 找瓶颈。

## 【问题】
Anthropic 更新后的 `skill-creator` 还提供了哪些测试、衡量和比较能力？

## 【回答】
Anthropic 将软件工程中的**测试—衡量—比较—迭代**引入 Skill 开发。`skill-creator` 可以帮助作者编写评测、运行基准测试，并在模型演进时检查技能是否仍然有效。基准测试跟踪**评测通过率、耗时和 Token 使用量**，结果可由用户保存到本地、仪表板或 CI 系统。

评测可并行运行：每个测试由独立智能体在**干净上下文**中执行，并记录独立的 Token 与时间指标，避免顺序执行的上下文交叉污染。比较器智能体则可对两个技能版本，或“加载技能 / 不加载技能”的结果进行**盲 A/B 比较**，帮助判断修改是否真正改善质量，而不是只让某一项断言得分上升。

对能力提升型 Skill，还要定期检查基础模型是否已经在无 Skill 状态下通过原有评测：若是，说明 Skill 所编码的技术可能已成为模型的默认能力，Skill 可能不再必要；对偏好编码型 Skill，则仍需验证其是否忠实执行团队工作流。

## 【问题】
如何迭代改进 Skill？完整的改进循环是怎样的？

## 【回答】
三个信号源驱动改进：**失败断言**、**人反馈**、**执行 transcript**（揭示为什么会错）。Anthropic 给出的典型闭环是：先为真实提示定义理想结果，运行评测定位失败场景，修改 Skill，再通过基准测试比较新旧版本；模型更新后重新运行回归评测，持续观察通过率、耗时和 Token 成本。

给 LLM 提改进建议的准则：

- **从反馈泛化**：修底层问题，而非打窄补丁。
- **保持精简**：少而好的指令优于穷举；去掉浪费性的工作；过度约束时尝试删除。
- **解释 why**：推理型指令（“做 X 因 Y 致 Z”）优于死板指令。
- **捆绑重复工作**：若反复写相似脚本，则归入技能 `scripts/`。

改进循环（The loop）：

1. 把信号 + 当前 `SKILL.md` 交给 LLM 提修改建议。
2. 审查并应用修改。
3. 在新的 `iteration-<N+1>/` 重跑评估。
4. 评分并聚合。
5. 人工审查，重复循环。

**停止条件**：已达到满意效果 / 反馈持续为空 / 相邻迭代之间无显著提升。

## 【问题】
如何评估 Skill 的触发可靠性，而不只是评估输出质量？

## 【回答】
输出评测成立的前提是 Skill 在应该触发时被加载。描述过于宽泛会误触发，过于狭窄会漏触发。可让 `skill-creator` 根据示例提示分析现有描述，识别触发问题并提出修改建议，同时兼顾减少误报和漏报。Anthropic 在文档创建 Skill 上测试时，**6 个公开 Skill 中有 5 个的触发效果得到改善**。
