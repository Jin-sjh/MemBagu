# 告警排查 Agent 实战

## 【问题】
得物技术用 LLM Agent 重构告警排查的背景和痛点是什么？为什么要做 Troubleshooter？

## 【回答】
传统告警排查的痛点：告警一来，人要在**日志平台、APM、链路追踪系统三个平台来回切换**，靠经验拼凑数据。这类排查通常耗时 **10～30 分钟**，主要耗时**不在分析本身，而在频繁登录多平台、拼凑分散数据**；而且排查效率**高度依赖个人经验**，新人面对告警往往不知道先看什么。

Troubleshooter 用 LLM Agent 自动完成**数据采集、根因分析、处置建议生成**。上线后**中位数排查耗时从 20 分钟左右降到 4.4 分钟**，覆盖 **11 个服务、10+ 种告警类型**。它不是替代运维，而是把"登录多平台、切换入口、凭经验猜方向"的机械操作交给 AI，让人专注需要判断力的决策。（来源：得物技术，作者溪石，2026-06-03）

## 【问题】
Troubleshooter 的整体架构设计遵循什么核心原则？为什么选 Spring AI Alibaba 而不是自建 ReAct 循环？

## 【回答】
核心原则：**告警接入与排查执行解耦**——接入层只负责接收和持久化，排查由独立调度器**异步触发**，接入和排查互不阻塞。

框架选型上选 **Spring AI Alibaba 的 ReactAgent**（而非自建 ReAct 循环），理由是**省事**：框架已内置**推理循环、工具拦截器（ToolInterceptor）、模型拦截器（ModelInterceptor）**，开箱即用。底层实现经典 ReAct 循环：**LLM 思考 → 选择工具 → 执行工具 → 观察结果 → 继续思考 → … → 输出结论**。

## 【问题】
Troubleshooter 的完整排查链路（核心流程）由哪几步组成？

## 【回答】
完整链路：
1. **告警接入**：接收告警数据，生成唯一**事件 ID**。
2. **指纹生成**：提取 5 维度特征（**服务名、告警类型、错误模式、指标名、错误摘要**），生成 **32 位 MD5 指纹**，用于知识库去重与复用。
3. **知识匹配**：检索相似历史记录，匹配成功则**直接复用历史结论**。
4. **AI 排查**：**Supervisor Agent** 编排，执行 ReAct 推理循环。
5. **结论验收**：独立 **Validation Agent** 检查根因明确性与处置建议完整性。
6. **报告推送**：生成 **Markdown 报告**推送到飞书群组。
7. **知识沉淀**：运维确认后的结论存入知识库，形成闭环。

## 【问题】
SupervisorAgent 为什么"不是简单地调 Prompt"？它真正需要什么？

## 【回答】
很多人的误区是"AI 排查 = 构造一个 Prompt 丢给大模型"。但 LLM **无法凭空知道**服务的当前 QPS、错误日志里写了什么、调用链哪个环节超时——**它需要工具**。

SupervisorAgent 的核心是**工具集成**：LLM 负责推理调度，真正的证据来自被调用的排查工具（日志、指标、链路）。这呼应 Agent 工程的基本判断——**模型既当运动员又当裁判会翻车，做判断需要工具与外部真实数据支撑**。

## 【问题】
四个排查工具（queryLogs / queryMetrics / queryTrace / queryEndpointErrors）各自的设计哲学是什么？

## 【回答】
- **queryLogs（日志查询与分析）**：排查第一入口，通过 **WebSocket** 连接日志平台，按优先级分批查询：**traceId > exceptionName > endpoint > keywords**；每批结果经 LLM 异步分析后汇总；并用 **LogDeduplicator** 去重，防止同一请求的多条日志重复占据分析窗口。
- **queryMetrics（监控指标查询）**：支持 **10 个维度**指标（qps、rt、errorRate、containerCpu、containerMemory、percentileRt、gcCount、gcRt、qpstop10、rttop10），LLM 按告警类型自主选择维度，如 OOM 告警通常选全维度、接口 RT 突增则关注 qps/rt/percentileRt/rttop10。**MetricService 接口对不同环境提供可插拔实现**。
- **queryTrace（分布式链路追踪）**：带 traceId 时直接查 APM 获取 **Span 树**，渲染为格式化文本，识别哪个下游变慢、哪个环节抛异常。
- **queryEndpointErrors（接口错误排查）**：无 traceId 但有接口路径时，查该接口错误日志，**正则提取所有 traceId** 逐个分析；防护逻辑：当 endpoint 为根路径 **"/"** 时**拒绝执行**（匹配所有请求无排查意义）。

## 【问题】
Troubleshooter 怎么做到"同一个排查用不同策略"？动态策略组装是怎么实现的？

## 【回答】
不同服务、不同告警类型的排查思路差异很大（OOM 看 GC 与堆内存，接口超时看 QPS 突变与下游延迟）。设计**策略匹配机制**：按 **(service_name, alert_type)** 从数据库**精确匹配**排查策略，未匹配时用**内置兜底策略**；运维可通过前端页**在线编辑策略内容，无需改代码**。

指令拼装公式：**instruction = ROLE + strategy(service_name, alert_type) + OUTPUT_FORMAT**——把角色、策略、输出格式三段动态组合，让 LLM 在每个具体场景下拿到针对性指引。

## 【问题】
外部系统（日志平台 / APM）不稳定时，怎么防止单个工具超时拖垮整个排查？

## 【回答】
每个工具调用用 **ToolExecutor** 包装，通过**独立线程池 + Future.get(timeout)** 实现超时控制。超时不报失败，而是**返回降级消息**（如"指标查询超时，继续使用已有信息进行排查"），**LLM 基于已有证据继续推进**，不会因单个工具超时导致整个流程中断。这是 Agent 工程里"**工具服务异常要走超时隔离与降级**"的典型实践。

## 【问题】
Troubleshooter 怎么保证 AI 权限安全？它能否直接改系统？

## 【回答】
排查 Agent **仅拥有只读权限**，不涉及任何变更操作（改配置、重启服务、回滚代码都不行）。所有优化建议**仅为文本输出，需人工二次确认后方可执行**。Agent 无法访问数据库、无法调用写接口、无法修改运行中系统配置。这是把"高风险动作"固化在权限边界、而非靠 Prompt 约束的体现。

## 【问题】
Troubleshooter 从哪几个维度控制 LLM 幻觉、保障结论质量？

## 【回答】
四维度幻觉控制体系：
1. **规则格式校验（零 LLM 调用）**：第一轮直接检查 5 个必要章节是否存在、指标表格格式是否规范，毫秒级完成。
2. **独立验收 Agent（内容质量审查）**：检查结论是否明确、核心判定是否合理、根因是否有**工具证据**、建议是否可执行。
3. **多轮交叉验证**：不同工具返回必须相互印证（queryLogs 与 queryTrace 交叉、queryLogs 与 queryMetrics 交叉、时间线一致性校验）才能形成结论。
4. **重试机制**：格式问题**不消耗**重试配额；内容问题最多重试 **2 次**；验收 Agent 异常时**宽容通过**。

效果数据（2026-04-21~05-14）：验收**首次通过率约 60%**、二次通过率约 38%、耗尽兜底率约 2%。

## 【问题】
排查过程的可观测性是怎么实现的？运维怎么看到 AI 每一步在做什么？

## 【回答】
两层可观测：
1. **文件系统日志**：每次排查在文件系统创建独立目录（按事件 ID，如 `logs/evt-20260514153012345-001/`），**LoggerInterceptor** 与 **ToolInterceptor** 记录所有 LLM 输入/输出和工具调用/返回。
2. **内存进度追踪**：**EventProgressTracker** 在内存维护每个事件实时状态（当前阶段、当前策略描述），前端通过 **3 秒轮询**获取进度更新。

这让排查不再是黑盒，呼应"Agent 可观测性要记录 Plan / Action / Observation / State Diff / Context Source / Eval Result"的工程要求。

## 【问题】
Troubleshooter 落地时踩过哪些坑？怎么解决？

## 【回答】
两个典型坑：
1. **环境统一映射**：告警里的环境标识五花八门（"xxprd""生产""XX石""prd"实际都指生产），且日志平台与 APM 的环境代码不同。解法：用 **EnvironmentProperties** 集中管理 **5 套环境别名映射**（精确匹配 + 包含匹配），**tool 方法直接使用告警事件里的环境字段，不让 LLM 自行映射**，避免 LLM "翻译"环境名出错。
2. **LLM 调用多 Key 限流**：LLM 网关有频率限制，单 Key 高频会限流。解法：实现 **RoundRobinChatModel**，配置多个 API Key，**按事件 ID 哈希取模固定分配**——同一排查过程所有调用用同一个 Key，避免上下文切换。

## 【问题】
Troubleshooter 的真实排查案例与效果数据如何？后续迭代方向是什么？

## 【回答】
案例（效率网关超时）：SupervisorAgent 在 **4 分钟内**完成 3 次工具调用 + 1 轮验收修正，逐步逼近根因；第 1 次验收未通过（缺必填字段），第 2 次通过（紧急程度"观察"、置信度"高"）。工具调用总计 88s + LLM 推理 + 验收，人工保守需 10~20 分钟。

后续方向（按优先级）：**多 Agent 并行排查**（日志与指标并行）、**指纹知识库**（秒级匹配已知问题）、**跨服务关联分析**（级联故障）、**自动处置能力**（从"排查+建议"升级到"排查+自动修复"）、**向量语义检索**（语义级相似问题检索）。
