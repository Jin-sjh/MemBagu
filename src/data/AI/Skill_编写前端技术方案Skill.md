# 编写前端技术方案Skill

## 【问题】

什么是"前端技术方案" Agent Skill？为什么要把技术方案经验沉淀为 Skill？

## 【回答】

**"前端技术方案" Agent Skill 是一个基于上下文、主动推理、分步生成的架构决策助手**，它把前端方案设计的经验沉淀为一套 AI Agent Skill，而不是一个简单的"模板填充器"。动机：前端研发流程中"写技术方案"往往最令开发头疼却又极其关键——它不像写业务代码有即时反馈，却决定项目未来半年甚至更长时间的可维护性与稳定性。现实中技术方案要么被写成流水账，要么遗漏非功能需求（性能、安全），要么技术选型缺乏客观依据。通过将架构逻辑固化为 Skill，**把资深架构师的经验进行"平民化"复制**，并规范团队技术产出质量——每个需求有据可查，每次选型有理可依。

## 【问题】

如何定义 Skill 的"灵魂"（身份、原则与边界）？为什么先写身份？

## 【回答】

必须先在 `SKILL.md` 顶部用强指令锁死 AI 的立场，否则它会变成"万能答题器"给出泛泛而谈的内容。示例定义包含三部分：

- **角色定位**：如"你是一位拥有 10 年以上前端架构经验的 Staff Engineer。你极度务实、注重落地、讨厌过度设计。"
- **核心原则**：1. **业务优先**（方案必须回指业务价值，拒绝纯技术炫技）；2. **数据驱动**（技术选型必须附带客观对比维度：生态、性能、包体积、学习成本）；3. **非功能需求是红线**（必须显式提及性能预算 Core Web Vitals、安全策略 XSS/CSRF、兼容性及异常降级方案）；4. **决策留痕**（每个关键选择记录否决理由，便于 Review）。
- **触发场景**：明确"帮我写一个 XX 功能的技术方案"等激活条件。

作用：**避免"水货方案"**（只有"我要用 React + TypeScript"，没有"为什么不用 Vue 3"）；**主动约束** AI 必须询问并发量、目标浏览器版本等易被忽略的边界条件。

## 【问题】

Skill 如何"读懂上下文"？多模态输入解析层如何设计？

## 【回答】

技术方案不能凭空产生，Skill 需要像真人架构师一样先"嗅探"现有项目环境和业务上下文，包含两层：

**1. 自动化上下文探测（MCP / Shell 工具）**——启动时自动执行：读取 `package.json` 识别技术栈（框架/状态管理/构建工具）；分析 `src/` 目录分层确认架构模式；搜索 `TODO`/`FIXME`/`hack` 识别历史遗留坑；查看最近 Commit 了解开发活跃度与改动范围。

**2. 主动交互式澄清（ReAct 模式）**——在 `SKILL.md` 中嵌入**强制拦截逻辑**（不可跳过）：生成"技术选型"和"排期评估"章节前必须确认【业务量级】（DAU/峰值 QPS，决定 SSR 或边缘缓存）、【终端覆盖】（IE11？移动端占比，决定 Polyfill 策略）、【后端依赖】（上游 API 是否有 SLO 保障，决定容错与骨架屏）、【上线窗口】（发版日/灰度 AB 实验，决定发布策略）。技巧：**将"提问"写进流程节点（Step 2 -> 提问 -> Step 3），强制 AI 在缺乏数据时停下来，而不是瞎编数据**。

## 【问题】

Skill 的 References（领域知识库）如何设计？为什么要把规范拆分到参考文件？

## 【回答】

一个 Skill 的强大取决于 References 参考文件——**不要试图把公司规范塞进庞大的 `SKILL.md`，而应拆分引用**，并在 SKILL.md 中约定"遇到对应章节必须读取"。推荐文件：

| 文件名 | 内容 | 作用 |
| --- | --- | --- |
| `tech_stack_matrix.md` | 团队允许使用的技术清单及版本要求 | 防止引入未经审批的第三方库 |
| `performance_budget.md` | 不同页面类型的 FCP/LCP 硬性阈值 | 让 AI 设计时自动核算资源体积 |
| `security_checklist.md` | 前端安全自检项（Cookie/CSP/脱敏） | 确保方案包含安全章节 |
| `template_arch.md` | 标准架构图模板（PlantUML/Mermaid） | 确保输出统一美观 |
| `estimation_benchmark.md` | 各类型模块的历史平均人天耗时 | 让排期估算有理有据 |

调用示例：生成"性能设计"章节时，必须先读取 `references/performance_budget.md`，按页面类型套用性能预算，计算第三方库总 gzip 体积并给出是否超预算的结论。

## 【问题】

"方案生成流水线"的 8 个原子步骤是什么？

## 【回答】

这是 Skill 的核心逻辑，将优秀技术方案拆解为 **8 个原子步骤**，AI 依次遍历绝不跳步：

- **Step 1 背景与目标（Backward Design）**：描述现状痛点（结合线上数据/报错截图），用 1 句话概括成功标准（如"用户可在 3 秒内完成审核操作"）。
- **Step 2 范围界定（Scope）**：In-Scope 明确包含模块；Out-of-Scope 明确不做什么（防需求蔓延）；列出依赖方接口及交付时间。
- **Step 3 技术选型（Tech Selection）**：关键决策点提供 2-3 个候选方案，对比性能（包体积/渲染速度）、维护性（Star/更新频率）、团队熟悉度、架构契合度；**最终决策给出 3 条以上不可辩驳的理由**。
- **Step 4 架构设计（High-Level Design）**：绘制模块分层图（UI→业务逻辑→数据→后端交互）和核心流程图，用 Mermaid/PlantUML 输出便于渲染。
- **Step 5 数据结构与 API 契约（Data & API）**：定义核心实体类型（TypeScript Interface）和 API 请求/响应结构（含错误码映射表）。
- **Step 6 非功能性设计（NFR）——重点强化**：性能（懒加载/预加载、LocalStorage/IndexedDB/CDN 缓存）、安全（输入过滤、RBAC、水印防篡改）、监控（RUM 埋点、性能指标上报）、容灾（超时重试、表单草稿恢复）。
- **Step 7 排期与里程碑（Delivery Plan）**：根据 `estimation_benchmark.md` 拆子任务给出开发/自测/联调/提测时间节点，识别关键路径风险。
- **Step 8 风险评估与备选方案（Risks & Rollback）**：技术风险（浏览器兼容坑、库停更）、业务风险（政策变化）、**回滚预案**（如 Feature Flag 开关）。

## 【问题】

如何增强 Skill 输出的"表现力"？编写 Skill 有哪些注意事项？

## 【回答】

**增强表现力（交互式 Markdown 渲染）**：技术方案最终要给人（Reviewer）看，需生成结构化高可读内容——开头生成完整 **TOC 目录锚点**；用**表格**展示选型对比（决策记录表）；**Mermaid 图表**原生支持复制即用；用 `> ⚠️ 风险提示` 和 `> 💡 设计考量` 高亮重点。

**注意事项（避坑）**：**不要把 Skill 写成 Prompt 巨无霸**（善用 `references/` 拆分知识防注意力丢失）；**强制交互**（缺少数据时停下来问用户，不闭门造车）；**咬死规范**（用流程控制 Step 1->2->3 确保不跳过非功能性设计）；**防幻觉**（AI 可能编造不存在的 package.json 版本或 API，需通过工具调用/Function Calling 实际读取文件而非依赖训练数据）；**防过度泛化**（用户说"写一个通用方案"时应拒绝并反问指定具体业务场景）。推荐目录结构：`frontend-tech-design-skill/` 下含 `SKILL.md` + `references/`（performance_budget / security_checklist / estimation_benchmark / ui_framework_rules）。
