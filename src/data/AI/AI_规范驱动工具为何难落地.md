# 规范驱动工具为何难落地

## 【问题】
什么是规范驱动开发（SDD）工具（以 speckit / openspec 为代表）？它们的理想化前提是什么？

## 【回答】
规范驱动开发（Spec-Driven Development，SDD）的思路是：**先用规范（Spec）把「要写什么」定清楚，再让 AI 按流程执行**。以 speckit 和 openspec 为代表：

- **speckit**：用**宪章（不可变原则）**约束流程，假设「需求清晰、可一次性规划」，AI 按既定流程从零开始推进开发。
- **openspec**：强调 **Delta（提案式）变更**：用 proposal 描述期望变更，再通过 `archive` 把变更合并回主 Spec。

它们的共同理想化前提是：**需求是清晰的、可一次性规划的、流程可以从零开始**——即工具为「标准化项目 + 清晰需求」而设计。

## 【问题】
speckit 在企业真实研发场景中为什么会碰壁？

## 【回答】
speckit 的四个关键缺陷：

1. **流程过于理想化**：假设需求可一次性规划；但企业真实需求是**动态的、多方博弈的、持续变化的**——多方博弈 → 动态调整 → 并行推进 → 持续扯皮 → 边做边改，理想流程根本走不完。
2. **无法处理「考古」需求**：真实开发必须先「考古」（历史坑点、现有能力、配置规范），而工具流程从零开始定义，**缺失「上下文检索」机制**——AI 看不到历史经验、业务边界、配置规范。
3. **知识不会沉淀**：每次执行都从头开始，实施中发现的坑不会被记录、排查信息丢失，**边际成本恒定**（第 1 次和第 N 次一样慢）。
4. **宪章系统僵化**：9 条不可变原则适合标准化项目，但**不适合企业定制场景**（历史债务、框架限制、合规要求）。

## 【问题】
openspec 的 Delta / Archive 机制为什么「理论美好、现实骨感」？

## 【回答】
openspec 用「提案（Delta）+ 归档（Archive）」管理 Spec 演进，存在四个现实问题：

1. **Delta 机制前提不成立**：假设需求可以「提案化、串行化」，但真实场景是**多线并行、动态调整**。
2. **Fail-Fast 的代价**：`openspec archive` 在冲突时直接**报错退出且无自动解决策略**；人工解决需同时在脑中持有「主 Spec 当前状态」和「Delta 期望变更」两套信息，**认知负担极大**——理论上保证一致性，实际上成为阻塞点。
3. **强依赖命名的脆弱性**：产品叫「用户激励」、运营叫「活动奖励」、研发叫「商品发放」——**跨角色命名不一致直接导致归档失败**。
4. **Archive 只是「合并」，不是「学习」**：`F(CurrentSpec, DeltaSpec) → NewSpec` 缺失了关键维度，完整公式应为 `F(CurrentSpec, DeltaSpec, Context, Lessons) → NewSpec + Knowledge`——只归档结果，不沉淀过程知识。

## 【问题】
从 speckit / openspec 的失败中能提炼哪些通用教训？

## 【回答】
四个通用设计教训：

1. **忽视人的认知负担管理**：**工具应该适配人的工作模式，而不是强行改变它**。
2. **忽视执行过程的知识价值**：只关注「规范」和「结果」，**忽视「过程」中的排查信息**——排查过程本身是知识，却被丢弃。
3. **忽视复利效应**：传统工具帮你「做事」但知识不留下；正确做法是**每次执行都让下一次更快、更稳**。
4. **Spec 详细程度的悖论**：**Spec 越详细 → 越接近代码本身 → 相当于维护两份「代码」**；**Spec 越简略 → 越难指导 AI → 失去规范的意义**。

核心替代思路（与 speckit 的本质差异）：speckit 依赖「**一个 Agent 记住所有事情**」，上下文持续累积，到 Implement 阶段时窗口已经很满；正确做法是 **Subagent + 结构化状态传递**——状态通过文件传递，而非上下文累积，让知识沉淀在工具链里而不是会话里。
