# 企业级 Agentic RAG 架构

## 【问题】
企业级 Agentic RAG 项目（如社区 ragent）整体是怎么分层的？接入层、编排层、工具层各自做什么？

## 【回答】
以 ragent（Java 17 + Spring Boot 3.5 后端、React 18 前端、Milvus 2.6 向量库，约 4 万行后端 / 1.8 万行前端 / 20 张业务表，已超越 Demo）为例，典型分层：

- **接入层（网关/API）**：鉴权、限流、TraceId、租户隔离。
- **意图与对话层**：意图分类、问题重写、拆分、澄清。
- **检索编排层**：意图定向通道 + 全局向量通道的融合、重排、溯源。
- **工具 / MCP 层**：外部 API / 业务系统调用。
- **LLM 编排层**：记忆窗口、摘要、路由、熔断、降级、成本与配额。
- **持久化层**：会话、文档块、向量索引、审计。

核心结论：企业级 Agent 不是"能跑通链路"的 Demo，而是**领域建模 + 持久化 + 可运维**的生产系统。

## 【问题】
这类企业级 RAG Agent 在检索与意图体系上有哪些可借鉴的设计？

## 【回答】
几个关键设计：

- **多路检索引擎**：意图定向通道（按意图缩小范围、减少噪声）+ 全局向量通道（广域召回、防漏检），融合常用**重排序（rerank）/ 加权融合**，并保留**可追溯的检索决策日志**。
- **意图识别体系**：树形分类（由粗到细，对齐业务流程与权限域）；**置信度 + 澄清引导**——低置信度不强行回答，而是追问槽位或列出候选意图（与企业客服/工单系统一致）。
- **问题重写与拆分**：口语化问题改写为检索友好查询；多跳任务拆成子问题分别检索与综合，降低单次上下文压力。
- **会话记忆**：滑动窗口保留近期消息，窗口前历史压成摘要以控 token（需处理**摘要与事实一致性**）。
- **模型路由与容错**：三态熔断器（关闭/半开/打开）避免拖垮整条链路；主模型失败自动降级到备用模型或缩小任务（如仅检索不做生成）。
- **文档入库 ETL 与全链路追踪**：ETL 的清洗/分块/元数据/版本/增量更新 + 溯源（provenance）决定知识库"越用越准"；TraceId 贯穿网关→检索→LLM→工具体排障与 SLA 归因。

## 【问题】
相比 Claude Code 这类开发者 CLI Agent，企业级 RAG Agent（如 ragent）在记忆、检索、权限、可观测上有什么本质区别？

## 【回答】
核心差异在**场景与基础设施侧重**不同：

| 维度 | Claude Code 系（开发 CLI） | 企业级 RAG Agent（ragent） |
|------|------|------|
| 主场景 | 开发者 CLI、代码库、工具执行 | 企业知识问答、流程型 Agent |
| 记忆侧重 | 会话、compact、团队记忆同步 | 业务表、审计、长期知识库 |
| 检索 | 代码搜索、Grep、LSP 等工具能力 | 向量库 + 业务过滤 |
| 权限 | 工具级审批、沙箱、Hook | 多租户、数据域、合规 |

结论：**两者是互补阅读**——Claude Code 系看"工具执行与本地编排"，ragent 系看"企业级检索、意图与可运维"，设计时按自身主场景取舍。
