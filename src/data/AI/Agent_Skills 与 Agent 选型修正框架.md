# Skills 与 Agent 选型修正框架

## 一、漏洞拆解：为什么原判断公式会产生歧义

原简化公式：

> 能写出输入 A→执行 B→输出 C 固定步骤 → Skill；只知道目标、不知道步骤 → Agent

漏洞点：很多业务**有书面标准 Workflow（步骤清单固定），但运行时每一步怎么做，不能硬编码写死**。

示例：财务报销标准流程：上传凭证→验真→预算校验→审批流转→打款。

- 纸面流程顺序固定
- 但运行时：凭证验真失败怎么重试？预算不足走哪个备用审批分支？不同金额路由不同审批人？异常如何归因？
- 流程骨架固定，但**分支、参数、异常处理无法提前穷举编码**，此时纯静态 Skill 编排会大量维护分支，性价比极低，适合轻 Agent 做流程内决策。

区分两个概念（很多人混淆）：

1. **业务流程规范（业务层面固定 Workflow）**：产品 / 制度定义的标准步骤
2. **执行流水线（代码层面硬编码 DAG）**：程序写死每一步调用哪个 skill、传什么参数、if-else 分支

> 业务有固定 Workflow ≠ 代码可以硬编码静态 DAG

## 二、完整修正后的选型判定框架（替代简化公式）

### 前置定义

- **Skill**：原子工具，输入输出契约固定，无自主决策
- **静态 Skill 编排（DAG / 工作流引擎，如 Airflow、n8n）**：多 skill 按硬编码顺序串联，分支提前枚举，**无 LLM 动态推理**
- **Agent**：具备规划、反思、工具调度能力，使用 LLM 做运行时决策，可以调用 Skill，也可配合标准 Workflow 骨架运行

### 四层判断（按顺序判断）

1. **单一步骤，输入输出完全可标准化，无分支、无重试** → 直接用 Skill
   例：调用接口查询单个订单、文本翻译
2. **多步骤，完整执行路径、所有分支、参数全部可提前枚举硬编码** → 静态编排 Skills（DAG 工作流，不需要 Agent）
   例：每日凌晨固定：读取数据表 A → 计算汇总指标 → 写入表 B → 推送固定模板邮件；无任何动态判断
3. **业务有标准 Workflow 骨架，但运行时存在下面任意一条** → 需要 Agent（轻量 Agent 即可，不是复杂自研 Agent）
   - 分支判断依赖上一步返回结果，分支无法全部提前枚举
   - 需要结果自校验、失败重试、参数动态调整
   - 需要理解非结构化输入，动态提取参数传给 Skill
   - 异常场景需要自主选择兜底策略
4. **开放式探索任务，不存在标准 Workflow** → 重型 Agent（自主拆解目标、动态规划路径）

## 三、典型对照案例

### 案例 1：完全固定流水线 → Skill 编排，不用 Agent

任务：每日导出固定报表 → 生成 PDF → 发送给固定邮箱。

所有步骤、参数、接收人全部写死，不会变化。

实现：DAG 编排 3 个 Skill，无需大模型决策。

### 案例 2：纸面有固定报销 Workflow，但运行分支动态 → 需要轻 Agent

流程文档：凭证上传→验真→预算校验→审批→打款。

运行特点：

- 发票 OCR 识别结果不固定，需要动态校验
- 不同部门、不同金额审批路由不同，规则复杂，if-else 维护成本爆炸
- 验真失败需要自主选择：重试、提醒用户重传、人工兜底

> ✅ 业务 Workflow 固定；❌ 无法硬编码全部分支 → 使用轻 Agent：Workflow 作为骨架约束，Agent 负责每一步的动态决策与 Skill 调度

### 案例 3：开放式调研，无标准流程 → 完整 Agent

任务：调研竞品定价策略，输出对比报告。

没有固定步骤，需要自主搜索、筛选、汇总、对比 → 必须 Agent。

## 四、补充："带 Workflow 约束的 Agent" 行业常用方案

很多业务为了可控，不会让 Agent 完全自由规划（防止越权、不可控），采用混合架构：

> **固定 Workflow 骨架（DAG 定义允许执行的步骤顺序） + Agent 负责每一步内部决策、参数填充、异常处理**

优势：

1. 满足业务规范，不脱离既定流程，可控可审计
2. 不用硬编码海量分支，降低维护成本
3. 保留 Agent 动态推理、纠错能力

## 五、一句话修正原版简化公式

> ✅ 原版简化公式适合入门理解，但不能作为生产唯一判断依据
> ✅ 完整判断：
> 如果**全部执行路径、分支、参数都能提前硬编码枚举** → 纯 Skill 静态编排，不需要 Agent
> 如果仅有业务层面固定 Workflow 骨架，但运行时需要动态推理、自适应参数、自主重试 / 分支选择 → 即便流程文档固定，依然需要 Agent
> 如果连目标达成步骤都无法定义 → 重型自由 Agent

## 六、常见踩坑提醒

1. 不要走向两个极端：
   - 极端 1：只要多步骤就上 Agent（增加成本、不可控，能用 DAG 编排就不用）
   - 极端 2：业务文档写了流程，就全部硬编码 Skill 编排（规则膨胀后维护灾难）
2. 轻 Agent vs 重 Agent：固定 Workflow 场景优先【骨架约束轻 Agent】，不要上完全自主规划的通用 Agent，降低幻觉与风险
