# Agent Skills 创建最佳实践

> 来源：agentskills.io 官方文档《Best practices for skill creators》。本条目为讲解型资料蒸馏，非逐字翻译。

## 【问题】
创建 Skill 时最常见的坑是什么？为什么不能只让 LLM 凭通用知识生成？

## 【回答】
最大的陷阱是**让 LLM 在没有领域上下文的情况下生成 skill**，只依赖它的通用训练知识。结果是一堆**含糊、通用的流程**（"妥善处理错误""遵循认证最佳实践"），而不是真正有价值的具体 API 模式、边界情况、项目约定。

有效的 skill 必须**从真实专业知识出发（start from real expertise）**，把领域特定上下文喂进创建过程。两种落地方式：

- **从一次实操任务中提取**：在和 agent 协作完成真实任务时，记录成功步骤、你对 agent 的纠正（"用 X 库而非 Y""检查 Z 边界情况"）、输入输出数据格式、你额外提供的项目约定。然后把可复用模式抽成 skill。
- **从已有项目产物综合**：把团队真实的内部文档 / runbook、API 规范与配置、代码评审评论、版本控制历史（尤其 patch 与 fix 揭示"实际改了什么"）、真实故障案例喂给 LLM 综合成 skill。关键是**项目特定材料**，而非"通用数据工程最佳实践"这类泛泛文章。

## 【问题】
Skill 首稿写完之后，应该怎么精炼？

## 【回答】
**通过真实执行精炼（refine with real execution）**。首稿通常需要迭代：把 skill 放到真实任务上跑，再把结果——**所有结果，不只失败**——反馈回创建过程。问自己：什么触发了误报？漏掉了什么？哪些能砍掉？哪怕只做一轮"执行→修订"也能明显提升质量，复杂领域往往要多轮。

重点：**读 agent 的执行轨迹（traces），不只是看最终结果**。如果 agent 在无效步骤上浪费时间，常见原因有三：指令太模糊（它试了好几种方法才找到可行的）、指令不适用于当前任务（它照样照做）、选项太多却没有清晰默认。

## 【问题】
SKILL.md 激活后会被整体加载进 agent 的上下文窗口，该怎么"明智地花费上下文"？

## 【回答】
一旦 skill 激活，它的**整个 `SKILL.md` 正文会和对话历史、系统上下文、其他在用 skill 一起挤进上下文窗口**，每个 token 都在和其他内容竞争 agent 的注意力。具体做法：

- **只写 agent 不知道的**：项目特定约定、领域特定流程、非显然的边界情况、该用哪个工具 / API。不要解释什么是 PDF、HTTP 怎么工作、数据库迁移做什么——它本来就懂。
- **设计连贯单元**：scope 太窄→单个任务要同时加载多个 skill，带来开销和指令冲突；太宽→难以精确激活。一个"查数据库并格式化结果"的 skill 是连贯单元，若还塞进数据库管理就过多了。
- **适中细节**：过度详尽反而有害——agent 难提取重点、易被不适用指令带偏。简洁分步 + 可运行示例通常优于穷举文档。
- **大型 skill 用渐进式披露**：规范建议 `SKILL.md` **控制在 500 行 / 5000 token 内**，只放每次运行都需要的核⼼指令；详细参考放到 `references/` 等目录，并明确告诉 agent **何时加载**（"当 API 返回非 200 时读 `references/api-errors.md`"），而非泛泛一句"详见 references/"。

## 【问题】
Skill 里不同部分的指令，控制力度（specificity）该怎么拿捏？

## 【回答】
**按任务"脆弱性"校准控制力度（calibrate control）**，不同部分不必同样死板：

- **给自由**：多种方法都有效、任务容错时，解释 **why** 比死命令更有效——理解了目的，agent 才能做贴合情境的判断。例如代码审查 skill 可以描述"查什么"，而不规定"每步怎么做"。
- **要死板**：操作脆弱、一致性重要、必须按特定顺序时，明确"严格按此序列执行，不要修改命令或加 flag"。
- **给默认值而非菜单**：多个工具都行时，挑一个默认并简要提替代，而不是列出一堆等量选项（"用 pdfplumber；扫描件需 OCR 时用 pdf2image + pytesseract"）。
- **重过程轻声明**：教 agent **怎么处理一类问题**，而非针对某次任务"输出什么"。给可复用的"读取 schema→按 `_id` 外键 join→映射过滤→聚合"的方法，比写死"join orders 表和 customers 表筛 EMEA"更有价值。

## 【问题】
Skill 里的 gotchas 小节为什么信号密度最高？怎么用最好？

## 【回答】
**gotchas 列表是许多 skill 里最值钱的内容**：它是"违背合理假设的环境特定事实"，是 agent 不被告知就一定会犯的具体错误，而不是"妥善处理错误"这类泛泛建议。原文例子：

- `users` 表用**软删除**，查询必须加 `WHERE deleted_at IS NULL`，否则会带出已注销账号。
- 同一个值，在数据库叫 `user_id`、auth 服务叫 `uid`、billing API 叫 `accountId`，三者其实是一回事。
- `/health` 只要 web 服务在跑就返回 200，**哪怕数据库挂了**；要用 `/ready` 才能查完整服务健康。

用法要点：**gotchas 放在 `SKILL.md` 正文里**，让 agent 在遇到情况前就读到（拆到独立参考文件虽可，但非显然的问题 agent 可能识别不出触发时机）。而且——**每当 agent 犯错被你纠正，就把纠正写进 gotchas**，这是迭代改进 skill 最直接的手段。

## 【问题】
除了 gotchas，还有哪些行之有效的指令模式（patterns for effective instructions）？

## 【回答】
这些是结构化 skill 内容的可复用技巧，按需取用：

- **输出格式模板**：需要特定输出格式时，给模板比用散文描述可靠（agent 擅长对具体结构做模式匹配）。短模板内联在 `SKILL.md`，长模板或仅特定场景用到的放 `assets/` 按需加载。
- **多步工作流清单**：步骤有依赖或校验门时，用显式 checklist 帮 agent 跟踪进度、避免跳步。
- **验证循环（validation loops）**：做完 → 跑验证器（脚本 / 参考清单 / 自检）→ 修问题 → 重复到通过。参考文档本身也可当"验证器"。
- **plan-validate-execute**：批处理 / 破坏性操作，先产出结构化中间计划，对照真值验证后再执行。关键是那个校验脚本——它把计划（`field_values.json`）和真值（`form_fields.json`）对碰，报错信息（"字段 signature_date 不存在，可用字段：…"）足够让 agent 自我纠正。
- **打包可复用脚本（bundling scripts）**：跨测试用例对比执行轨迹时，若发现 agent 每次都重造相同逻辑（画图、解析格式、校验输出），就是信号——写一次测试好的脚本放 `scripts/` 里随 skill 分发。
