# 通用Agent是饮鸩止渴

> 蒸馏自陈以强《从 Agent Flow 到 AI Native：为什么通用 Agent 是"饮鸩止渴"》（阿里技术，2026-08-05）。核心论点：通用 Agent 把一切押在 LLM 的概率能力上，既不可靠也不可复现；用户要的是"确定地、可靠地完成具体任务"，因此应当用 Flow + 最小任务单元 + hardcode + 独占数据，把 Agent 当作能力之一而非一切，这才是 AI Native。

## 【问题】
作者为什么说"通用 Agent 是饮鸩止渴"？通用 Agent 在可靠性上到底出了什么问题？

## 【回答】
根子在于 **LLM 的输出本质上是概率性的，不是确定性的程序**。具体有三个表现：

- **不可复现**：同一个任务开两个不同的对话，通用 Agent 很可能用两种完全不同的思路去做，一个成功、一个失败。用户要的根本不是让 LLM 像程序员解 bug 一样去"探索"路径。
- **堆记忆治标不治本**：业界大多靠堆砌 Memory 系统来缓解这个不确定性，但到目前为止，**没有哪个通用 Agent 敢说自己记忆系统已经彻底解决问题**。
- **用户要的是确定性**：大量客户的真实需求只是"完成一些有固定流程和链路的重复性任务"，他们要的是"用最低的认知负担，确定地、可靠地完成复杂任务"，而不是在难懂的 Skill 和漫长等待 LLM 自有能力升级之间来回折腾。

所以"饮鸩止渴"指的是：把一切 all in 在通用能力和 LLM 上，幻想一个 world agent、幻想"许愿就能解决一切"，结果反而迟迟给不了用户想要的结果。

## 【问题】
什么是"最小任务单元（最小混沌单元）"？为什么要把任务切分下发？

## 【回答】
因为 **大模型的输出是概率性的、上下文窗口有限**，所以每次派发给大模型的任务，最好都是"有着具体上下文、工作量适中、并且可以闭环确认结果"的单元。在 Agent Flow 里，Flow 的每一个 **Node 就是一个最小任务单元**：让某个 Node（如 QwenWork）执行某个动作，或呼叫外部工具处理某段逻辑，做完之后再进入下一个节点。

这种做法的两个好处：**一是让庞大复杂的任务变得受控**，二是**极大拓展了系统的编排能力**——把任务切分发包给合适的 Node，而不是指望单个 Agent 一口气把所有事做完。

## 【问题】
Agent Flow 是什么？它和传统 Skill、通用 Agent 的核心区别在哪？

## 【回答】
Agent Flow 是**传统 Flow 的强化**，核心不是让用户理解节点、连线和 JSON，而是让用户用**自然语言描述目标**，然后让 LLM 去理解目标、生成 Flow、修改 Flow、运行 Flow。

关键定位差异：

- **Flow 降级为编排层**：只负责链路控制、任务下发和结果回收，不对 Node 和细节负责；具体任务由 Node 负责。Node 可以是 QwenWork、Codex CLI、影刀、千牛接口，也可以是阿里内部的运维 Agent。
- **跳出单个 Agent，上升到编排层和控制层**：不像通用 Agent 把一切押在 LLM 上，而是把任务拆成合适的 Node，"外包"给合适的 Agent Node，把 Agent 作为能力之一，而不是当成一切。
- **能跑通长链路**：例如一个电商用户要汇总报表，需经 QwenWork 取数、影刀 RPA 取数、千牛接口取数，汇总后通过 DWS 写钉钉文档、再发到钉钉群——以前几乎不可能在单个 Skill 的 loop 里无介入跑通，Agent Flow 可以实打实地直接跑通。

## 【问题】
为什么说"YAML / Flow / hardcode 是可靠的，而纯自然语言是不可靠的"？

## 【回答】
这是**确定性与概率性的根本区别**。基于 **YAML 的 Flow 自生成和自维护，远比松散的 Skill 简单高效**；而纯自然语言不可靠——正如前面所说，同一任务不同对话会走出不同思路，成败不一。

因此作者的工程取向很明确：**能写死的链路就写死，能编排的就编排**，把不确定的部分（自然语言理解、生成内容）限制在最小任务单元里，用确定性的编排层去"框住"概率性的 LLM，而不是反过来让 LLM 自由发挥整条链路。

## 【问题】
作者为什么说"Hardcode 是美丽的"？LLM 时代为什么不该再排斥 hardcode？

## 【回答】
过去我们排斥 hardcode，是因为**人工写代码成本高**——写一段定制逻辑有成本，维护有成本，未来扩展也有成本，所以追求抽象、通用、平台化，好像写个 if else 就"土"、不"高级"。

但 **LLM 时代这个前提变了：代码是"廉价"的**。写一个 Flow 是廉价的，写几个固定的 LLM Call 是廉价的，给一个付费客户手搓一条 Agent Flow 也是廉价的。而且**对 LLM 来说，10 个 if else 绝对比一大堆抽象工厂更容易理解**。

所以务实做法是：如果一个客户的问题三个有顺序的 LLM Call 加两个 API 就能解决，就那么写；如果是固定的审批辅助链路，就写死；如果客户愿意付费、只想每周生成一份可靠报告，就给他做一个可靠的 Flow。只要用户问题被解决、愿意付费、成本被覆盖、系统能从真实场景里生长出来，就是成功。**问题没解决、客户没付费，就先设计通用 Agent 平台堆 Loop / Memory / Harness / MCP / RAG，才是本末倒置**。

## 【问题】
AI Native / LLM Native 的本质到底是什么？为什么说很多产品只是"LLM 套皮"？

## 【回答】
本质非常简单：**基于 LLM，让 AI 解决用户的问题**。不是让产品"看起来有 AI"，不是让架构看起来先进，也不是让用户去学习 Agent / Loop / RAG / MCP。

- **真 AI Native**：用户真有一个问题，AI 真帮他解决了，而且解决得更轻松、更可靠、更便宜，或至少更自然，然后用户愿意继续用甚至付费。
- **LLM 套皮**：旧系统突然看见大模型，赶紧往自己身上贴一层 AI 的皮——旧框架还是旧框架，旧流程还是旧流程，只是某个环节多调了一次 LLM、某个页面多塞了一个聊天框（例如很多 AI 搜索就是把 LLM 别扭地接入推荐系统）。相比之下，OneRec 直接搞一个原生的推荐大模型，更接近真实的 LLM Native 方案。

作者的态度是"强硬地砍掉所有挡路的东西，脑子里只保留一个念头：**用户的一句自然语言，到底能不能把这个任务完整跑通？**"

## 【问题】
用户为什么会选择你的 Agent？一个 Agent 产品的护城河到底在哪？

## 【回答】
原因只有两个，而框架的先进性并不在其中：

1. **只有你能解决某些问题**——不要迷信架构，LLM 时代写一个优秀的 Agent 架构并不难，**真正关键的是你拥有别的 Agent 拿不到的东西**。随着 LLM 兴起，爬虫、数据获取重新炙手可热，因为大模型没有正确且核心的数据充其量只是个 Chatbot。淘宝的商品数据、钉钉的聊天记录，这些才是 Agent 最宝贵的财富：哪怕通用模型再聪明，它也突破不了安全限制进到你的数据库里"自动总结聊天记录、精准推送到指定钉钉群"，**只有能拿到独一无二数据和接口的 Agent 才能做到**。
2. **你真的能解决问题**——RAG、MCP、Tool Calling、Multi-Agent、Agent Loop 这些对用户来说**毫无意义**，用户只关心"我的问题解决了吗"。大部分客户的真实需求其实只要三个有顺序的 LLM Call 加两个 API；但很多产品非要上一堆通用能力，烧掉大量 token 换来客诉，或任务根本无法复现成功。

所以 **Agent 的核心不是架构、不是 loop、不是 harness，而是用户是否愿意为它解决的问题付费**——只要能解决问题，用户根本无需在意是什么架构、是不是 hardcode、甚至是不是用了 LLM。

## 【问题】
为什么作者说"基建与组织对 LLM 不友好"？这和实践有什么关系？

## 【回答】
从研发侧看，作者做内部运维 Agent（WarRoom 研发助手）时深有体会：想查日志，日志系统需人工授权且无法 A2A；想看代码，代码库需手动开权限；想管中间件，没有开放 AK/SK；想接强模型，审批批不下来、外部模型访问不了内网。每一步受阻，最终沦为"**人肉胶水**"——Agent 说要查日志，人去点；说要看权限，人去申请；说要验证，人去截图复制喂回去。原因是**过去 20 年所有基建都是为"人"设计的，不是 LLM friendly 的**。

这又引出一个结论：**location（位置/权限）很重要**。后来 Aone 团队把日志、trace、代码直接喂给现成的 Code Agent，做出了真实可用的运维 Agent，正是因为它的"位置天生好"，能更简单拿到权限和基建。

放大到组织层面：**任务、权限、上下文和反馈的链路越长，组织就越"厚"**——"一千张 A4 纸叠起来依然是厚的"，层级再怎么包装成扁平都一样。理想的扁平是链路足够短：每个人都能成为"超级自由人"，看到问题直接写代码、提交、部署并全权负责；任务分发者点对点把完整任务交给一线研发，而不是层层派发。把人做成 Agent、把任务和交流变成 TCP/IP 协议（点对点、可靠、稳定、充分），任务就会变成极简的 goal 模式。

## 【口诀】
通用 Agent 押概率、不可复现是硬伤；最小单元切任务、Flow 编排框住它。Hardcode 不丢人、能付费才是真；AI Native 看结果、套皮终归会露馅。护城河在数据、不在架构多花哨。
