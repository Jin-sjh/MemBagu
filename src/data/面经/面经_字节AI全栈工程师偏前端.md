## 【问题】
一面：谈谈你对 SSE（Server-Sent Events）的理解，它与 WebSocket 有什么区别？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

**SSE** 是基于 HTTP 的**单向**（服务端 → 客户端）长连接推送，`Content-Type: text/event-stream`，浏览器原生 `EventSource` 支持**自动重连**（并通过 `Last-Event-ID` 请求头续传），协议为纯文本、不支持二进制。

**WebSocket** 是独立协议（`ws://`），经 HTTP Upgrade 握手后**全双工**，支持二进制帧，但**没有自动重连与心跳**，需要自行实现。

**选型判断**：AI 对话是**单向流式输出**，SSE 足够且更简单 —— 可复用 HTTP 的鉴权、网关、日志与压缩链路；需要双向通信（协作编辑、实时对战、语音）才上 WebSocket。

**工程坑（这是追问的重点）**：

- `EventSource` **不能自定义请求头**（无法带 `Authorization`）、也不能用 POST 传 body —— 所以实际项目常用 **`fetch` + `ReadableStream` + `TextDecoder` 自行解析 SSE 帧**，代价是要自己维护**帧游标、断线续推与心跳**；
- 必须处理**网关/反向代理缓冲**（`X-Accel-Buffering: no`、`Cache-Control: no-cache`）与代理空闲超时，否则流会被攒住不吐；
- 协议细节：`data:` 多行需以 `\n` 拼接、`event:` 决定事件类型、`id:` 用于续传、`retry:` 指定重连间隔，通常以 `[DONE]` 约定终止。

## 【问题】
一面：在前端处理大模型返回的 Markdown 字符串时，如何保证渲染性能和安全性？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

**性能（流式场景的最大坑是「每来一个 token 就全量重渲染」）**：

- **增量与分块渲染**：按代码块/段落边界切分，**已闭合的块缓存解析结果，只重解析尾部未闭合块**；避免整棵子树销毁重建导致的闪烁与掉帧；
- **帧合并**：把一帧内到达的多个 chunk 合并成一次 DOM 更新（`requestAnimationFrame` 批量 flush）；
- **长文与长会话**：虚拟滚动，只渲染视口内内容；
- 复用解析器实例（`markdown-it` 创建成本高），代码高亮语言包**按需加载**。

**安全（核心风险是 XSS）**：

- Markdown 允许内联原始 HTML，攻击面包括**原始 HTML 标签、内联事件属性（`onerror=`）、`javascript:` 协议链接**；
- 必须做**转义 + sanitize 白名单**（如 DOMPurify），**不要直接 `innerHTML` 插入**未净化内容；
- 外链统一加 `rel="noopener noreferrer"` 并做**协议白名单**（只允许 http/https/mailto）；
- 代码高亮的输出同样要落在可信边界内，禁止执行渲染产物中的脚本。

## 【问题】
一面：TypeScript 中的泛型有什么作用？请写一个通用的 AI 接口响应包装类型。

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

**泛型的作用**：把类型作为参数传入，让「容器/流程」与「具体数据类型」解耦 —— 调用方拿到**强类型业务数据**而不是 `any`，错误分支在编译期被约束；对 AI 接口层而言，同一个包装结构可复用于对话、检索、工具调用等不同 payload。

```ts
type ApiCode = 0 | 400 | 401 | 403 | 429 | 500

interface ApiResponse<T> {
  code: ApiCode
  message: string
  data: T
  requestId?: string
}

// 用可辨识联合让调用方在判断 ok 后自动收窄类型
type ApiResult<T> =
  | { ok: true; data: T }
  | { ok: false; code: ApiCode; message: string }

// 流式分片（SSE chunk）
interface StreamChunk<T = string> {
  id: string
  delta: T
  finishReason: 'stop' | 'length' | 'abort' | null
}

// 包装调用：保留入参类型并推导返回值类型
declare function request<T, P = unknown>(
  url: string,
  payload?: P
): Promise<ApiResult<T>>
```

**设计要点**：`code` 用字面量联合而非 `number`，杜绝任意值；`ApiResult` 用**可辨识联合**代替「`data` 可能为空」的写法；泛型参数给默认值（`T = string`）降低调用成本；需要时用 `Partial<T>`、`Awaited<ReturnType<F>>`、条件类型做错误映射。

## 【问题】
一面：说一下 CSS 中 Flex 布局和 Grid 布局的应用场景区别？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

- **Flex 是「一维」布局**（主轴 + 交叉轴），**内容驱动**：先有内容再决定排布。典型场景 —— 导航条、按钮组、表单行、卡片内部对齐、不定数量的标签流；`flex: 1` 做等分、`gap` 代替 margin、`align-items: center` 做垂直居中。
- **Grid 是「二维」布局**，**布局驱动**：先定义轨道（`grid-template-columns/rows`、`grid-template-areas`）再把内容放进去。典型场景 —— 页面骨架、仪表盘、后台表单、图片墙。
- **判据**：**按行或按列排就够了 → Flex；行列都要同时对齐 → Grid**。二者常嵌套使用：外层 Grid 定骨架，内层 Flex 排内容。
- AI 场景锚点：聊天消息与工具调用卡片内部用 Flex，多列卡片的工作台 / 后台管理用 Grid，配合 `minmax()` 与 `auto-fill` 做自适应。

## 【问题】
一面：实现一个简单的防抖函数（Debounce），并解释它在 AI 搜索建议场景中的作用。

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

```js
function debounce(fn, wait = 200, { immediate = false } = {}) {
  let timer = null
  let lastArgs = null
  let lastThis = null

  const debounced = function (...args) {
    lastArgs = args
    lastThis = this
    const callNow = immediate && timer === null
    if (timer) clearTimeout(timer)
    timer = setTimeout(() => {
      timer = null
      if (!immediate) fn.apply(lastThis, lastArgs)
    }, wait)
    if (callNow) fn.apply(this, args)
  }

  debounced.cancel = () => { clearTimeout(timer); timer = null }
  debounced.flush = () => {
    if (timer) { clearTimeout(timer); timer = null; fn.apply(lastThis, lastArgs) }
  }
  return debounced
}
```

**原理**：每次触发都**重置定时器**，只在停止触发 `wait` 毫秒后执行一次；与节流的区别是**防抖关注「最后一次」，节流关注「固定频率」**。

**在 AI 搜索建议场景中的作用**：

- 输入每个字符都发请求会**打爆服务端**，并产生**竞态覆盖**（慢的旧请求后返回，覆盖掉新结果）；
- 防抖把请求收敛到**用户停顿后一次**，显著降低 QPS 与 token 消耗；
- **但防抖不够** —— 必须配合 `AbortController` 取消在途请求 + **请求序号/时间戳判定丢弃过期响应**，并在 UI 上区分「加载中」与「无结果」；
- 实践折中：纯防抖会导致输入期间毫无反馈，常见做法是**防抖 200–300ms + 保留首次即时请求**（或用节流做兜底刷新）。

## 【问题】
一面：浏览器中的事件循环（Event Loop）机制是怎样的？微任务和宏任务谁先执行？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

**机制**：JS 单线程，调用栈清空后从任务队列取任务执行。**一轮循环 = 执行一个宏任务 → 清空所有微任务 → 浏览器有机会渲染 → 进入下一轮**。

- **宏任务**：`<script>` 主代码、`setTimeout/setInterval`、I/O、UI 事件、`MessageChannel`、Node 中的 `setImmediate`；
- **微任务**：`Promise.then/catch/finally`、`queueMicrotask`、`MutationObserver`、以及 `await` 之后的代码（等价于 `.then` 回调）。

**结论：微任务优先 —— 同一轮里微任务必须全部清空，才轮到下一个宏任务**，所以 `Promise.then` 总是先于 `setTimeout`。微任务中再产生微任务会**继续在当前轮清空**，因此微任务递归会饿死渲染。

**与 AI 流式渲染的关联（追问常见）**：微任务队列清空后才轮到渲染，所以**在微任务里做长同步计算会阻塞上屏**；流式场景若每个 token 都触发一次响应式更新，会造成高频同步 flush 与掉帧 —— 正确做法是**按帧合并批次**（`requestAnimationFrame`）或用框架的批处理/低优先级调度。

## 【问题】
二面：React 的 Fiber 架构解决了什么问题？在 AI 长文本生成渲染时有何优势？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

**解决的问题**：旧的**栈调和（Stack Reconciler）是递归且不可中断**的，一旦开始就必须把整棵虚拟 DOM 树算完，长任务会阻塞主线程，导致掉帧与输入卡顿。Fiber 把渲染重构为**可中断的链表工作单元**，并引入**优先级调度**，让高优先级更新（输入、点击）可以插队，低优先级更新让出时间片，从而保证交互响应。

**AI 长文本生成场景的优势**：

- 流式 token 高频到达 → 高频状态更新。Fiber 的**时间切片 + 优先级**能把「打字机效果」的更新标为**低优先级**（`startTransition` / `useDeferredValue`），**保证输入框与滚动不卡**；
- **可中断**意味着大文档 / 长列表的重新渲染可以被打断，不会一次性堵死一帧；
- 配合并发特性，流式内容可用 `useDeferredValue` 延迟渲染、`Suspense` 做局部占位。

**必须补一句边界**：React 18 的并发特性**需要主动表达优先级**（`startTransition` 等），仅靠 Fiber 不会自动变快。对比 Vue 3 的路径是**细粒度响应式 + 编译期依赖收集**，更新粒度本身就小，无需这套协调器 —— 这个对比是加分项。

## 【问题】
二面：你们是如何处理 AI 接口的流式数据解析的？如果返回的是 JSON 片段怎么办？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

**解析链路**：`fetch` 拿 `res.body.getReader()` → `TextDecoder({ stream: true }).decode(value, { stream: true })` → 按 `\n\n` 切分事件、取 `data:` 前缀 → 遇 `[DONE]` 终止。

**最关键的一点**：**必须自维护缓冲区**，因为 **chunk 边界与事件边界不对齐** —— 一个事件可能被拆到两个 chunk，一个 chunk 也可能含多个事件。做法是保留 buffer，只处理最后一个完整分隔符之前的部分，剩余留给下一轮（即「**自维护帧游标**」）。

**返回 JSON 片段的处理**，按「改协议 → 容错解析 → 兜底」三层：

- **首选改协议（最正确的工程判断）**：让每个分片**自包含**，例如 NDJSON（一行一个完整对象）、或按 `{"type":"delta","path":"answer","value":"..."}` 的结构化事件分发 —— 从源头规避半截 JSON；
- **只能收半截 JSON 时**：维持累积字符串，做**容错解析** —— 首次 `JSON.parse` 失败则判断是否「引号未闭合 / 括号未闭合」并补全后重试，或用**流式 JSON 解析器**（逐字符推进的状态机，`clarinet` / `json-stream` 思路）先取出已完整的字段，**把已解析部分先上屏**；失败则退化为**纯文本渲染**；
- **兜底原则**：解析失败**绝不丢弃已生成内容**，保留原文并埋点上报 —— **不能因为一个坏分片丢掉整段回答**。

**补充细节**：SSE 的 `data:` 可多行需 `\n` 拼接；`event:` 决定事件类型（用于区分 `delta` / `tool_call` / `error`）；`id:` 用于 `Last-Event-ID` 断线续传。

## 【问题】
二面：请设计一个 Prompt 模板管理系统，前端需要考虑哪些核心功能？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

**数据模型**：模板（名称/描述/标签）→ **变量声明**（类型、必填、默认值、枚举约束）→ 内容分段（system / user / few-shot）→ 模型参数（model / temperature / max_tokens）→ **版本历史**（diff、回滚、发布与灰度）。

**核心功能清单**：

- **变量系统与校验**：`{{var}}` 语法、必填校验、类型约束，从源头杜绝运行时空值；
- **版本管理与 diff**：Prompt 是**改动最高频、影响最大**的资产，必须版本化、可回滚、有变更记录（谁改的、为什么改）；
- **试运行与并排对比（eval）**：同一批测试输入跑新旧版本并排对比 —— 这是 Prompt 系统**真正产生价值**的部分，不是编辑器；
- **权限与状态机**：草稿 → 评审 → 发布，防止线上 Prompt 被随意改动；
- **效果回流**：模板版本 ↔ 调用日志 ↔ 人工反馈/自动评分三者绑定，形成闭环；
- **多模型适配**：不同厂商的 message 结构与参数差异做归一化封装；
- **审计与成本**：调用量、token 成本、失败率。

**前端设计要点**：受控编辑器 + **变量高亮 + 实时预览**；变量插入用 `textarea` 比富文本更稳（避免富文本引入格式污染）；**模板与调用方解耦** —— 调用侧只认「模板 id + 变量对象」，不感知模板内容。

## 【问题】
二面：什么是 RAG（检索增强生成）？前端在 RAG 应用中可以承担哪些工作？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

**RAG 定义**：检索（Retrieval）→ 增强（Augment）→ 生成（Generate），把外部知识库中召回的片段拼进上下文，让模型**基于给定材料**作答，以缓解幻觉与知识时效问题。完整链路：文档解析与切分 → 向量化入库 → 查询改写 → 召回（向量 / 关键词 / 混合检索）→ 重排（Rerank）→ 上下文组装 → 生成 → **引用与溯源**。

**前端能承担的工作**（不止是画界面）：

- **引用溯源与可解释 UI（最核心）**：把答案中的引用标记映射到原文片段，**高亮命中句、可点击定位、侧栏展示来源** —— 这是 RAG 产品建立信任的根本；
- **检索过程可视化**：展示召回片段、相关度得分、最终被采用的片段，既服务调试也服务信任；
- **查询改写与检索范围的交互承载**：让用户澄清意图、圈定范围（时间、文档集、权限）；
- **文档预处理链路的交互**：上传后的切分策略预览、表格与图片处理、OCR 结果校对；
- **权限与数据边界**：RAG 是数据泄漏高发区，检索结果必须**按用户权限过滤后再渲染**，并在 UI 上明示来源；
- **人工反馈回流**：点赞/点踩、标注「这条引用不相关」，这些数据是检索质量优化的燃料。

**锚点**：浙大数据中心的 RAG QA 引擎做过**混合检索（向量 + 关键词互补）+ Rerank（交叉编码器精排）**，可直接作为项目回答。

## 【问题】
二面：如何优化 AI 聊天界面的首屏加载速度和交互流畅度？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

**首屏加载**：

- **代码分割与按需加载**：聊天页与 Markdown 渲染器、代码高亮、图表、文件预览分开打包；**highlight.js 语言包必须按需**（全量体积很大）；
- **骨架屏 + 乐观渲染**：先渲染框架与历史消息占位，数据到达后替换；
- **历史消息分页 / 虚拟列表**：长会话绝不能一次性渲染几百条 Markdown；
- 字体子集化，避免字体阻塞首屏；必要时做预渲染/SSR 输出骨架。

**交互流畅度**：

- **流式渲染帧合并**：一帧内多个 chunk 合并为一次 DOM 更新，杜绝每 token 一次渲染；
- **增量渲染 + 分块缓存**：已闭合的 Markdown 块缓存，只重解析尾部未闭合块；
- **优先级调度**：用 `startTransition` / `useDeferredValue` 把流式内容降为低优先级，保证**输入与滚动不掉帧**；
- **自动滚动策略**：用户手动上滚后**停止自动吸底**，并给「回到最新」按钮 —— 体验细节，面试官爱听；
- **降级**：低端设备关闭代码高亮与动画。

**量化方式（务必准备）**：用 Performance 面板看 **long task 数量、INP、FPS**；把「提升」表述为**首屏 JS 体积、长任务次数、INP** 等具体指标，而不是「变流畅了」。

## 【问题】
二面：在 Node.js 中如何处理高并发的 AI 转发请求？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

**本质**：「转发」是**代理 + 流式透传**，瓶颈不在业务逻辑，而在**连接数与内存**。

- **纯流转发，不缓冲**：用 `stream.pipeline` 把上游 SSE 流**直接 pipe 给下游响应**，**绝不在 Node 层拼接完整回答**（一个回答可能几十 KB，乘上并发会直接吃爆内存）；
- **背压**：`pipe` 自动处理 backpressure；手写 `data` 事件时必须检查 `write()` 返回值；
- **禁用各级缓冲**：`Content-Type: text/event-stream`、`Cache-Control: no-cache`、`X-Accel-Buffering: no`，并 `flushHeaders()`，否则 Nginx 会把流攒住；
- **上游连接与取消**：Keep-Alive Agent 复用连接；**客户端断开必须立刻中止上游模型请求**（`AbortController` 级联），否则连接断了模型还在生成、成本还在烧 —— **这是最容易被追问的点**；
- **限流与排队**：按用户/租户做并发上限与令牌桶限流，超出直接返回 429，而不是让连接堆积；
- **长连接运维参数**：`keepAliveTimeout`、`headersTimeout`、`maxRequestsPerSocket`，以及负载均衡的 **idle timeout**（要比 SSE 心跳间隔长）；
- **多进程**：`cluster` / PM2 多实例；注意 SSE 长连接会占满连接，轮询式均衡需评估，并检查 **FD 上限（ulimit）**；
- **可观测**：并发连接数、上游 P99、**首 token 延迟（TTFT）**、token 速率、取消率。

**收尾判断**：Node 在 I/O 密集转发上足够，**真正的瓶颈通常是上游模型服务而非 Node**；若追求极致吞吐可换 Go，但收益点不在这一层。

## 【问题】
二面：谈谈你对 Agent 架构的理解，前端如何实现多步骤任务的进度展示？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

**Agent 架构分层**：**规划（Planner）→ 工具调用（Tool Use）→ 执行与观察（Act / Observe）→ 记忆与上下文（Memory）→ 终止与校验（Reflect / Critic）**，外层是 **Runtime / Harness**（循环控制、重试、权限、沙箱、日志）。范式上分 ReAct、Plan-and-Execute、Multi-Agent 分工。

**前端进度展示（关键判断：能力上限由协议决定）**：

- **协议先行**：后端必须把输出设计为**结构化事件流**（`step_start` / `tool_call` / `tool_result` / `delta` / `step_end` / `done` / `error`），前端才可能渲染真实进度 —— **进度展示的瓶颈是协议，不是 UI**；
- **任务模型**：把扁平事件流**聚合成树状步骤列表**（父子步骤、并行分支），这才是前端的主要工作量；
- **展示形态**：可折叠步骤列表（等待/执行中/成功/失败/跳过状态图标）、工具调用卡片（入参、出参、耗时）、并行分支时间轴、整体进度条（按步骤数或 token）；
- **不确定性处理**：Agent 会**重试、回滚、动态新增步骤**，UI 必须支持**步骤插入与状态回退**，且**用稳定 `stepId` 而非索引做 key**；
- **中断与人工接管（HITL）**：高风险工具调用前需**人工确认**，UI 要能暂停、改参数、拒绝；
- **长任务与断线**：重连后**基于事件 id 续推、幂等重建状态**，不能假设连接一直活着；
- **可观测**：完整事件日志、耗时瀑布、失败重放，用于排查「Agent 为什么走了这条路」。

**锚点**：CDG 的 Issue 自愈 Agent（状态机 + Checkpoint + Git Worktree）与工作流编排画布（节点状态可视化）都可直接作为项目回答。

三面：在 AI 全栈开发中，你会如何选择后端技术栈（Node.js vs Python）？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

**按四维判断**：模型/AI 生态、I/O 形态、团队与交付效率、性能要求。

- **Python**：AI 生态最完整（模型 SDK、LangChain/LangGraph、数据处理与评测工具链）；适合**Agent 编排、RAG 检索与重排、模型侧服务、离线批处理**；GIL 下若要高并发 I/O 需异步或多进程；
- **Node.js**：**I/O 密集型网关与流式转发**最自然，且可与前端共享 TypeScript 类型；适合 **BFF、鉴权与聚合、SSE 透传代理、工具调用网关**；AI 生态较弱。

**常见结论**：**Python 做 AI 内核（Agent / RAG / 推理侧），Node 做 BFF 与流式网关**，两者用 HTTP/SSE 或消息队列解耦。若团队以 Web 为主、场景是「编排 + 转发 + 交互」，Node 一体化能省掉一层服务与类型同步成本。

**分界线一句话**：**有没有重计算 / 重 AI 依赖 —— 有则 Python；纯编排与转发，Node 够用且交付更快。**

## 【问题】
三面：场景题——如何实现一个支持「中断生成」和「重新生成」的对话界面？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

**中断生成**：

- 前端用 `AbortController.abort()` 中止 fetch 流；捕获 `AbortError` 时**不当作错误上报**；**保留已生成内容**，消息状态置为「**已中止**」而非「失败」；
- **必须通知服务端取消上游模型请求** —— 否则连接断了模型仍在生成、成本仍在消耗；服务端要把客户端断开事件**级联到上游 abort**；
- **状态机**：`sending → streaming → (done | aborted | error)`，中止后的消息可继续或重新生成；
- **细节**：中止后输入框立即恢复可用；已上屏内容**一次性固化为最终态**（避免缓冲里还有未渲染内容导致丢字）；未闭合的结构化数据（如半截 JSON）要截断清理。

**重新生成**：

- **语义是关键**：对同一用户输入产生**新的分支回答**，而不是覆盖历史 —— 因此需要**消息树 / 分支模型**（`parentId` + `children`）与 UI 上的「1/2/3」版本切换。**这是最容易答漏、也最能体现设计功力的一点**；
- **实现**：隐藏或保留旧回答的后续消息为分支 → 用**当时的上下文快照**重新发起同一 prompt → 新回答作为兄弟节点插入；
- **幂等与一致性**：用 `requestId` / `clientMessageId` 去重，避免重试产生重复消息；重新生成必须用**上下文快照**而非当前上下文；
- **交互细节**：生成中禁止重复点击、按钮进入 loading、失败退化为「重试」；
- **可扩展**：编辑用户消息后重发、从中断处继续、选中文本局部重写 —— 都是同一套分支模型的延伸。

## 【问题】
三面：谈谈 AI 应用中的数据隐私和安全问题，前端能做些什么？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

- **减少数据出域**：能本地处理就不上传（本地做 PII 检测与打码、文件本地切分与预览）；上传前**明确告知范围**并让用户选择；
- **输入侧防护**：敏感字段（身份证、手机号、密钥）**本地检测与提示**；粘贴大段内容时给出风险提示；**Prompt 注入**在 UI 层的缓解 —— 可视化地区分「用户内容 / 系统指令 / 外部文档」，并对引用来源做显式标注；
- **传输与存储**：全程 HTTPS/WSS；**令牌不进 URL**（这也是流式请求用 `fetch` 而非 `EventSource` 的原因之一）；前端不持久化敏感内容（localStorage / IndexedDB 的会话缓存设 TTL 与清理策略）；**绝不把模型 API Key 打包进前端**；
- **展示侧防控**：Markdown/HTML 的 **XSS 防护**（DOMPurify + 白名单）、链接协议白名单、**引用溯源与来源标注**、企业场景的屏幕水印与防截屏；
- **权限与审计**：UI 层体现数据权限边界（**越权内容不渲染**）、操作留痕与审计日志、共享与导出前的二次确认；
- **合规配合**：授权弹窗与可撤回、数据留存期限可配置、**用户数据删除入口**。

**收尾判断**：**安全的最终责任在后端与合规，但前端是唯一的数据出入口** —— 前端的价值在于「**最小化出域、让风险可见、把选择权还给用户**」。
