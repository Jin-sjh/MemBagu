## 【问题】
一面：项目上线之后有哪些可以量化的效果？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

核心是**给「基线 → 现状」的差值，而不是只报绝对值**：

- 指标分三层：**效率指标**（单次处理时长、人日节省）、**质量指标**（准确率、误关率、需人工复核的比例）、**采纳度指标**（周活跃使用人数、被其他团队复用次数）；
- **一定要先说清上线前的基线**，否则任何数字都没有锚点；
- 必然追问「**这个数字怎么保证不是虚的**」——提前准备**统计口径**、**对照组**与**失败案例**（哪些场景处理不了、如何兜底）；
- 结尾给一句**局限与下一步**，比继续堆数字更可信。

可调用锚点：腾讯 CDG 实习的 Issue 自愈 Agent，**自动关闭 56 个 Issue**，另有 Search 组件交付。

## 【问题】
一面：如果让你设计一个 AI 面试助手——上传简历后自动生成问题并进行模拟面试，你会怎么设计？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

系统设计题，按**需求拆解 → 链路设计 → 模块 → 难点 → 评估**五段讲：

- **输入层**：简历（PDF／图片）→ 解析为结构化 JSON（教育、项目、技能、时间线），保留原文位置以便溯源；
- **出题层**：先做**岗位画像匹配**（JD ↔ 简历的技能交集与缺口），再按「**高频题 + 简历强相关 + 简历薄弱点**」三路取题；
- **对话层**：多轮状态机，**根据上一轮回答动态追问**（答得浅就下钻，答得偏就换角度），而不是一次性吐 10 题；
- **评估层**：分维度打分（准确性、深度、结构化、项目证据），输出**诊断报告**而非单一分数；
- **难点判断**：**题目录入质量 > 模型能力**（题库脏，模型再强也白搭）；幻觉控制要求追问必须 **grounding 到简历原文**；另有上下文长度、成本、交互延迟三个工程约束；
- **闭环**：用户反馈 + 人工标注集 + 回归测试，否则质量不可控。

## 【问题】
一面：你从计算机本科到 AI 硕士，再到 Agent 系统开发，学习一个新领域时通常采用什么方法？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

这是**学习迁移能力题**，几乎每轮都会出现，建议做成可复述的模板：

- 一条明确路径：**先建立地图**（该领域的术语与问题分类）→ **找 1–2 篇高质量综述或经典实现** → **做一个最小可运行的东西** → **用输出倒逼输入**（写笔记、讲给别人、落到项目里）；
- 强调**带着问题学**，用当前项目里的真实卡点作为入口，而不是按章节通读；
- 强调**区分「知道」和「能落地」**：跑通 demo ≠ 理解，**能改 bug、能调参、能解释取舍**才算；
- 收尾点题：每次跨领域时**复用的是底层能力**（系统设计、工程实现、调试方法），**领域知识是后补的**。

## 【问题】
一面：你怎么判断一项技术值得深入学习，还是只需要做了解？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

给**可复述的判据**，不要说「看感觉」。例如三个问题：

- **① 它是否在我当前或目标岗位的核心链路上？**
- **② 它的知识半衰期有多长**（半年后还会不会变）？
- **③ 不用它的时候，我能不能在一周内捡回来？**

分层结论：**核心链路 + 长半衰期 → 深学**（原理 + 源码 + 调优）；**周边但要能对话 → 会用 + 知边界**；**纯热点 → 只知它解决什么问题、什么时候不该用**。

举例锚点：RAG 项目中做过「混合检索 + Rerank」的取舍——**深学检索与重排的评估方法**（直接决定效果），**只了解各家向量库的 API 差异**（可迁移）。

**判断标准不是「热不热」，而是「它在你的能力树上是不是一个承重节点」。**

开放式，考的是**判断力而非立场**，建议分层说：

## 【问题】
二面：你怎么理解 Harness？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

**这个词有歧义，建议先确认语境再展开**，至少准备三层含义：

- **Agent 语境**：Harness 是**模型之外的那层运行时脚手架**——工具调用与权限、上下文/记忆管理、循环与终止条件、沙箱、日志与评测驱动，即「**Agent = Model + Harness**」；模型决定上限，**Harness 决定能不能稳定复现**；
- **测试语境**：指**测试夹具 / 驱动框架**（test harness），负责准备环境、驱动被测对象、收集断言结果；
- **AI × 游戏语境**：很可能指**把游戏包一层、让 Agent 能像人一样观察并操作它**的驱动层（截图或 UI 树输入、动作注入、状态回读、奖励/断言定义）。

**答题动作：先反问一句「您这里指的是哪一层？」，再分层展开，比直接猜更稳。**

## 【问题】
二面：如果让你用 AI 做游戏 UI 自动化测试，你会怎么设计？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

**本场最关键的技术设计题**。先定义「UI 自动化测试到底测什么」：

- **功能可用性**（按钮与流程是否可通）、**视觉正确性**（错位、遮挡、分辨率适配、多语言文本溢出）、**稳定性**（crash、卡死、帧率）。

再并列三条技术路线并讲清取舍：

- **基于控件树 / 注入式**（引擎暴露 UI 层级或 Accessibility 信息）：**稳定且快**，但依赖被测端配合、跨引擎不通用；
- **基于视觉 / 截图**（模板匹配、OCR、多模态模型判读）：**通用、无需侵入**，但**脆**（版本迭代后基线失效）、慢、贵；
- **录制回放 + 脚本化**：稳定但**维护成本高**，适合回归而非探索。

**AI 的真正增量不在「用什么模型跑」，而在三处**：① 用多模态模型做**视觉断言**（「这个画面是否正常」）；② 用 Agent 做**探索式测试**（像玩家一样乱点，找 crash 与卡死）；③ 用历史 bug 与需求文档**自动生成用例与断言**。

**必须主动提到的坑**：

- **随机性与不可复现** —— 固定随机种子、状态快照、录屏回放；
- **判定标准模糊** —— 「看起来怪」怎么量化；
- **误报导致用例被废弃** —— 这是自动化测试失败最常见的原因；
- **成本与速度** —— 多模态推理贵，要做分层：**廉价规则前置，模型兜底**。

**评估闭环三指标**：**召回的真实 bug 数 + 误报率 + 维护成本**，缺一不可。

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

「闲聊」的实质是**软素质与稳定性评估**：沟通表达、价值观与团队匹配、情绪稳定性、求职动机与去向、是否有竞对 offer。

高频陷阱与应对：

- 让你评价前司或前领导 —— **只说事实与收获，不评价人**；
- 「你为什么想来我们这边」 —— **具体到团队在做的事**，不要说大厂光环；
- 套你现有 offer 与流程 —— **如实说进度**，不要拿它抬价；
- 准备 **3–5 个你主动想问的问题**（团队实际在做什么、新人前三个月的预期、培养机制），把单向盘问转为双向沟通。

**底线：薪资与职级在对方先出数之前不要先报价。**
