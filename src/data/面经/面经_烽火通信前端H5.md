## 【问题】
1. 什么是关键渲染路径？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

关键渲染路径（Critical Rendering Path）是浏览器把 HTML、CSS、JavaScript 等资源转换为屏幕像素的过程。典型阶段包括解析 HTML 构建 DOM、解析 CSS 构建 CSSOM、合并生成渲染树、布局计算几何位置、绘制并合成图层。JavaScript 可能阻塞 HTML 解析，CSS 通常会影响渲染树构建。

## 【问题】
2. 如何优化关键渲染路径？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

目标是缩短关键资源的下载、解析和执行时间，并尽早呈现首屏内容。可以压缩 HTML、CSS、JavaScript；减少关键资源数量和体积；内联少量首屏关键 CSS，将非关键 CSS 延后；给非关键脚本使用 `defer` 或 `async`（依据依赖顺序选择）；压缩图片、使用合适格式和尺寸；通过缓存、CDN、预加载关键资源改善获取时间。应结合性能指标和瀑布图定位瓶颈，避免盲目优化。

## 【问题】
3. 当用户点击按钮后，需要让按钮颜色逐渐变为另一种颜色并保持最终状态时，应该使用 `transition` 还是 `animation`？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

通常用 `transition`：点击时切换一个状态类或属性值，浏览器在旧值和新值之间插值，过渡结束后新值自然保留。例如通过 React 状态添加 `.active`，并为 `background-color` 设置 `transition`。如果效果包含多阶段关键帧、自动循环或独立时间线，更适合 `animation`；动画需要保持结束态时可用 `animation-fill-mode: forwards`。

## 【问题】
4. `transition` / `animation` 背后的机制是什么？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

两者都是 CSS 驱动的属性变化效果。浏览器在样式计算后，根据可动画属性的起始值和目标值，在时间进度上计算中间值，再更新渲染。`transition` 需要属性值发生变化才启动，通常由交互或状态切换触发；`animation` 由 `@keyframes` 定义关键帧，可以自动开始、循环、暂停并设置填充模式。渲染管线中，属性可能触发布局、绘制或合成；`transform`、`opacity` 通常更有机会仅由合成阶段处理，但应以实际浏览器性能分析为准。

## 【问题】
5. 在使用 React 构建用户界面时，组件重新渲染会带来性能开销，如何避免不必要的重新渲染？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

先用 React Profiler 定位真正有成本的组件，再针对性处理：用 `React.memo` 跳过 props 未变化时的子组件渲染；用 `useMemo` 缓存昂贵计算结果、用 `useCallback` 稳定传给记忆化子组件的函数；保持 state 尽量靠近实际使用它的组件，避免把局部状态放到过高层级；拆分组件和状态，减少订阅范围；避免每次渲染都创建导致比较失效的新对象或数组。记忆化本身也有比较和维护成本，应以测量结果为依据。

## 【问题】
6. 当多个组件需要共享并响应同一状态变化时，为什么需要引入更高级的状态管理方案？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

当共享状态跨越多个组件分支时，仅靠逐层传递 props 会产生 prop drilling，状态更新逻辑也可能散落在多个组件中。集中或按领域组织状态可以明确状态来源、更新方式和订阅关系，便于跨层共享、统一更新、调试和测试。并非所有共享状态都需要额外库：范围小且更新简单时，提升到共同父组件或使用 Context 通常足够；状态复杂、更新频繁或有中间件、时间旅行等需求时，再考虑专门方案。

## 【问题】
7. 不同状态管理方案与 Context API 的适用条件和局限性是什么？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

- **组件本地 state（`useState` / `useReducer`）**：适合局部、生命周期跟随组件的状态；跨树共享时需要提升状态并传递 props。
- **Context API**：适合主题、语言、登录用户等低频变更且许多后代需要读取的依赖；Provider 的 value 变化会让读取该 Context 的组件重新渲染，拆分 Context 或稳定 value 可缩小影响范围。它本身不提供完整的异步数据、缓存或开发工具约定。
- **Redux Toolkit**：适合状态边界较清楚、更新流程需要规范化、团队需要可预测调试和中间件的应用；需要遵循其状态建模方式，配置和概念比本地 state 多。
- **轻量外部 store（如 Zustand）**：适合希望以较少样板代码共享状态，并按选择器订阅部分状态的场景；团队仍需约定状态结构和更新边界。
- **服务器状态库（如 TanStack Query）**：适合请求数据的缓存、重试、失效和同步；它管理的是远端数据生命周期，不能替代所有客户端 UI 状态。

选择应看状态属于组件、跨组件客户端数据还是服务器数据，以及更新频率、团队规模和调试需求。

## 【问题】
8. 在配置 Rollup 多格式输出时，如何通过 `output` 配置项生成兼容不同运行环境的产物？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

在 `output` 中配置多个输出对象，每个对象指定 `format` 和对应文件名，例如：

```js
export default {
  input: 'src/index.js',
  output: [
    { file: 'dist/index.esm.js', format: 'es' },
    { file: 'dist/index.cjs', format: 'cjs', exports: 'named' },
    { file: 'dist/index.umd.js', format: 'umd', name: 'MyLibrary' }
  ]
};
```

库项目可分别提供 ESM、CommonJS 和浏览器全局构建，让不同加载器选择对应产物。具体格式和扩展名应与 `package.json` 的 `exports`、`main`、`module` 等入口声明保持一致。

## 【问题】
9. Rollup 不同 `format` 的适用场景分别是什么？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

- `es`：ES Module，适用于现代构建工具、支持原生模块的环境和需要 tree-shaking 的消费方。
- `cjs`：CommonJS，适用于 Node.js 中使用 `require` 的环境及相关工具链。
- `umd`：兼容 AMD、CommonJS 和浏览器全局变量的通用构建，常用于通过 `<script>` 引入的浏览器库。
- `iife`：立即执行函数形式，常用于直接注入页面的独立脚本；通常需要配置全局变量名或依赖映射。
- `amd`：适用于 AMD 加载器环境。
- `system`：适用于 SystemJS 模块加载器。

应根据目标运行环境、消费者的模块系统和发布方式选择，而不是机械地输出所有格式。

## 【问题】
10. 配置不同输出格式时有哪些关键注意事项？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

检查每种格式的文件名及包入口映射是否正确；`umd`、`iife` 等需要为 bundle 提供 `name`，并处理外部依赖的 `globals`；明确导出形态，必要时设置 `exports`；确认 `external` 依赖在目标环境可获得；注意 ESM 与 CommonJS 的扩展名和 Node.js 包类型规则；多入口或代码分割时使用适配的 `dir`、`entryFileNames`、`chunkFileNames` 配置。发布前应从各目标环境实际导入产物验证。

## 【问题】
11. 发起异步请求时，如何使用 Promise 实现超时控制，使请求超过指定时间仍未响应时自动判定为失败？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

可以将请求 Promise 与一个定时拒绝的 Promise 通过 `Promise.race` 竞争：

```js
function withTimeout(promise, ms) {
  let timer;
  const timeout = new Promise((_, reject) => {
    timer = setTimeout(() => reject(new Error('Request timed out')), ms);
  });
  return Promise.race([promise, timeout]).finally(() => clearTimeout(timer));
}
```

这会让调用方在超时后收到失败结果，但 `Promise.race` **不会取消仍在执行的底层请求**，需要配合请求 API 的取消机制。

## 【问题】
12. Promise 超时方案中应该如何设置超时时间？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

超时应由业务时效和网络环境决定，没有适用于所有接口的固定值。根据接口类型、用户可接受等待时间、正常延迟分布和失败重试策略设定，并可按请求类型采用不同阈值。浏览器端请求超时还应与服务端、代理和网关的超时策略协调，避免层级间设置矛盾。通过监控超时率和延迟分位数持续校准。

## 【问题】
13. 请求超时后，如何中断仍未完成的底层请求？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

使用 `AbortController`，将 `signal` 传给 `fetch`，超时时调用 `controller.abort()`：

```js
const controller = new AbortController();
const timer = setTimeout(() => controller.abort(), timeoutMs);

try {
  const response = await fetch(url, { signal: controller.signal });
  // 处理响应
} finally {
  clearTimeout(timer);
}
```

`fetch` 被中止时会以 `AbortError` 拒绝，应与普通网络错误区分处理。使用 Axios 时可按所用版本支持的 `signal` 选项传入同一个信号。

## 【问题】
14. 浏览器处理跨域 AJAX 请求时，什么情况下会触发预检请求（Preflight Request）？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

浏览器对不属于 CORS 简单请求的跨域请求先发送 `OPTIONS` 预检。常见触发条件包括使用 `PUT`、`DELETE` 等非简单方法；设置了非 CORS 安全列出的请求头；或使用不符合简单请求条件的 `Content-Type`，例如 `application/json`。简单请求的常见条件包括 `GET`、`HEAD`、`POST`，且请求头和内容类型符合规范列举的限制。是否预检由浏览器依据请求条件判断，也会受凭据模式等配置影响。

## 【问题】
15. CORS 预检机制如何保障接口访问的安全性？

## 【回答】
> 回答建议（资料未提供原文答案，以下为根据公开资料的整理）

预检让浏览器在发送特定的实际跨域请求前，先询问服务器是否允许该来源、请求方法和请求头。服务器通过 `Access-Control-Allow-Origin`、`Access-Control-Allow-Methods`、`Access-Control-Allow-Headers` 等响应头表达授权范围；不通过时，浏览器不会发送实际请求。它帮助服务器在请求产生副作用前声明跨域策略，但 CORS 是浏览器实施的跨域读取控制，不能代替身份认证、授权、CSRF 防护或服务端输入校验，也不能阻止非浏览器客户端直接请求接口。
